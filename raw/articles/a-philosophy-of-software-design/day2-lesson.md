# Day 2 · 复杂性的定义与症状

你真正的敌人不是 bug，不是需求变更，不是沉没成本，而是**复杂性**——那种让你看着一段代码发呆五分钟，却仍然不确定改了会不会爆炸的东西。

Ousterhout 第二章做了一件很少有工程师愿意做的事：把「复杂性」这个模糊的感受，**精确地定义出来**。

---

> *"Complexity is anything related to the structure of a software system that makes it hard to understand and modify the system."*

注意这个定义的边界。它不是说系统有多少功能，也不是说代码有多少行。它说的是：**难以理解和修改**。这个定义把复杂性从客观属性变成了主观体验——复杂性存在于读者的脑子里，不在代码里。

这个转变极其重要。很多工程师会说「我觉得这段代码挺清晰的」，然后认为讨论结束了。但 Ousterhout 明确告诉你：

> *"Complexity is more apparent to readers than writers."*

写这段代码的人永远是最难察觉复杂性的人。你在写的时候脑子里有完整的上下文，所有的隐式假设、所有的设计决策都是鲜活的。但三个月后的自己，或者你的同事，看到的是一个被剥夺了所有上下文的代码壳子。

这就是为什么代码审查有价值。不是为了抓 bug——而是为了检验：一个没有你上下文的人，能不能看懂这段代码。

---

## 复杂性的「公式」

Ousterhout 给了一个粗糙但有用的数学表达：

> *"The overall complexity of a system (C) is determined by the complexity of each part p (cp) weighted by the fraction of time developers spend working on that part (tp)."*

用公式写就是：**C = Σ(cp × tp)**

这个公式看起来显而易见，但蕴含着一个非常有力的推论：**把复杂性隔离到不常触及的地方，几乎等同于消除它**。

在游戏引擎设计里，这个思路随处可见。

以 Unity 的渲染管线为例。HDRP（High Definition Render Pipeline）的内部实现极其复杂——光照模型、Temporal AA、体积雾……这些模块的代码是真的难读，里面充满了各种 GPU 优化的 trick 和历史包袱。但绝大多数 Unity 用户从来不需要碰这些代码。他们只需要用几个 Volume Override 调参数，或者在 Shader Graph 里拖节点。

这就是 cp × tp 策略的完美案例：tp（接触频率）被设计为几乎为零，所以即使 cp（内在复杂度）很高，对整体系统的影响也微乎其微。

反过来，如果你设计的模块很复杂，而且每次改需求都要改它，那就是麻烦的开始。你在游戏里见过「上帝类」吗——一个 GameManager 挂满了所有可能的引用，任何功能改动都要来这里转一圈？那就是 cp 高 + tp 高，双重诅咒。

## 三个症状：学会识别复杂性的形态

Ousterhout 说，复杂性以三种形态出现在你的工作里。把它们讲清楚，是因为如果你连症状都看不清，你就无法对症下药。

### 症状一：变更放大（Change Amplification）

> *"A seemingly simple change requires code modifications in many different places."*

书里用了一个网页换背景色的例子：早期网页把颜色写死在每个页面里，换颜色就要改所有页面。听起来很蠢，但你在工作中见过多少等价的设计？

在 Unity 游戏开发里，最典型的变更放大来自**魔法数字**和**硬编码的字符串**。

```csharp
// 噩梦版本：改一个伤害系数要找 17 个地方
if (damage > 50) { ... }
enemy.health -= 50;
if (player.level == 5) { unlockAbility("damage_boost"); }
```

每次策划说「我们把基础伤害从 50 改成 60」，你就要开始全局搜索，祈祷没有漏掉任何一处。这就是变更放大——**你的设计决策（伤害数值）没有被集中管理，导致变更成本线性甚至超线性增长**。

更复杂的例子是层次设计的扁平化。如果 UI 代码直接依赖战斗逻辑的内部状态，当战斗逻辑重构时，UI 也必须跟着改。你改了一个底层的 struct 布局，上面五层代码都得跟着动——这就是典型的依赖链导致的变更放大。

在大型游戏项目里，这种痛苦往往在里程碑前集中爆发。「我只是改了个动画状态机的参数，怎么 AI 的行为也乱了？」追查下去发现 AI 代码直接读了动画状态机的枚举值，而那个枚举是和动画参数绑定的。漂亮的变更放大案例。

### 症状二：认知负荷（Cognitive Load）

> *"Cognitive load refers to how much a developer needs to know in order to complete a task."*

认知负荷不是代码行数的问题。Ousterhout 特别提醒了一个常见误区：

> *"System designers sometimes assume that complexity can be measured by lines of code... However, this view ignores the costs associated with cognitive load. Sometimes an approach that requires more lines of code is actually simpler, because it reduces cognitive load."*

这是在打脸「简洁就是代码短」这种肤浅理解。

我见过 Unity 项目里最经典的认知负荷来自**内存管理的隐式约定**。C++ 游戏引擎里更普遍——某个函数返回一个指针，但文档里没说是谁负责 free，于是每次调用这个函数你都要去翻源码，确认所有权语义。这就是认知负荷：**你在做一件本来不应该由你做的脑力工作**。

Rust 用所有权系统解决了这个问题——把「谁负责释放内存」从一个隐式约定变成了编译器强制执行的语义。认知负荷降到零，因为编译器不让你做错。

在 Unity C# 里，类似的问题经常出现在协程（Coroutine）上。当你调用 `StartCoroutine` 时，谁负责停止它？如果 GameObject 被 Destroy 了，协程会怎样？如果忘了 StopCoroutine，会不会泄漏引用？这些都是认知负荷——每次写协程你都要在脑子里跑一遍这些问题，而不是专注于业务逻辑本身。

UniTask 的出现部分是为了降低这个认知负荷：明确的取消机制（CancellationToken）、和 GameObject 生命周期绑定的扩展方法，让所有权语义更显式。

认知负荷还有一个隐形来源：**全局可变状态**。当你在 Update() 里读一个 static 变量，你需要知道这个变量在哪里被写入，什么时候，被哪些代码影响。这是一个无边界的知识需求。大型 Unity 项目里，充满了各种 Singleton，每个 Singleton 都是认知负荷的发射源。

### 症状三：未知的未知（Unknown Unknowns）——最危险的那个

> *"Of the three manifestations of complexity, unknown unknowns are the worst."*

变更放大让你的工作更多。认知负荷让你需要学更多东西。但这两个至少你知道问题存在——你可以花时间解决。**未知的未知是你不知道自己不知道**，所以你连开始寻找的机会都没有，直到 bug 出现。

书里用了一个精妙的例子：网站把背景色存在一个中心变量里（已经很好了），但某些页面还用了一个「强调色」，是背景色的深色版，却写死在各个页面里。你改了背景色，找到了所有引用中心变量的地方，以为改好了，但没人告诉你还有这些写死的强调色。

> *"Unknown unknown means that there is something you need to know, but there is no way for you to find out what it is, or even whether there is an issue. You won't find out about it until bugs appear after you make a change."*

在游戏开发里，这种体验太真实了。

举个具体场景：你在游戏里新增了一个状态枚举值 `PlayerState.Stunned`。你正确地更新了所有处理 PlayerState 的 switch 语句——至少你认为是所有的。但三天后，QA 报告说被眩晕的玩家还能触发某个特定的存档点对话。你去查，发现存档点触发逻辑里有一段旧代码，用硬编码的整数值（`if (playerState == 3)`）在做判断，新的 Stunned 状态整数值是 7，所以漏掉了。

这就是未知的未知：**你不知道有这个依赖，你没有办法在没有全局 grep 的情况下找到它，而且你甚至不知道需要去找**。

更深层的未知的未知来自**隐式的时序假设**。某个子系统假设它总是在另一个子系统初始化之后被调用，但这个假设没有文档，也没有代码上的断言。在某个平台上，由于不同的初始化顺序，某个边缘场景触发了崩溃。这个 bug 的查找成本极高，因为你甚至不知道要去找「初始化顺序」这条线索。

## 复杂性的两个根源：依赖与模糊

诊断完症状，Ousterhout 要讲病因了。

> *"Complexity is caused by two things: dependencies and obscurity."*

**依赖（Dependencies）**的定义：

> *"A dependency exists when a given piece of code cannot be understood and modified in isolation; the code relates in some way to other code, and the other code must be considered and/or modified if the given code is changed."*

依赖是软件的本质——你不可能写没有任何依赖的代码，毕竟你得调用标准库。但问题在于**不必要的依赖**和**不透明的依赖**。

依赖导致变更放大（你改 A，必须改 B、C、D）和认知负荷（要理解 A，你必须先理解 B、C、D）。

好的依赖设计是：让依赖**显式、简单、方向清晰**。坏的依赖是：隐藏在全局状态里的、双向的、跨层次的依赖。

在游戏引擎架构里，一个常见的依赖地狱是**循环依赖**。渲染模块依赖物理模块提供碰撞体位置，物理模块依赖渲染模块提供几何数据做碰撞检测，然后你发现两个模块必须同时初始化才能工作，任何一个先初始化都会访问到空指针。解决这种循环依赖通常需要引入一个中间层（比如共享的 Transform 数据），让两个模块都依赖这个中间层，而不是互相依赖。

**模糊性（Obscurity）**的定义：

> *"Obscurity occurs when important information is not obvious."*

模糊性直接制造未知的未知。书里的例子：一个叫 `time` 的变量，你不知道它是秒还是毫秒，是 UTC 还是本地时间，是启动时间还是帧时间。

在实际项目里，模糊性最常见的来源是：

1. **命名不精确**：`count` 是什么的数量？`flag` 标记了什么？`temp` 是临时值还是温度？

2. **不一致性**：同一个概念在不同地方用了不同的名字。游戏里的「角色」在一处叫 `Character`，另一处叫 `Actor`，还有地方叫 `Entity`。你永远不确定这三个是同一个概念，还是有细微区别。

3. **隐式约定**：某个函数有副作用，但没有文档，也没有任何迹象表明它会修改全局状态。

4. **过时的文档**：注释说「这个函数返回当前帧的时间」，但代码改过了，现在返回的是上一帧的时间。

Ousterhout 有一个重要的观察：

> *"The need for extensive documentation is often a red flag that the design isn't quite right. The best way to reduce obscurity is by simplifying the system design."*

这句话值得细品。文档本身不是解决模糊性的根本方案，因为文档也会过时，也会有人懒得写。**能让设计自我解释，才是正道**。当你需要写一大段注释来解释一个函数的行为时，这是一个信号：这个函数的设计可能有问题。

## 复杂性是渐进累积的——温水煮青蛙

> *"Complexity isn't caused by a single catastrophic error; it accumulates in lots of small chunks."*

这是最容易被忽视的一条。没有一个工程师是某天早上起来决定「我要把这个系统搞复杂」的。复杂性都是这样来的：

「这里先 hardcode 一下，等以后有时间再重构」
「这个 class 再加一个方法应该不影响什么」
「这个参数先传进来，以后可以优化」

每一个决定单独看都是合理的妥协。但几百个这样的妥协叠加在一起，就是 Ousterhout 说的：

> *"Eventually, there are so many of these small issues that every possible change to the system is affected by several of them."*

我在游戏项目里见过最典型的渐进腐化是**Event/Delegate 网络的扩张**。最初系统很干净，有几个清晰的事件。然后需求来了，加一个事件，再加一个，慢慢地，一个 PlayerDied 事件有了十七个订阅者，分散在代码库的各个角落。没有一处文档记录了所有订阅者，也没有人知道全貌。改任何一个订阅者都有可能影响到其他十六个。这时候调试 PlayerDied 相关的 bug 就变成了一场噩梦。

这就是为什么 Ousterhout 在第三章会提出「零容忍」哲学——等到复杂性已经严重了，消除它的代价往往比当初预防要高出十倍。

## 与其他经典书籍的对比

这里值得停下来比较一下不同书对「复杂性」的理解。

**《Clean Code》**（Robert Martin）对复杂性的处理是战术层面的：函数要短、类要小、命名要好。这些建议都是对的，但它们是**症状的管理**，而不是**病因的消除**。一个有 100 个小类、每个类方法都很短的系统，同样可以有极高的认知负荷和变更放大——因为要理解系统的行为，你需要跳转 100 次，追踪 100 个调用链。

Ousterhout 的框架更底层：他不是告诉你「怎么写」，而是告诉你「怎么思考」。复杂性 = 依赖 + 模糊性，三个症状是诊断工具。这个框架可以 evaluate 任何代码设计，而不是提供一套规则。

**《设计模式》**（GoF）提供了解决特定设计问题的模式，但它对复杂性的影响是中性的——模式既可以降低复杂性（通过提供标准的问题解法），也可以增加复杂性（通过引入额外的抽象层）。GoF 本身没有帮你判断「什么时候用模式比不用更简单」。APoSD 的框架给了你这个判断标准：问自己，这个模式降低了认知负荷吗？减少了变更放大吗？还是制造了更多的未知未知？

**《Pragmatic Programmer》**讲「DRY（Don't Repeat Yourself）」——这对应了 Ousterhout 的变更放大问题。重复的代码是隐式依赖的一种形式：多处代码依赖同一个业务规则，但没有显式连接，所以变更时必须同步多处修改。DRY 是一个好的 heuristic，但 APoSD 给出了它背后的原理。

## 游戏引擎视角：大型 Unity 项目里的复杂性观察

游戏开发是观察「复杂性如何演化」的绝佳场所，因为游戏项目有一些独特的特征：

1. **需求变化极快**：策划的设计会反复迭代，这意味着你的代码需要面对大量变更。变更放大的代价在游戏开发里特别高昂。

2. **跨学科协作**：程序员、策划、美术操作同一个代码库（特别是在 Unity 里，策划经常直接操作 ScriptableObject 和 Prefab）。认知负荷必须在不同背景的人之间共享，这对「代码是否显而易见」提出了更高要求。

3. **实时系统的隐式顺序**：游戏的每一帧都有更新顺序、渲染顺序、物理顺序，这些顺序之间存在大量隐式依赖。未知的未知在这里特别危险。

以 Unity ECS（Entity Component System）为例，它的出现部分是为了解决传统 OOP 游戏开发中的复杂性问题：

- **变更放大**：在传统 Unity 里，角色的血量可能存在 PlayerHealth 组件里，技能系统通过 GetComponent<PlayerHealth>() 访问它，UI 系统也通过 GetComponent 访问，存档系统也是。改了 PlayerHealth 的接口，需要在所有用到它的地方做修改。ECS 把数据（Component）和行为（System）分离，通过查询系统解耦依赖。

- **认知负荷**：传统 Unity 里，一个 GameObject 挂了十几个 Component，互相调用，你需要在脑子里重建整个调用图才能理解行为。ECS 的数据是扁平的、显式的，System 的依赖通过数据访问声明出来（读哪些 Component，写哪些 Component），认知负荷更低。

- **未知的未知**：传统 Unity 里的 Singleton 和 event 是未知未知的温床。ECS 通过强制所有数据访问显式声明，让很多隐式依赖变成了显式依赖。

当然，ECS 本身也引入了新的复杂性（更陡的学习曲线，调试更难），这说明设计总是有 trade-off 的，没有银弹。但它的设计方向是正确的：**把复杂性从隐式变为显式，从散射变为集中**。

## 品味判断时刻：你真正该担心的是什么？

读完这章，一个重要的品味判断是：在这三种症状里，**你更应该主动预防哪一个**？

变更放大很痛，但至少你知道它在那里——每次改东西你都会感到痛。
认知负荷很累，但至少你可以通过写文档、代码审查来部分缓解。

**未知的未知才是真正的黑天鹅**。你不知道它们的存在，所以你没有机会预防，只能在 bug 出现后被动响应。

这意味着，在设计系统的时候，**最值得投资的是：让依赖变得显式**。

隐式依赖是未知未知的主要来源。当你把一个假设（比如「这个函数总是在那个函数之后调用」）写成断言或者类型约束，你就把一个潜在的未知未知变成了已知的已知。当你把一个全局状态的访问变成一个显式的参数传递，你就把一个隐式依赖变成了显式依赖。

从这个角度看，强类型系统（Rust、Haskell、甚至 C# 的 nullable reference types）的真正价值不是「让编译器帮你抓 bug」，而是**把隐式约定变成显式契约，消灭未知的未知**。

## 复杂性的隐形增长：一个真实的腐化时间线

我想用一个虚构但非常真实的游戏项目案例，把复杂性的「渐进积累」具象化。

**第一个月：项目干净，一切美好**

项目开始，有一个简洁的 `CharacterController`，负责移动、跳跃、动画同步。依赖很清晰：接收输入，输出物理位移。认知负荷极低，新人两小时就能看懂整个文件。

**第三个月：第一批「临时」决定**

策划要求区分地面状态和空中状态，于是加了一个 `isGrounded` 标志。战斗系统需要知道角色的移动速度，于是 `CharacterController` 开始向外暴露内部状态。UI 系统为了显示跳跃次数，直接依赖了 `CharacterController` 的内部变量。每一个决定单独看都是合理的：「现在先这样，以后重构」。

**第六个月：事情开始变味**

现在 `CharacterController` 知道的事情太多了：它知道角色的血量（因为被击中会触发硬直），它知道技能状态（因为某些技能会改变移动速度），它知道游戏模式（PVP 和 PVE 的碰撞规则不同）。变更放大开始出现：每次加新技能，`CharacterController` 都要改。认知负荷极高：新人读这个类需要半天，因为它的行为依赖十几个外部状态。

**第十个月：没人敢动它了**

这个 `CharacterController` 变成了所有人最害怕的文件。没有完整的测试，没有清晰的文档。但它又是核心逻辑，不能绕过。任何改动都可能引入你想不到的 bug——因为它的依赖已经多到没有人能在脑子里重建完整的影响图。未知的未知遍布其中。

这就是 Ousterhout 说的「每一个小依赖单独看无害，但积累起来就是灾难」。每一步都有合理的理由，但每一步都在往同一个方向走。

## 认知负荷的度量：代码审查的第一性原则

这里有一个实践上很有用的推论：**代码审查的核心任务，就是检测认知负荷**。

很多团队的 code review 变成了风格检查——命名够不够规范、格式够不够整齐、有没有遵守 linting 规则。这些都有价值，但它们不是最重要的。

最重要的是：**作为一个没有上下文的读者，我能在合理的时间内理解这段代码的行为吗？如果不能，为什么？**

这个问题的答案，直接对应了 Ousterhout 的三个症状：

- 如果我理解了这段代码，但感觉改动它会影响很多地方 → 变更放大的风险
- 如果我需要大量前置知识才能理解这段代码 → 认知负荷过高
- 如果我看完觉得「我不确定改这里还需要改哪里」 → 未知的未知的警报

这三个问题应该成为你的 code review checklist 的一部分。不是「这段代码好不好看」，而是「这段代码对下一个读者是否公平」。

## 为什么说复杂性是「读者视角」的判断，是最深刻的洞察之一？

我想在这个点上多停留一会儿，因为我认为它是全书最重要的认识论立场。

软件工程里有一个根深蒂固的偏见：写代码的人是主体，读代码的人是客体。我们说「这段代码很难」，通常意思是「写这段代码很难」——算法复杂、逻辑繁琐。但 Ousterhout 把这个关系颠倒了：**代码最重要的受众不是编译器，不是写代码的人，而是未来需要维护它的人**。

这个立场有几个重要的推论：

**推论一：代码不是给自己写的。** 你写一段代码，用它一次，然后你的工作就完成了——对你来说。但这段代码可能被你、你的同事、你的接班人读一千次。每一次的认知成本都是实际成本。

**推论二：「我看得懂」不是充分条件。** 最了解这段代码的人，永远是刚写完它的那个人。如果你是评判标准，你永远是最偏向的那个裁判。

**推论三：减少认知负荷是真实的生产力优化。** 不是软技能，不是「代码美观度」，而是实际的开发效率提升。一个认知负荷高的系统，每次改动都需要更多时间来理解上下文，产出等量的功能需要更多时间，且更容易出错。

这和《代码整洁之道》对「可读性」的强调是一脉相承的，但 APoSD 更进一步：它给了你一个可以量化和诊断的框架，而不只是「代码应该像散文一样流畅」这样的主观建议。

**Q2（应用）：** 你正在开发一个 Unity 手游的战斗系统。策划要求新增一个「冰冻」状态，被冰冻的单位：移动速度变为 0，技能冷却暂停，受到水属性伤害额外增加 30%。

在开始写代码之前，请分析：在你的现有系统里，新增这个状态可能触发哪种复杂性症状？变更放大在哪里？认知负荷来自何处？最可能出现哪种未知的未知？

**Q3（品味）：** 下面是同一个问题的两种设计方案——

**方案 A**：写一个详细的注释文档，解释一个函数的所有行为、副作用、前置条件和后置条件。注释有 30 行，覆盖了所有边缘情况。

**方案 B**：重新设计函数，消除副作用，让函数签名通过类型系统表达所有约束，使函数行为通过代码本身变得显而易见。函数注释只有 3 行，说明「为什么」而非「是什么」。

从 APoSD 的视角，哪个方案更好？Ousterhout 会怎么看「好注释」vs「好设计」的优先级？
