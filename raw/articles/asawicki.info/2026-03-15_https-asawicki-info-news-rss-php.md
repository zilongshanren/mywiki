<p>When I was working at AMD, I was deeply involved in this area - writing code, publishing articles on the <a href="https://gpuopen.com/">GPUOpen website</a>, attending GDC, and even giving a talk there twice. <h1>Introduction</h1>
<p>Every year, GDC is the pinnacle moment for game developers, including rendering programmers. Whether it’s worth going there is a separate question, considering the cost of travel (especially for someone living in Europe) and the price of a hotel in San Francisco. There are other important events as well: Nvidia has <a href="https://www.nvidia.com/gtc/">GTC</a>, Epic has <a href="https://www.unrealengine.com/en-US/unreal-fest">Unreal Fest</a>, Vulkan has the <a href="https://vulkan.org/events/vulkanised-2026">Vulkanised conference</a> as its main event, and graphics researchers gather at <a href="https://www.siggraph.org/">SIGGRAPH</a>. But GDC in March is the annual opportunity for people from all these worlds to get together, listen to talks, and socialize, so we should all pay attention to what happens there.</p>
<p><b><a href="https://devblogs.microsoft.com/directx/directx-gdc-2026/">DirectX Innovation at GDC 2026</a></b> is the article announcing the talks Microsoft delivered during the event. “DirectX State of the Union” is the main one, spanning a variety of topics related to recent DX12 developments. “DirectX is Bringing Console-Level Developer Tools to Windows” is also very interesting, announcing unprecedented progress in graphics tooling, especially PIX. Microsoft was joined on stage by representatives of all four current PC GPU vendors (AMD, Intel, Nvidia, Qualcomm), who normally compete with each other. This is always a sign that something important is happening (like the memorable presentation <a href="https://gdcvault.com/play/1020791/">"Approaching Zero Driver Overhead in OpenGL"</a> from GDC 2014, which I mentioned as part of the story in my article <a href="articles/graphics_apis_yesterday_today_tomorrow_en.php">Graphics APIs – Yesterday, Today, and Tomorrow</a>). Hopefully video recordings or slides from this year’s talks will available online after some time. For now, we need to analyze what we have - just the web pages they published.</p>
<p>GPU vendors also posted their announcements simultaneously, expressing support for Microsoft’s announcements.</p>
<ul>
<li><a href="https://gpuopen.com/learn/amd-microsoft-gdc-2026/">AMD and Microsoft partner on DirectX ML, DirectStorage, and developer tools at GDC 2026</a></li>
<li><a href="https://www.intel.com/content/www/us/en/developer/articles/news/microsoft-collaboration-powers-future-of-pc-gaming.html">Intel & Microsoft collaborate closely on the Future of PC Gaming</a></li>
<li><a href="https://developer.nvidia.com/blog/nvidia-rtx-innovations-are-powering-the-next-era-of-game-development/">NVIDIA RTX Innovations Are Powering the Next Era of Game Development</a>. As we might expect, Nvidia being Nvidia, they keep developing lots of custom technology, mostly focused on AI.</li>
</ul>
<p>On one hand, for Microsoft and GPU vendors (also called Independent Hardware Vendors - IHVs), GDC is a major milestone every year. Developers crunch on their code to finish demos, articles and slide decks are prepared, travel and meetings get scheduled... On top of the engineering effort, there is surely politics involved. Cooperation between teams in a big corporation is difficult enough. Here, Microsoft needed to coordinate with all PC GPU vendors. I believe it is even more challenging for Khronos, where all hardware and software vendors that care about graphics (both desktop and mobile) come together, but I’m sure it was a hectic time there as well.</p>
<p>But on the other hand, what has been announced in these talks will only ship to the public in the upcoming months, basically “when it’s done”, so nothing really changed this week. We just received new information that had been secret so far. It’s like watching a teaser video for a new game (when we read an article announcing new technology) or maybe a gameplay trailer (when we can see an actual API spec), with the game shipping later this year.</p>
<h1>1. Tool improvements</h1>
<p>The main blog post on DirectX Developer Blog:
<br><b><a href="https://devblogs.microsoft.com/directx/directx-bringing-console-level-developer-tools-to-windows/">DirectX: Bringing Console-Level Developer Tools to Windows</a></b></p>
<p>This topic is the most interesting and most important for me personally. Compared to the debuggers we have for CPU programming languages (whether high-level like Python or native like C and C++), I think GPU debugging is really in the Stone Age. GPU crashes (also known as Timeout Detection and Recovery - TDR - whether caused by a timeout or a memory page fault) are especially difficult to debug. Sure, frame capture tools like <a href="https://devblogs.microsoft.com/pix/">PIX on Windows</a> and <a href="https://renderdoc.org/">RenderDoc</a> are helpful in debugging various problems, but they require a frame that successfully rendered until the <code>Present()</code> call. The Debug Layer and GPU-Based Validation also do a great job. Finally, crash capture tools like <a href="https://microsoft.github.io/DirectX-Specs/d3d/DeviceRemovedExtendedData.html">DRED</a> and custom vendor tools - <a href="https://developer.nvidia.com/nsight-aftermath">Nvidia Aftermath</a> and <a href="https://gpuopen.com/radeon-gpu-detective/">Radeon GPU Detective</a> - help identify the cause of a crash... when they work, because sometimes they don’t show any meaningful information.</p>
<p>I wish we had a proper debugger for shaders, just like we have debuggers for CPU code - with breakpoints, step-by-step execution, watching the values of local variables, etc. (They would likely need to be conditional breakpoints for a specific frame, draw call, and pixel coordinate or thread ID, because there are thousands of threads running simultaneously on the GPU and millions of them starting every frame.) Sure, PIX and RenderDoc offer shader debugging, but RenderDoc does it by emulating shaders on the CPU, which can break in many cases because it doesn’t show what really happens on the GPU. What if there are timing issues or race conditions, such as a missing barrier? What if there is a bug in the shader compiler for a specific GPU?</p>
<p>Of course, this is not as easy on the GPU as it is on the CPU, where a thread or a process can be suspended while the operating system, IDE, and other apps continue running. On a GPU, the entire chip may be busy executing just a single draw call. However, I can still imagine a scenario where the GPU is stopped, breaking into a debugging session, while the debugger runs on a separate machine or on the same machine with the desktop rendered using integrated graphics. In fact, stopping the entire machine and debugging it from a remote system connected through a network is possible using <a href="https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/windbg-overview">WinDbg</a>, but that is kernel-mode, low-level, hardcore debugging. So we can say that making GPU debugging possible is mostly a matter of developing good high-level tools.</p>
<p>Despite the confidentiality of console SDKs, it shouldn’t be a secret if Microsoft disclosed it in the title of their talk that consoles like Xbox have better graphics tools than the PC. In <b><a href="https://devblogs.microsoft.com/directx/directx-bringing-console-level-developer-tools-to-windows/">DirectX: Bringing Console-Level Developer Tools to Windows</a></b>, they announced a major update to PIX on Windows, along with other tools and APIs intended for debugging. Let’s see what exactly they announced.</p>
<h2>DirectX Dump Files</h2>
<p>First of all, they disclosed a plan to support new DirectX Dump Files (.dxdmp), containing a dump of the GPU state after it crashes. They will be available to open in PIX. It’s great to see they have buy-in from all GPU vendors, as this surely requires their deep involvement and support. It’s also great that there will be a toggle to adjust the trade-off between performance overhead and <i>"actionability"</i> (as they called it), since gathering more data may impact performance, which in turn could hide the bug. The “no overhead” mode, where supported, may even be suitable to leave always enabled for end users. Dump files will be available for manual management or collected by Microsoft via Watson.</p>
<p>This all looks very promising. I have just one concern. Based on the example screenshots shown from all four GPU vendors, I suspect this whole system may just be a generic placeholder, with the specific data gathered and displayed being highly dependent on the GPU. We can only hope that the actual crash dumping and the data gathered from the crash will be:</p>
<ul>
<li>reliable - pinpointing the actual crash most of the time instead of showing some generic failure error or outputting random markers on every attempt,</li>
<li>understandable - showing information that is high-level enough, related to the DX12 API, and actionable, rather than just a low-level GPU state dump.</li>
</ul>
<p>From the screenshots shown:</p>
<ol>
<li>I would score Nvidia the highest. Given the unreliable nature of GPU crash capturing, showing information like "Confidence: X%" or "Possible Cause 1/2/..." looks like a good direction.</li>
<li>AMD seems to display the same information that the current text-based reports from Radeon GPU Detective contain. (A tool that I had the honor and pleasure to work on.) Which is great, because I know their crash capturing is very reliable. The information shown is sometimes just too low-level. For example, it is known that it shows a "Make Resident" event (also visible in this screenshot) as an internal driver operation, even if the developer didn’t explicitly call <code>ID3D12Device::MakeResident</code>.</li>
<li>Intel scores the worst, as it shows raw GPU registers with cryptic names like <code>VS_INVOCATION_COUNT_RCSUNIT_BE_</code> and their hexadecimal values. It’s great that they are able to dump the exact state of the GPU at the moment it crashed, but do they really believe game developers will read thousands of pages of <a href="https://www.intel.com/content/www/us/en/docs/graphics-for-linux/developer-reference/1-0/overview.html">their GPU documentation</a> to make sense of it?</li>
</ol>
<h2>PIX API</h2>
<p>Next, Microsoft announced the PIX API - a programmatic way to access all the data a PIX capture and the new crash dump can contain, available to C++, C#, and Python. This is a great step forward. It will definitely be useful for various kinds of automation. I can also imagine developing an MCP server, so an AI agent could use such captures to help with graphics debugging or performance optimization. It’s worth mentioning that by doing this, PIX is basically catching up with RenderDoc, which already has its own <a href="https://renderdoc.org/docs/python_api/index.html">Python API</a>.</p>
<h2>DebugBreak</h2>
<p>Next, they are going to add a HLSL intrinsic function <code>DebugBreak()</code>. See the specification: <a href="https://github.com/microsoft/hlsl-specs/blob/main/proposals/0039-debugbreak.md">0039 - Debugging Intrinsics</a>. It will be similar to the <code>assert</code> macro known from C++ and other CPU languages, triggering an instant crash, which can help identify exactly where an asserted condition was hit - in which frame, which draw call or dispatch, and hopefully also with a pixel or thread ID. It definitely has a chance to work more reliably than my hacky <a href="https://github.com/sawickiap/ShaderCrashingAssert">ShaderCrashingAssert library</a>.</p>
<p>Too bad they didn’t define any parameter that would allow the shader to return some data to the crash dump. Even a single <code>uint</code> or <code>uint4</code> would make a huge difference. Dear Microsoft, can we have that, please???</p>
<p>I also wish that together with this “assert” function, they worked on some standardized “printf” function that would let shaders output messages and data while running, even without crashing. Having those two would move GPU debugging to the Medieval Ages. Implementing convenient logging in HLSL has been discussed many times, including in the good article <a href="https://www.abolishcrlf.org/2025/12/31/Printf.html">An Experimental Approach to printf in HLSL</a> by Chris Bieneman - still unofficial, despite the fact that he is a Microsoft employee. After this year’s GDC there are still no signs that Microsoft is working on standardizing this, unfortunately.</p>
<h2>PIX event configurability</h2>
<p>Then we have PIX events (also known as markers) - the begin/end events with custom strings that we use to organize our draw calls into a logical hierarchy for easier debugging in PIX or RenderDoc. Microsoft announced that they will finally be passed to the graphics driver. This is a huge thing. Let me explain why.</p>
<p>There are basically two ways graphics debugging tools can operate. The first is injecting themselves into the game process and intercepting all calls to the graphics API. That’s what PIX, RenderDoc, and <a href="https://github.com/LunarG/gfxreconstruct">GfxReconstruct</a> do. This is great, because it captures all the calls and all the data at a high level, exactly as the game developer passed them. On the other hand, it causes multiple problems:</p>
<ul>
<li>The game must be launched from the tool, which involves specifying the path to the executable, command-line parameters, etc. It can be difficult if a game has a more complex launch workflow involving Steam, Epic Game Store, or some other launcher app, requiring it to be a sub-process of the launcher, etc. Various scenarios are possible that make such debugging difficult or simply impossible.</li>
<li>The game can detect that it has been altered and refuse to launch, especially when using some anti-piracy or anti-cheat protection.</li>
<li>There are various other scenarios where the API injection can break. I’ve seen many of those. Very often the tool needs to be fixed for a particular game title. Problems may involve having some extra software installed on the system (like OBS Studio or other video capture tools), the game doing something unusual with the swap chain (for example when using frame generation), etc.</li>
</ul>
<p>The second mode is a tool connecting directly to the graphics driver (e.g. through a socket) and fetching data from it. That’s how <a href="https://gpuopen.com/tools/">Radeon Developer Tools</a> operate. It works independently of what game is running or how it was launched. The game process is not altered in any way. A strategic decision to implement tools like this has many advantages. They work very reliably. However, there is one big caveat: the calls that the driver sees are not necessarily the same calls that the game developer made using the graphics API.</p>
<p>In Vulkan, this is not such a big issue, because the driver basically implements the API “on the other side”. It can also expose new extensions (like VK_EXT_debug_utils) that are available to the game code for direct use. With DirectX 12, however, this is not that simple. The sequence looks like this: Game engine code -> DX12 API -> DirectX Runtime (Microsoft code) -> Device Driver Interface (DDI) API -> Driver. Some information gets lost along the way. This includes PIX events. Because of that, AMD had to define their own way of submitting events so they become visible in their tools, in the form of the <a href="https://github.com/GPUOpen-LibrariesAndSDKs/AGS_SDK">AMD GPU Services (AGS) library</a> or a replacement header for PIX events. See <a href="https://gpuopen.com/manuals/rgd_manual/help_manual/#known-issues-and-workarounds">RGD documentation - Known issues and workarounds</a> for more details. Now, with Microsoft changing their mind and allowing standard PIX events to reach the driver, this will no longer be necessary. Finally!</p>
<p>I hope that together with begin/end events, Microsoft will also pass to the driver the string names that we assign to our textures and buffers using <code>ID3D12Object::SetName</code> calls. Preferably also data set through <code>ID3D12Object::SetPrivateData</code> - that would provide much more flexibility. Their new <a href="https://microsoft.github.io/DirectX-Specs/d3d/D3D12PIXMarkers.html">PIX Markers spec</a> mentions <code>SetName</code> to be passed to DDI. This is great, because currently, AMD tools fetch these names through the Event Tracing for Windows (ETW) mechanism, which is a workaround and doesn’t always work reliably. (Which is not a secret - see the article <a href="https://gpuopen.com/learn/rmv-directx-named-resources/">Viewing DirectX® 12 Named Resources with Radeon™ Memory Visualizer 1.3</a>).</p>
<p>By the way, I personally like the Vulkan approach of formally defining a way to inject layers into the API. I believe it’s high time for Microsoft to do the same. I was secretly hoping they would add such support for layers a long time ago, but they still haven’t, so every tool like PIX, RenderDoc, GfxReconstruct, or <a href="https://github.com/GPUOpen-Tools/GPU-Reshape">GPU Reshape</a> needs to implement its own solution and struggle with numerous issues. <a href="https://github.com/NVIDIA-RTX/Streamline">Nvidia Streamline</a> seems to be an effort in this direction, providing a generic layer system for DX12, but because it’s made by Nvidia, unfortunately other GPU vendors didn’t join the effort to spread its adoption. (Hopefully they will have more luck with the <a href="https://shader-slang.org/">Slang shading language</a>.)</p>
<h2>Live Shader Debugging</h2>
<p>Microsoft also announced they are working on <i>“real-time, on-chip shader debugging”</i>. This almost sounds too good to be true. But they are giving themselves time until 2027, so I believe that by then they may be able to achieve it, with intense effort and support from GPU vendors. That would be the holy grail that could bring GPU debugging into modern times, catching up with CPU programming languages.</p>
<p>One big challenge in bringing this feature to PC is stopping the GPU and inspecting its state at the exact moment, as I described above. But another problem is showing and stepping through the shader code. I hope it won’t be the GPU assembly (ISA) or the intermediate language (DXIL, SPIR-V), but the real high-level shader language (HLSL, GLSL) as written by the game developer. Supporting this would require all stages of shader compilation to preserve the correlation between ISA instructions and high-level shader source lines, as well as between GPU registers and variables in the shader source. Shaders are highly optimized, with everything inlined. There is no call stack to inspect. Providing a decent debugging experience must therefore be a complex endeavor.</p>
<h1>2. ML advancements</h1>
<p>The main blog post on the DirectX Developer Blog:
<br><b><a href="https://devblogs.microsoft.com/directx/evolving-directx-for-the-ml-era-on-windows/">Evolving DirectX for the ML Era on Windows</a></b></p>
<p>Let's say it plainly: machine learning using deep neural networks is, at a low level, largely about matrix multiplication. GPUs are great at that. We still call them "graphics processing units", but developers discovered a long time ago that they perform well for many other kinds of tasks. First it was breaking ciphers, then crypto mining, and now it's AI. At a high level, such workloads may look very similar to graphics, which is also about regular, massively parallel processing of vectors and matrices. However, when we dig deeper, there are many differences, including:</p>
<ul>
<li>In graphics, we typically use vectors with up to four components, interpreted as XYZW or RGBA. Matrices are also typically up to 4x4. In ML, we may have tensors of much larger sizes and higher numbers of dimensions (e.g., 4D), which must be divided into blocks for efficient processing.</li>
<li>In graphics, we typically use 32-bit floating-point types (FP32), sometimes also half-floats (FP16). In ML inference, using even smaller data types often maintains sufficient quality while providing memory and performance benefits, including INT8, INT4, and even 8-bit floating-point types (FP8) (of which there are many variants - see my article <a href="articles/fp8_tables.php">FP8 data type - all values in a table</a>).</li>
<li>In graphics, we write shader code with a single thread in mind, calculating a single pixel or another data element. Cross-thread communication using wave functions or groupshared memory is typically used as a performance optimization. In ML, a more optimal algorithm may involve the cooperative work of many threads on a single vector or matrix.</li>
<li>In ML, data sometimes needs to be swizzled compared to a naïve row-major layout - preferably into some opaque, vendor-specific format. Similarly, the workload may be optimized across multiple passes, for example by fusing several operations into one, effectively executing at the level of entire compute dispatches or even command buffer submissions. In graphics, this is something we typically achieve through manual shader editing or by implementing a "render graph" system in a game engine. For ML, it would be better if such optimizations could target a specific GPU automatically.</li>
</ul>
<p>GPU vendors introduced dedicated hardware to accelerate these types of <del>matrix multiplication</del> ML workloads. Nvidia has been the most effective at marketing theirs, making sure that even average gamers have heard about Tensor Cores, but AMD also has its Wave Matrix Multiply-Accumulate (WMMA) instructions, and Intel has its XMX units. The problem is that they are available in purely compute-oriented APIs like Nvidia CUDA, AMD HIP/ROCm, and Intel oneAPI, not in graphics APIs and shader languages. They are also used in proprietary upscaling technologies: DLSS, FSR 4, and XeSS, respectively - all implemented as black-box libraries performing some vendor-specific magic under the hood.</p>
<p>Is this the desired and target state of things? Having a custom, proprietary, high-quality technology like DLSS surely gives a vendor some competitive advantage when gamers decide which graphics card to buy. But on the other hand, do GPU vendors really like the fact that precious transistors on their chips and their potential TOPS of computational power stay idle most of the time? I don't think so. I think the real issue is exposing these capabilities in a way that is unified across vendors, high-level, and convenient enough for game developers on one hand, while still utilizing the full performance potential of the hardware on the other.</p>
<p>Vulkan faces the same problem. They solve it in a typical Vulkan way - by introducing extensions. We have VK_KHR_shader_integer_dot_product, VK_KHR_cooperative_matrix, VK_KHR_shader_float16_int8, VK_EXT_shader_float8, and many others. In DirectX 12, Microsoft has made several attempts to offer similar capabilities, with mixed success.</p>
<ul>
<li>First, Shader Model 6.4 added intrinsic functions for dot products on <b>8-bit integer types</b>, which are useful for the inference of ML models quantized to the INT8 type. Shader Model 6.6 extended them with functions for packing and unpacking these small types.</li>
<li>Microsoft added <code>D3D12_FEATURE_DATA_WAVE_MMA</code> to the Agility SDK 1.711.3-preview in June 2023. It was supposed to add support for instructions performing Matrix Multiply-Accumulate cooperatively across a wave, with an API to enumerate all supported matrix dimensions and element data types. Judging by its name, it could have been related to what AMD added to their hardware. Apparently it was a false start, because Microsoft retracted it from the Agility SDK before it shipped in the retail version. Fun fact: one leftover of this abandoned API still remains in retail DX12 in the form of the <code>D3D12_FEATURE_DATA_D3D12_OPTIONS9::WaveMMATier</code> structure member.</li>
<li>Approaching the problem from a completely different angle, Microsoft added a new API: <b>DirectSR</b> to the Agility SDK 1.714.0-preview in May 2024. It was supposed to unify all vendor-specific image upscaling technologies (marketing term: "super resolution"): DLSS, FSR, and XeSS in a single API. To me, it looked strange from the very beginning. The whole concept of DirectX 12 as a low-level API doesn't match providing ready-made, multi-pass, black-box graphics effects like this. It is also notoriously difficult to design a good API for a standalone graphics effect, which I described in: <a href="news_1702_how_to_design_api_of_a_library_for_vulkan">How to design API of a library for Vulkan?</a>. On top of that, by the time Microsoft developed their unified upscaling API, GPU vendors were already working on extending their proprietary APIs with frame generation, and then denoising (marketing term: "ray reconstruction"). Finally, Microsoft removed DirectSR from the preview Agility SDK without ever shipping it in the retail version, and without any official announcement.</li>
<li>There are also <b>Metacommands</b> in the DX12 API. My RTX 4090 enumerates metacommands with names such as "Conv (Convolution)", "CopyTensor", and "GEMM (General matrix multiply)", which clearly indicates they can be used for executing ML workloads. However, they are not typically intended to be used directly by developers. Instead, they are used under the hood by DirectML and DirectSR.</li>
</ul>
<p>Side note: <a href="https://github.com/microsoft/DirectX-Specs/blob/master/d3d/WorkGraphs.md">GPU Work Graphs</a> are not this kind of technology. This recent addition to the DX12 API allows the execution of entire graphs of different shaders. However, we still need to focus our implementation on individual threads and manually control how they are spawned. There is no automatic operator fusion or other optimization performed automatically, like ML frameworks do. Work Graphs are more intended for compute work serving rendering workloads, as an extension of Indirect calls that let the GPU spawn new work on its own. They provide more flexibility by supporting a switch to a different shader, as opposed to only changing the vertex/index buffers and the number of vertices/instances/threads, as in Indirect calls.</p>
<p>Here we are now, after GDC 2026, and Microsoft's current plans to expose these ML-related hardware capabilities seem to come from both angles at once:</p>
<p><b>1. As instructions available in normal shaders</b></p>
<p>These can be useful for implementing inference of small ML models as part of existing vertex/pixel/compute shaders. For example, this could include neural texture (de)compression, approximation of complex material and lighting models (BRDFs), character animation, or approximate physics simulation. In the future, we may have many small models evaluated every render frame.</p>
<p>These are not really news from this week, because they were announced and their specifications have been available for quite some time. Microsoft develops its HLSL language advancements quite openly by sharing <a href="https://microsoft.github.io/hlsl-specs/proposals/">HLSL specification proposals</a>.</p>
<p><b>Long vectors</b>, as specified in proposal <a href="https://github.com/microsoft/hlsl-specs/blob/main/proposals/0026-hlsl-long-vector-type.md">0026 - HLSL Long Vectors</a>. It adds support for vectors with more than four elements, e.g. <code>vector<float, 15></code>. Note that they are still normal variables, local to an individual shader thread.</p>
<p><b>Linear algebra</b>, as specified in proposal <a href="https://microsoft.github.io/hlsl-specs/proposals/0035-linalg-matrix/">0035 - Linear Algebra Matrix</a>. It adds a matrix type, such as <code>Matrix<ComponentType::F16, 8, 32, MatrixUse::A, MatrixScope::Wave></code>, as well as vector-matrix and matrix-matrix operations like <code>Multiply</code> and <code>MultiplyAccumulate</code>.</p>
<p>Note that the matrix has many template parameters:</p>
<ul>
<li>Element data type (including <code>I8</code> and two <code>F8</code> formats).</li>
<li>Number of rows and columns.</li>
<li>"Usage" (<code>A, B, Accumulator</code>), meaning the intended role as arguments of the <code>a * b + c</code> operation.</li>
<li>"Scope" (<code>Thread, Wave, ThreadGroup</code>), meaning whether the matrix is local and different in each thread, or uniform across the entire wave or thread group and thus shareable across threads and processed cooperatively.</li>
<li>When performing a load/store to a <code>[RW]ByteAddressBuffer</code>, there is also "Layout" (<code>RowMajor, ColumnMajor, MulOptimal, OuterProductOptimal</code>), which allows matrices containing intermediate results that we do not need to access directly to be stored in some opaque, GPU-specific layout optimized for the best performance.</li>
</ul>
<p>This API looks very clean and convenient. I believe they may have found a good abstraction. Hopefully, with enough effort put into developing shader compilers, it can also deliver good performance while utilizing the hardware capabilities of each GPU. My concern is whether the API will keep up with new hardware capabilities that GPU vendors may want to expose. <h1>Barriers needed</h1>
<p>The functions <code>ClearUnorderedAccessViewUint</code> and <code>ClearUnorderedAccessViewFloat</code> require the buffer to be in the <code>D3D12_RESOURCE_STATE_UNORDERED_ACCESS</code> state, just like when writing to it from a compute shader. If the buffer was in a different state before, we need to issue a transition barrier (<code>D3D12_RESOURCE_BARRIER_TYPE_TRANSITION</code>). If we use the buffer as a UAV before or after the clear, the state doesn't change, but we need to issue an UAV barrier (<code>D3D12_RESOURCE_BARRIER_TYPE_UAV</code>) to make the commands wait for each other. Otherwise, a race condition could occur, as the commands could run in parallel.</p>
<p>These restrictions make buffer clearing with these functions similar to using compute shaders, and different from <code>ClearRenderTargetView</code> and <code>ClearDepthStencilView</code>, which are used for clearing textures, or from copy operations (<code>CopyResource</code>, <code>CopyBufferRegion</code>), which do not require barriers around them. For a more in-depth investigation of this distinction, see my older article: <a href="news_1722_secrets_of_direct3d_12_copies_to_the_same_buffer">"Secrets of Direct3D 12: Copies to the Same Buffer"</a>.</p>
<h1>Conversions from uint</h1>
<p>Here comes the main part that inspired me to write this article. I asked myself how are the <code>UINT[4]</code> values passed to the <code>ClearUnorderedAccessViewUint</code> function converted to the values of elements in the buffer, depending on the element format. I could not find any mention of this on the Internet, so I did some experiments. Below, I summarize my findings. Unfortunately, the behavior is inconsistent between GPU vendors! I tested on Nvidia (GeForce RTX 4090, driver 591.44), AMD (Radeon RX 9060 XT, driver 25.11.1), and Intel (Arc B580, driver 32.0.101.8250) - all on Windows 25H2 (OS Build 26200.7462) with DirectX Agility SDK 1.618.3 Retail.</p>
<ul>
<li>If the format is <code>DXGI_FORMAT_R32G32B32A32_UINT</code>, the values are written as-is, because the format matches exactly the values accepted by the function, so for example <code>{1, 2, 3, 4}</code> gets written as <code>0x00000001, 0x00000002, 0x00000003, 0x00000004, 0x00000001, 0x00000002, 0x00000003, 0x00000004, ...</code></li>
<li>If the format has less components per element, like in <code>DXGI_FORMAT_R32G32_UINT</code>, from <code>{1, 2, 3, 4}</code>, the buffer will be filled with <code>0x00000001, 0x00000002, 0x00000001, 0x00000002, ...</code> - only the first 2 components are used.</li>
<li>If the component has smaller range than 32 bits, like in <code>DXGI_FORMAT_R16G16B16A16_UINT</code>:
<ul>
<li>On Nvidia and Intel, values exceeding the range are saturated to the maximum, so value <code>0x20003</code> gets written as <code>0xFFFF</code>.</li>
<li>On AMD, other the other hand, the value is truncated to use only the lowest significant bits, so it becomes <code>0x0003</code>.</li>
</ul>
</li>
<li>For <code>UNORM</code> formats:
<ul>
<li>On Nvidia, same values are written as for the <code>UINT</code> formats. For example, values <code>{0, 2, 255, 0xFFFFFFFFu}</code> written to a buffer with <code>DXGI_FORMAT_R8G8B8A8_UNORM</code> become <code>{0x00, 0x02, 0xFF, 0xFF}</code>, despite they logically represent <code>{0, 2.0/255.0, 1.0, 1.0}</code>. The normalization logic isn't working here. Note this is different from the Float version of the function described in the next section. However, it makes sense, because otherwise the only useful values in this function would be 0 and 1.</li>
<li>On AMD, it works similarly, just the values are bit-trimmed instead of clamped, so that <code>0x20003</code> becomes <code>0x03</code>.</li>
<li>On Intel, zeros are always written to this format!</li>
</ul>
</li>
<li>If the format is a small signed integer, like <code>DXGI_FORMAT_R16G16B16A16_SINT</code>, and we use only the lowest 16 bits of the value, like <code>0xFFF0u</code> to write value -16:
<ul>
<li>On Nvidia and AMD, it becomes -16, as expected.</li>
<li>On Intel, however, it somehow becomes the maximum <code>0x7FFF</code>.</li>
</ul>
</li>
<li>If we still use the format <code>DXGI_FORMAT_R16G16B16A16_SINT</code>, but this time specify <code>0xFFFFFFF0</code> (which is the 32-bit representation of -16):
<ul>
<li>On Nvidia: it becomes -1.</li>
<li>On AMD and Intel, it becomes -16, as the value is truncated to the lowest 16 bits, not clamped.</li>
</ul>
</li>
<li>If we use this function on a buffer with floating-point element format, like <code>DXGI_FORMAT_R32G32B32A32_FLOAT</code>, the values are bit-casted to float, e.g. value <code>0x3F800000u</code> becomes 1.0.</li>
</ul>
<p>To summarize, the <code>ClearUnorderedAccessViewUint</code> function may be useful when we want to set a specific bit pattern to the elements of a buffer in <code>UINT</code> format, but for other formats or out-of-range values the behavior is unreliable and we cannot be sure it won't change in the future.</p>
<h1>Conversions from float</h1>
<p>Here is a similar summary of the behavior of function <code>ClearUnorderedAccessViewFloat</code>, which takes 4 floats as the value, for different formats of buffer elements:</p>
<ul>
<li>If the format is <code>DXGI_FORMAT_R32G32B32A32_FLOAT</code>, the values are written as-is, because the format matches exactly the values accepted by the function.</li>
<li>Just like before, if we specify <code>{1.0f, 2.0f, 3.0f, 4.0f}</code>, but the format has only 2 components, like <code>DXGI_FORMAT_R32G32_FLOAT</code>, only <code>{1.0f, 2.0f}</code> is written repeatedly.</li>
<li>If the format uses half-floats, values are converted appropriately. For example, <code>{1.0f, -1.0f, 0.5f, 2.0f}</code> in <code>DXGI_FORMAT_R16G16B16A16_FLOAT</code> become <code>0x3C00, 0xBC00, 0x3800, 0x4000</code>.</li>
<li>If the format is integer:
<ul>
<li>On Nvidia and AMD, values are converted to integers, truncated fractional part. <code>{0.0f, 123.0f, -1.0f, -10.5f}</code> written to a buffer with <code>DXGI_FORMAT_R32G32B32A32_SINT</code> becomes <code>{0, 123, -1, -10}</code>.</li>
<li>On Intel, these values are written as <code>{0, 0x42f60000, 0xbf800000, 0xc1200000}</code>, which are floating-point values specified on input, just directly bit-casted.</li>
</ul>
</li>
<li>If the format is unsigned integer:
<ul>
<li>On Nvidia, negative values are written using the same bit pattern as if it was signed integer. For example, <code>-100.0</code> becomes <code>0xFFFFFF9C</code>.</li>
<li>On AMD, a negative floating-point value is clamped, becoming 0.</li>
<li>On Intel, the value is again bit-casted from float to int, becoming <code>0xC2C80000</code>.</li>
</ul>
</li>
<li>If the format is smaller integer:
<ul>
<li>On Nvidia and AMD, values are clamped to its range. <code>{0.0f, 1.0f, 123.0f, 1000.f}</code> written to a buffer with <code>DXGI_FORMAT_R8G8B8A8_UINT</code> becomes <code>{0, 1, 123, 255}</code>.</li>
<li>On Intel, somehow they become <code>{0x00, 0xFF, 0xFF, 0xFF}</code>.</li>
</ul>
</li>
<li>If the format is <code>UNORM</code> or <code>SNORM</code>, values are converted and clamped, respecting its logical representation with normalization. For example, with <code>DXGI_FORMAT_R8G8B8A8_UNORM</code>, values <code>0.0...1.0</code> are mapped to <code>0...255</code> and values above <code>1.0</code> become <code>255</code>. Note this is different from the Uint version of the function described above. The Float version is better to work with such formats.</li>
</ul>
<p>To summarize, the <code>ClearUnorderedAccessViewFloat</code> function is useful when we want to set a specific numeric value, correctly converted to the specific format, especially when it's <code>FLOAT, UNORM, SNORM</code>. For consistent behavior across GPUs, we should avoid using it with <code>UINT, SINT</code> formats.</p>
<h1>Limited range</h1>
<p>If we want to limit the range of elements to clear, we have 2 equivalent ways of doing so:</p>
<p>1. Set the limit when filling the descriptor:</p>
<pre>D3D12_UNORDERED_ACCESS_VIEW_DESC uavDesc = {};

uavDesc.Buffer.NumElements = elementCount; // !!!
device->CreateUnorderedAccessView(...</pre>
<p>2. Set the limit as a "rectangle" to clear:</p>
<pre>D3D12_RECT rect = {

0, // top
firstElementIndex + elementCount, // right
1}; // bottom

shaderVisibleGpuDescHandle, // ViewGPUHandleInCurrentHeap
shaderInvisibleCpuDescHandle, // ViewCPUHandle
buf // pResource
values, // Values
1, // NumRects !!!
&rect); // pRects !!!</pre>

While working with geometry in 2D, I was recently looking for an algorithm to calculate the bounding box of a specific shape that I initially called a "cone". Actually, as I'm talking about 2D, I should rather say I needed the bounding rectangle of a circular sector - a part of a circle with a limited angle around an axis pointing in a specific direction.</p>
<p>When developing a 2D game, this shape can represent, for example, the area of effect of an attack, such as punching nearby enemies, firing a shotgun, spraying some substance ahead, or casting a magical spell. Calculating its bounding rectangle can be useful for querying a space-partitioning data structure (like a grid, a quadtree, etc.) for potentially affected objects.</p>
<p style="text-align: center;">

</p>
<p>I prototyped my solution in ShaderToy, which you can see here: <a href="https://www.shadertoy.com/view/w3jcRw"><strong>shadertoy.com/view/w3jcRw</strong></a>.</p>
<p>A circular sector is described by:</p>
<ul>
<li><code>vec2 apex</code> - the starting point and the center of the circle that this shape is part of</li>
<li><code>vec2 direction</code> - a vector pointing in the direction of the axis (must be normalized)</li>
<li><code>float halfAngle</code> - the angle between the axis and the edges, or half of the angle between the opposing edges (in radians, in range 0...π)
<ul>
<li>For 0, the shape becomes just a line segment.</li>
<li>For π, it becomes a full circle.</li>
</ul>
</li>
<li><code>float radius</code> - the radius of the circle that this shape is part of</li>
</ul>
<p>The output bounding rectangle is described by just <code>vec2 MinPos, MaxPox</code> - two points defining the minimum and maximum coordinates it contains.</p>
<p><img style="display: block; margin-left: auto; margin-right: auto;" src="files/bounding_rectangle_of_a_circular_sector/bounding_rectangle_of_a_circular_sector_diagram.png" alt="" width="554" height="554">To calculate the bounding rectangle of our cone, we need to consider all possible points that extend the furthest along the X and Y axes, and take their min/max. The first such point is the apex. The next two are what I call "edge points."</p>
<p style="text-align: center;"><img src="files/bounding_rectangle_of_a_circular_sector/bounding_rectangle_of_a_circular_sector_case1.png" alt="" width="554" height="554"></p>
<p>However, there are cases where this is not enough. We also need to check four "extra points" located at a distance of radius from the apex along -X, +X, -Y, +Y, as long as each of these points belongs to the cone.</p>
<p style="text-align: center;"><img src="files/bounding_rectangle_of_a_circular_sector/bounding_rectangle_of_a_circular_sector_case2.png" alt="" width="554" height="554"></p>
<p>My final algorithm in GLSL is:</p>
<pre>void CalcConeBoundingRect(vec2 apex, vec2 direction, float halfAngle, float radius,
out vec2 boundingRectMinPos, out vec2 boundingRectMaxPos)
{
float sinHalfAngle = sin(halfAngle);
float cosHalfAngle = cos(halfAngle);
vec2 edgeVec1 = vec2(
direction.x * cosHalfAngle - direction.y * sinHalfAngle,
direction.y * cosHalfAngle + direction.x * sinHalfAngle);
vec2 edgeVec2 = vec2(
direction.x * cosHalfAngle + direction.y * sinHalfAngle,
direction.y * cosHalfAngle - direction.x * sinHalfAngle);
vec2 edgePoint1 = apex + edgeVec1 * radius;
vec2 edgePoint2 = apex + edgeVec2 * radius;
boundingRectMinPos = min(min(edgePoint1, edgePoint2), apex);
boundingRectMaxPos = max(max(edgePoint1, edgePoint2), apex);
vec2 unitVec[4] = vec2[](
vec2(-1.0, 0.0), vec2(1.0, 0.0),
vec2(0.0, -1.0), vec2(0.0, 1.0));
for(int i = 0; i < 4; ++i)
{
if(dot(unitVec[i], direction) >= cosHalfAngle)
{
vec2 extraPoint = apex + unitVec[i] * radius;
boundingRectMinPos = min(boundingRectMinPos, extraPoint);
boundingRectMaxPos = max(boundingRectMaxPos, extraPoint);
}
}
}</pre>
<p>Note that we don't use raw angles here, apart from the initial parameter. We don't call the <code>atan2</code> function, nor do we compare whether one angle is smaller than another. We simply operate on vectors - a common theme in well-designed geometric algorithms.</p>
<p>The algorithm can be optimized further if we store the sine and cosine of the angle in advance. Alternatively, if we have only one of them, we can compute the other using the formula below. This way, we never need to use the raw angle value at all.</p>
<pre>float sinHalfAngle = sqrt(1.0 - cosHalfAngle * cosHalfAngle);</pre>
