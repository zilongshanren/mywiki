# 消息队列作为线程所有权原语

「只有两种程序员：对多线程代码有健康恐惧的程序员，和**应该**被代码恐惧的程序员。」[[ben-supnik|Supnik]] 在 X-Plane 并发实践里把这句话当作出发点：**线程不是免费午餐，引入线程必须有明确收益，因为它的开发成本极高**。

## 为什么多线程这么贵

单线程程序的正确性可以通过「跑若干次」来逐步验证；多线程不能。原因在于：

- **执行顺序每次都不一样**，且没有任何保证说「跑 N 次就穷举了所有可能的 interleaving」。
- **bug 可能只在特定组合下出现**——一个多核用户 + 一个后台任务吃 CPU 就可能触发从未见过的顺序。
- 想真正验证，必须**用逻辑证明**锁 / 同步约束把执行 interleaving 收敛到有限且每个都正确的集合。这个证明不简单。

换句话说，多线程的验证从「动态 testing」升级到「静态 reasoning」。人类不擅长后者，工具支持也远远不够。

## X-Plane 的应对：设计模式而非裸锁

X-Plane 需要吃满多核，所以不能不用线程；Supnik 的策略是**用执行限界已知的设计模式**，用模式本身而不是 review 来保证正确性。最常用的一个是**消息队列**：

**核心约束——数据访问权随消息沿队列流动**：

- 消息被 push 进队列时，发送方交出对数据的所有权；
- 消费方从队列 pop 出消息才获得所有权；
- 任何时刻只有一个线程持有数据的指针。

在 C++ 里这种约束天然落地：如果你没拿到消息，你就没指针，什么也 deref 不了——**类型系统和 RAII 帮你封死误操作的可能**。这和 Rust 的 `Send`/单一所有权哲学完全同构，只是 C++ 里靠程序员纪律+局部 API 约束，而非编译器强制。

## 为什么这比粗锁好

粗锁把执行 interleaving 限得不够狠：持锁线程跑什么代码锁不管，真出 bug 往往是「锁内调用了其他路径，那路径又间接触到第二把锁」这种坑。消息队列把 interleaving 限在**消息粒度**：要么你收到消息，要么没收到，没有「半握」的状态。这大大缩小了需要推理的状态空间。

## 对其他并发模式的启示

这个观察可以推广：**好的并发模式都在把「可能的执行组合」收紧到人类能 reason about 的规模**。类似的模式有：

- [[main-thread-task-injection|主线程任务注入]]——子线程把工作排队到主线程，避免直接操作主线程数据；
- [[vfx-multithreading-patterns|VFX 工具的 task 化]]——把线程 spawn 换成 task 提交给调度器；
- Erlang / Go channel、actor 模型——同一套思路在语言层面的原生支持。

Supnik 的这篇短文价值不在讲模式本身（业界共识），而在给出**工程判断**：**不要自问「这段能不能加线程」，要问「加了线程我省到的 ms 是否值得多付的工程成本」**。对于绝大多数代码，这个问题的答案是否定的。
