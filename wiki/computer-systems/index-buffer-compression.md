# 索引缓冲压缩

索引缓冲（index buffer）是一系列三角形顶点索引的线性数组。在 GPU 硬件上，一个 mesh 的索引可以占用相当可观的带宽，尤其是 SPU 时代需要把 mesh 数据分块传入向量处理单元。Jon Olick 在 2007-2008 年的演讲中提出了一套专门面向索引缓冲特性的无损压缩方案。

## 压缩流程

整个算法分四个递进的步骤，每步都利用索引数据的结构特征消除冗余。

**第一步：前期清理。** 先用 cache-coherency optimizer（如 Tom Forsyth 算法）对索引做排序，再删除退化三角形（两个或更多索引相同）和重复三角形，最后把顶点缓冲按照索引出现的顺序重排，使顶点下标尽量连续递增。

**第二步：重复模式编码（2-bit repeat table）。** 相邻三角形通常共享两个顶点（triangle strip 或 fan 的局部结构）。对每个三角形，若它与前一个三角形恰好共享两个索引，就可以只记录那个新索引，再用 2 bit 描述两个重复索引的排列方式（共四种 pattern，第四种 `11` 是逃逸模式——不满足 2 重复则写完整 3 索引）。这一步把"新索引流"大幅瘦身。

**第三步：顺序性编码（1-bit sequential table）。** 经过顶点重排后，剩余的新索引往往是严格递增的自然数序列（0,1,2,3,...）。对每个新索引，只用 1 bit 标记"它是否等于前一个分配出去的顺序索引"，若是则完全省略该索引的值。

**第四步：Delta 编码 + 正值偏移。** 对于未被顺序性模式覆盖的"混沌索引"，对相邻索引做差分（delta encode），差值的绝对值通常很小。由于差值可正可负，还需要找最小值并整体平移到 $\geq 0$，最终只需记录刚好够用的位数。

## 最终编码

压缩后需要存储：最小索引偏移量（`min_idx`）、2-bit repeat table、1-bit sequential table、以及混沌索引列表。后三者都是密集比特流，可以：

- **直接打包**：找到混沌索引列表能表示的最小位宽，定宽打包。  
- **扔给通用压缩器（Kraken/zstd/zip）**：让熵编码处理剩余冗余，压缩比通常更优，但解压有 CPU 开销。Kraken 路线下，建议将混沌索引的高字节和低字节分开存储（高字节几乎全零，对 LZ 字典非常友好）。

## 权衡与局限

该方案的有效性高度依赖**索引缓冲优化器的质量**——若三角形排列本身毫无局部性，repeat 和 sequential 两步几乎没有增益。选用更好的 cache optimizer 是提升压缩比的先决条件。在现代 GPU 上，带宽已不再是 SPU 时代那样的绝对瓶颈，但对移动平台（带宽受限）以及网络传输场景（模型下载）仍有参考价值。

与 [[meshoptimizer-vertex-codec]] 的思路互补：后者专注于**顶点属性**的 delta 预测压缩，而本方案专注于**拓扑索引**的结构性冗余消除。[[triangle-strips-vs-indexed-triangles]] 讨论了为什么现代 GPU 应优先使用 indexed triangles 而非 strips，索引缓冲压缩正是在此基础上的进一步优化。
