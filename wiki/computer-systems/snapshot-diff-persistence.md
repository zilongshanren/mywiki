# 快照差分持久化

许多老派 MMO 服务器（典型如《梦幻西游》）根本不用数据库：主进程把所有玩家状态放在内存数据结构里，登录时从本地文件文本反序列化，登出时序列化回磁盘；为了防止崩溃丢数据，中途由一个独立 IO 进程从共享内存里拉快照定期整块写盘。这个设计在 10 年以上的稳定运行后依然有效，只是量级起来了——8K 以上同服之后，磁盘 IO 变成瓶颈，甚至影响到主循环。

[[cloudwu]] 指出瓶颈其实非常好啃：只需在内存里加一层 cache，让运行时的读都从 cache 走，然后把"每次写全量快照"改为"写与上一次快照的差分"。相比从头迁移到数据库，这种改造面极小，几百行 C 就够，且能在不动核心系统的前提下把写盘量减少 90% 左右——玩家平均半小时内的行为产生的 diff 只占总数据量的 10% 量级。

难点不在思路而在 diff 粒度。传统文本 diff 按行切片，但历史积淀下来的玩家存档没有严格的行格式，单行可能长达数千字节；基于文本行的 diff 落到这种数据上效果很差。云风的做法是把"分隔符"从回车扩展为可配置的多种字符，先把 48 K 的玩家文本按结构性字符切成约 2000 个数据元，再套传统 diff 算法。每批数据约 1 万玩家、百兆量级，独立工具的 IPC 开销会压过 diff 本身，所以他选择做一个常驻的小服务，一秒能处理 20 组玩家存档，正好把平时闲置的几个 CPU 核吃掉。这个做法几乎是"运行时快照 + 增量持久化"的极简落地：既保留了原系统的内存友好性与崩溃恢复的简单语义，又把[[latency-vs-throughput|磁盘 IO 带宽]]的成本压了一个数量级。
