# C/C++ 的未定义行为（Undefined Behavior）

「未定义行为」（undefined behavior, UB）是 C/C++ 里最容易引发误解也最容易被工程师低估的一类语言特性。它的字面含义是：标准**拒绝**规定某段程序在执行时应当发生什么，编译器因此可以生成任意代码——包括正确运行、崩溃、默默返回错误结果，甚至像 [nasal demons](http://www.catb.org/jargon/html/N/nasal-demons.html) 那个玩笑里说的「从你鼻孔里飞出恶魔」。[[raph-linus]] 在 2018 年的一篇长文里把这个现象的历史、本质与后果梳理得很清楚。

## C 的三种使用方式

理解 UB 的前提是意识到 C 社区从未是一个同质群体。Raph 把 C 程序员分成三个阵营：

1. **不可移植 C（Unportable C）**——「比汇编稍高一级」的用法。目标是为特定硬件生成 binary，指针就是某种已知宽度的整数，整数算术按硬件实际行为绕回。代表作品是那本被公开唾弃的 *Mastering C Pointers*。
2. **半可移植 C（Semi-portable C）**——通过 `#ifdef`（常借助 autoconf）处理目标机器差异：指针可能是 16/32/64 位、大端或小端。类型双关（type punning）被视作合法工具，只要尺寸对齐。这才是「C 是可移植的汇编」这个口号真正指代的对象。
3. **标准 C（Standard C）**——委员会为了让同一份代码能在所有奇特硬件（甚至不是二补码、字长非 2 的幂的机器）上运行，发明了一种「虚拟计算模型」。UB 正是这个抽象模型和真实硬件之间裂缝的表现。

历史现实是：标准化那一刻几乎**所有已有 C 程序都变成了「不严格遵循标准」**，而早期编译器出于兼容考虑并没有真的把 UB 当作「随便做任何事」，于是程序在编译后照常工作。随着编译器作者越来越大胆地把 UB 作为激进优化的前提，那些「事实上能跑」的程序开始一个接一个地爆炸，Linus Torvalds 对 union-based aliasing 补丁的那篇著名 rant 正是这种冲突的缩影。

## 指针并不只是数字

UB 除了抹平平台差异，第二个重要动机是**让别名分析（aliasing analysis）可行**。C 标准假设程序严格尊重类型：两个不同类型的指针不可能指向重叠的内存，即所谓严格别名规则（strict aliasing）。违反这一条就是 UB。

这意味着标准 C 的「真正计算模型」不是「指针就是带宽的整数」，而是一个复杂的虚拟机：**指针是带类型与有效区间标注的数字**，任何不守规矩的使用都会立即跌入 UB。Ralf Jung 的 [Pointers Are Complicated](https://www.ralfj.de/blog/2018/07/24/pointers-and-bytes.html) 系列、以及论证 LLVM/GCC 在某些技术上合法的程序上会编译错误的 LLVMTwin 论文都是这套规则的深入剖析。这种虚拟机可以很方便地在真实硬件上「剥掉外衣直接跑」，但这正是 UB 的陷阱：人很容易忘记编译器其实是基于更复杂的模型在推理。

## UB 的目录非常长

Raph 援引 John Regehr 的 [UB 指南](https://blog.regehr.org/archives/213) 时强调：UB 的条目远远超过「解引用空指针」之类的经典案例。有符号整数溢出、读未初始化内存、**仅仅计算**出越界指针（不解引用也算）、类型双关的指针使用、shift 超过位宽……每一类都是潜在的 UB 源。这张清单把「不严格遵循标准」的程序比例推到接近 100%。

举一个容易被低估的例子：`x << 64`（当 `x` 是 64 位）并没有被定义为「结果是 0」或「结果按 64 取模的位数移动」，而是**纯粹的 UB**——标准允许它崩溃、打出错误结果，甚至连上服务器把你账户里的钱转走。Raph 提到这一类「本可以定义为 implementation-defined」的选择是标准委员会的一个历史污点。

## 一个缓慢发生的激进变革

这背后真正可怕的地方不是 UB 本身，而是它**缓慢展开**。同一段代码在 GCC 3 下工作良好，在 GCC 7 下因为新的优化 pass 开始返回错误结果——没有警告、没有提示。UB 是一种「埋在代码库里几年、某次升级编译器时突然引爆」的地雷。这也是为什么 [[avoid-unsigned-types|整数类型的选择]] 和编译器的防御性使用在 C/C++ 工程里始终是个活话题。

「友好 C 方言」的提案曾试图把最离谱的几种 UB 变成 implementation-defined，但因为无法在编译器作者与语言委员会之间达成共识而流产。编译器作者**极度珍视** UB 提供的优化空间，不愿让出一点。Raph 判断这种局面短期内不会变。

## 线程、内存模型与表达力的再扩张

C89 时代标准 C 语言完全没有线程概念，pthreads 是作为库、按半可移植语言的方式描述的。因此严格遵循标准的 C 比半可移植 C **表达能力更弱**——连一个线程程序都无法描述。C11 和 C++11 的内存模型（受 Java 内存模型启发）补回了这部分能力，但把内存模型真正读懂仍然很难。即便如此，像 Boehm-Demers-Weiser 垃圾回收器、尾递归、协程这些高级语言构造仍然依赖半可移植 C——标准 C 仍然无法涵盖所有现实的系统编程需求。

## 怎么办？

1. **工具**——LLVM 的 UBSan 是目前最实用的防线，和 fuzzer 一起用能把大量潜在 UB 挤出来。但它只能发现「某次真实执行踩到的 UB」；针对恶意输入才会触发的那些它无力。配合 [Undefined Behavior in 2017](https://blog.regehr.org/archives/1520) 提到的多层防御仍是必要的。
2. **编码规范**——Thomas Lord 在 Raph 文章里给了一条朴素但正确的建议：把 C 当作「目标语言」来看，早期就定下严格、安全的子集并强制团队遵守；也可以用代码生成工具（lex/yacc 乃至高级语言翻译器）生成 C 片段，而不是让人直接写。
3. **换语言**——Java 基本没有 UB（除了 JNI），Rust 则把「安全子集」与「unsafe 子集」明确分开，并有 [Ralf Jung 发起的项目](https://www.ralfj.de/blog/2017/07/14/undefined-behavior.html)去精确记录 unsafe Rust 的 UB 规则。「现代 C++」用智能指针与 RAII 缓解了大半内存问题，但对整数溢出、[iterator 失效](https://stackoverflow.com/questions/6438086/iterator-invalidation-rules) 这些微妙形式依然无能为力——Raph 的判断是：它比裸 C 好很多，但**绝对达不到真正安全语言的保证水平**。

## 为什么所有语言都躲不开它

即便换了 Rust 或 Java，系统底层几乎仍然建立在 C 运行时之上，FFI 是必经之路。数据竞争曾被分成「良性」与「危险」两类，但 Hans Boehm 的研究表明「良性数据竞争」这个类别根本不存在——任何数据竞争都可能触发 UB。因此「C 的 UB 问题」某种意义上是**整个软件栈的 UB 问题**，只是被挪到了一个更小、可以被严格审计的界面上。
