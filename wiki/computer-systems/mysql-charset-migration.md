# MySQL 跨十年升级时的 GBK → UTF-8 迁移

[[cloudwu]] 在 2025 年 9 月把他运行了十多年的个人博客服务器做了操作系统升级。结果 MySQL 从 4 一路强升到 8，旧数据库里的中文全部乱码。他把这次迁移过程记录了下来，是一个很典型的"老数据库编码没标注、升级后被默认当 latin1 对待"故事。

## 起因：老 MySQL 不存储字段编码

博客建于 2005 年，当时为了节省存储与带宽选了 GBK（那年"手机流量 3 分钱 1K"），而不是 UTF-8。老版本的 MySQL 里，字符字段并不强制记录字符集——**你写进去什么字节它就按什么字节存**。MySQL 升级后，这些没有标注编码的字段被统一标成了 `latin1 / latin1_swedish_ci`，但实际字节仍然是 GBK。读出来自然就是乱码。

官方文档给了一个"转码两步走"方案：

1. 先把列转成 binary 类型（此时字符集信息被剥掉，但字节不变）。
2. 再把列转成目标字符集类型（此时按你指定的源字符集重新解释字节）。

这个思路对**列上有索引**的情况不工作——作者最初在生产库直接试失败，原因是得先 drop 索引、转码、再 rebuild。于是他把库 dump 下来在本地 MySQL 8 上实验。

## 迁移管线：dump → 文本替换 → 重导入

关键命令：

```
mysqldump -u root -p --default-character-set=binary
```

**`--default-character-set=binary` 是这条管线的关键**。如果不加，dump 会把数据当 latin1 再做一次字符集转换，输出的字节已经被改坏了，再想恢复就难了。

拿到 binary 的 dump 文件后（大约 500M），直觉方案是 `iconv` 一把梭。但实际跑一遍发现两个坑：

1. **混杂编码**：dump 文件里居然既有 GBK 串又有 UTF-8 串。作者推测是当年试过一次转 UTF-8、发现不对劲又换回来，中间残留了一批已经是 UTF-8 的记录，最终找到约 680 条。`iconv` 遇到非法 GBK 序列会报错或吞字节，对这种混杂数据束手无策。
2. **SQL 转义被破坏**：MySQL 的 dump 对某些字符（尤其是引号）做了转义。编码转换中一旦吃掉或错位，就可能破坏引号配对，导回时语法错误。

作者的解法是**写一个 Lua 小程序最低限度解析 dump 的词法**：只挑出 binary 字符串字面量，对转义序列做反转义，用自己的启发式判断每个字符串是 GBK 还是 UTF-8——UTF-8 原样留下，GBK 交给 `iconv`——转换完再加回转义符，保证生成的 SQL 依旧合法。

文本替换到此为止，字段声明仍然写着 latin1，只需最后用 `sed` 做一次声明替换：

```
sed -i 's/CHARSET=latin1/CHARSET=utf8mb4/g' backup_utf8.sql
sed -i 's/COLLATE latin1_swedish_ci/COLLATE utf8mb4_unicode_ci/g' backup_utf8.sql
```

此时 dump 文件本身是合法的 UTF-8 SQL，导回新库即可。

Windows 本地实验时还踩了一个小坑：`source` 命令的路径必须用正斜杠，反斜杠会被 MySQL 当转义符处理。

## 经验

- **dump 要 binary**：任何跨编码迁移，先确保从老数据库取字节的过程不做任何转换。
- **iconv 不适合处理混杂编码**：要么先分桶再分别转，要么写一个最小化的词法解析器挑字符串做局部转换。
- **索引会挡路**：列类型转换前要 drop 索引。
- **假设会错得很离谱**：这种"十年跨度升级"的数据里常有你早就忘掉的历史残渣（像那 680 条 UTF-8 串）。
- **解决方案别急着通用化**：作者没有去写一个通用迁移工具，只是"够用就行"的 Lua 脚本。这跟他其它笔记（[[xlsx-text-versioning]]、[[lua-class-pattern]]）一贯的克制风格一致。

迁移完成后博客的 RSS 也终于输出 UTF-8，解决了多年来"我的 RSS 阅读器不支持 gbk"这类反馈。
