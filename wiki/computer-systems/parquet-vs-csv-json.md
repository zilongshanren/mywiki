# 表格数据的存储格式：为什么 CSV 与 JSON 都不够好

Anteru（[[matthaeus-chajdas]]）在这篇博客里直面一个几乎所有工程团队都会遇到的问题：实验、测量、分析产生的**表格数据**（tabular data）应该怎么存。他从真实使用场景出发，列出三项需求：结构化的表格、可演进的版本元数据、以及"无摩擦查看"。这三条合在一起，筛掉了几乎所有行业里最常见的做法。

## 需求的次序

最关键的观察是次序：**易查看** > **版本化** > **性能 / 体积**。他强调性能与磁盘占用是"在被问题淹没之前都排在后面的次要需求"，真正推动人们快速决策的是"我现在打开一个文件能立刻看到里面是什么吗"。这也解释了为什么 CSV 和 JSON 能在工程实践中长期占据主导——它们恰好最大化了"打开文件就能看"的短期幻觉，而把长期代价推到了处理与归档环节。

版本化的份量经常被低估。测量代码会有 bug，设备会升级，采集管线里的任何一环都可能在某个时间点后往某列写脏数据。光靠时间戳不够——版本号必须**内嵌在数据里**，只有这样才能在若干年后告诉你"这张表能不能信"。

## 三个常见选项的失败模式

**电子表格文件**（xlsx / ods）并不是最糟的——它们能被任何人直接打开，也能塞下额外的版本 sheet。真正的问题是生成侧：类型系统脆弱（日期会被自动解析成"1 月 2 日"式的悲剧），批量处理昂贵且不友好。只有在"方便是首要指标"的场景下才推荐，而且最好通过 Pandas 的 `to_excel` 生成。

**CSV** 的失败几乎发生在每一层。没有字符串转义标准，于是每个生成器都发明了自己的方言（双引号、三引号、"最后一列是自由文本"……）。没有类型标准——日期全是字符串，数字用 `printf` 打出来既不是最短表示也不是最精确表示，布尔值可以是 `On`/`Off`、`Yes`/`No`、`True`/`False`、`0`/`1` 中任意一种。欧洲的小数分隔符是逗号，直接让整张表在某些电子表格里坍缩成一列。最后一根稻草是**没法原生存版本**——把版本塞进第 0 行、虚拟列名、甚至文件名里，都是需要读者具备隐性知识才能处理的 hack。归档场景下，随手捡起的一个 CSV 文件，你永远不能确定它的世系。

**JSON** 在版本 / 元数据维度上比 CSV 好得多（只要加字段即可），但它在数据存储方向上有致命缺陷：**数字都是 double**。规范上整数精度只到 53 位，64 位整数无法可靠地往返；没有标准的日期表示；更糟糕的是，典型的"每一行存成对象、列名反复出现"的写法会让数据膨胀 10–100 倍——压缩之后磁盘占用能抢救回来，但解析时的重复开销完全救不回来。至于各种二进制 JSON（BSON、UBJSON、CBOR、MessagePack），它们的存在本身就说明问题没被解决：没有一个事实标准，库与语言支持割裂。

## Parquet：贴合"表格"概念的那一层

作者的结论是 [Apache Parquet](https://parquet.apache.org)。之所以优于 Protocol Buffers（后者目标是 RPC，有协议定义开销）和 HDF5（"太灵活反而难用"，社区外没有真正流行），是因为 Parquet 在**定位**上恰好是 CSV / 电子表格的 1:1 替代品，没有多余能力：

- **列式**存储，按列过滤时直接受益；
- 每列**强类型**，数字天然 round-trip，无需类型推断博弈；
- 支持现代压缩算法（[Zstd](https://facebook.github.io/zstd/)）；
- **元数据**机制能干净地承载版本、来源、采集工具等信息；
- Pandas 原生读写、VS Code Data Wrangler 等开源 viewer、[DuckDB](https://duckdb.org/)、[Iceberg](https://iceberg.apache.org) 都直接消费它；
- Parquet → CSV / 电子表格的转换是单向廉价操作，这让"便利派"也能被安抚——把 Parquet 当作**主存储**（primary storage），其它格式视为**按需派生**（derivative）。

作者把 Parquet 本身的复杂度（底层依赖 Apache Thrift）视为唯一的瑕疵，但在生态位上，它"嵌在了正确的位置"。对归档也足够友好：格式文档公开、生态全开源，真出了问题总能迁移到届时的最佳格式。他给出的底线是："只要不是 JSON 或 CSV，就有我的祝福。"

## 对工程实践的启示

- **默认别用 JSON 存测量数据**。它在文档数据库里是方便，但一旦跨进程、上磁盘，就把所有问题又带回来了。
- **CSV 不是"简单"，是"把复杂度推给每一个下游"**。几十 MiB 以上的 CSV 根本没法在编辑器里直接查看，所谓"文本友好"在真实数据规模下会迅速失效。
- **版本号要在文件内部**。任何"靠文件名 / 目录结构记录版本"的方案，都会在你最需要它的时刻（归档查证）失效。
- **选型时先考虑人机工效再考虑性能**。文中反复出现的主旨是"获取数据的速度决定了实际选型"，工具链要围绕这个事实而不是理想模型去搭。
