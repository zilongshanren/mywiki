# 重构 ltask 的任务调度器（云风 / blog.codingnow.com）

[[cloudwu|云风]] 发表于 2024 年 3 月 22 日的工程笔记，记录他对 [[ant-engine|Ant Engine]] 并发基础设施 [[ltask-scheduler|ltask]] 调度器的一次较大重构——主要动机是把"独占线程服务"这个曾经为处理特殊场景而引入的大特性整个删掉，代价是给共享工作线程加上"绑定到特定线程"的能力。

## 摘要

ltask 和 skynet 要解决的问题表面相同（m 个任务跑在 n 个核心上），但应用场景完全相反：ltask 面向游戏客户端，由一两个重负荷任务加若干低负荷任务构成，优化目标是**低延迟**；skynet 面向服务器，成百上千同质任务，优化目标是**高吞吐**。服务器端只需要最简单的调度器即可榨干 CPU；而客户端想降低帧时间，就必须让主线任务在依赖满足时最快开始运行——这需要更复杂的算法和更多调度开销，用复杂度换延迟。

早期 ltask 把服务分成两类：**共享工作线程**的普通服务由调度器管，**独占系统线程**的服务交给 OS 管。独占线程用来吸收三类麻烦事——会阻塞的系统 API（`sleep`、`epoll`）、要求固定线程的 C 库（TLS、主线程限制）、永不返回的系统循环（iOS 窗口）。云风原本希望独占线程只做简单事，但两套 API 的边界越来越模糊。

重构时他挨个重新审视：

1. **阻塞系统 API**——他先尝试仿 Python GIL 的思路，划分 Lua VM 与 C 代码两态，设计 `yield` / `resume` 两个 C API 显式界定边界。但需要改写已有 C 库且使用者容易用错，最终放弃。转而接受"阻塞工作线程其实没那么不可接受"——多开几条工作线程（超过核心数）并在调度器里给长挂起线程特殊处理即可。
2. **TLS / 主线程限制的 C 库**——这才是 ltask 没做好的那块。解法是让调度器支持**把服务绑定到某条特定工作线程**，保证"服务调用始终在同一物理线程上"。
3. **iOS 主线程不返回**——特例中的特例，ltask 不处理，由使用者在库外自己写几行代码兜住。

解决完这三个问题，独占线程服务就可以整块删掉——C 代码减了 600 多行，Lua 代码也大量简化。最后一段给出一个反直觉的观察：**把"关键任务"绑定到特定线程未必是最低延迟的解**——如果没有替补，被依赖卡住时要么闲等要么切走就回不来了。这正是自写调度器能做而 OS 调度器做不到的那层——OS 只看到被阻塞的线程，不懂任务间的依赖。

## 关键要点

- 客户端低延迟 vs 服务器高吞吐是对立的调度器目标，不能"既要又要"。
- Python GIL 的隐喻：GIL 把 Python 代码与 C 代码划分为两态，C 代码其实可以真正并行——Lua VM 在苛刻条件下也能这样做，但云风最终放弃这条路。
- **阻塞工作线程可以被接受**，前提是多开几条工作线程 + 调度器特殊处理。
- **服务绑定到特定工作线程** > 独占线程服务：解决 TLS / 主线程约束足够了。
- 绑定线程不等于低延迟——需要有替补者才能在依赖卡住时不浪费主线任务的产能。
- 重构的净收益：600+ 行 C 代码删除 + 调度器语义简化。
