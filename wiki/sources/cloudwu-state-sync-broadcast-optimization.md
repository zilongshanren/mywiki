# 服务器状态同步广播的设计优化（云风的 BLOG）

[[cloudwu]] 发表于 2025 年 2 月的一篇开发日记。自研游戏项目第一里程碑冻结特性期间，他盯着压测数据发现 40v40 战场上服务器压不住，决定先从同步协议这一层挖。

## 摘要

项目用大量 Erlang 进程（而非 OS 进程）协作，框架内把同机器的进程间通讯优化成同进程的函数参数传递，但数据 marshal 和内存复制依然构成可观负担。压测显示多人对战时 **90% 的内部数据包都是 Agent 之间的状态同步包**。当前做法基于一个假设——服务器内部广播远比逐个发送廉价，所以把同一张地图上任一 Agent 的状态变化直接广播给地图内所有 Agent，由每个 Agent 在收到后按自己的可见性过滤再转发给各自的客户端，从而省掉动态维护分组的代价。这个假设在 50+ 人聚集时遭到挑战：需要一个更高效的广播方案来削掉无谓的包复制。文末点出他要设计一个相应的数据结构，但本文只起了个头，设计细节留给后文。

## 关键要点

- 多人战场里，90% 内部流量是状态同步包——是第一个该优化的对象
- 早期发现的性能问题常常是**设计错误**的外显，推迟到后期做低层优化反而更费力
- 同机器内 Erlang 进程通讯在该框架下被退化为函数参数传递，但 marshal / 复制不是零成本
- "广播比逐发廉价"在大地图高密度时会失效——接收端过滤的设计要重审
- 文章是一个设计过程的起点：诊断 + 待实现的数据结构占位
