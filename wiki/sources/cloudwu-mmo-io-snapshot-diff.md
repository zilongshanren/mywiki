# 梦幻西游服务器 IO 的一点优化（云风 / blog.codingnow.com）

[[cloudwu]] 发表于 2010 年 12 月的工程笔记，剖析了《梦幻西游》运行了近十年的"内存驻留 + 文本快照"型持久化方案在 8K 同服以上时 IO 压力的瓶颈，并提出一个几百行 C 代码就能落地的差分快照优化。

## 摘要

梦幻西游服务器不用数据库，所有玩家数据都在主进程内存里；登录时读本地文本文件反序列化，登出写回；为了崩溃恢复，主进程定期把全部内存快照经共享内存交给一个独立 IO 进程写盘。这套设计十年如一日地跑着，只是量级上来后磁盘 IO 成了瓶颈。云风的建议是两步：第一步在内存里加一个 cache，把所有需要被读取的数据都兜起来避免穿透到文件；第二步把"每次写全量快照"改为"写与上一次快照的差分"，相当于把定期存盘仅视为灾难恢复的保险。问题在于 diff 粒度：存档没有严格的行格式，单行可能几千字节，传统按行 diff 效果很差。云风写了几百行 C，把 diff 的分隔符从回车扩展为可配置的多种字符，把 48K 玩家文本切成约 2000 个数据元再套传统 diff 算法；一秒能处理 20 组玩家数据，正好吃掉平时闲置的几个 CPU 核，让 diff 量降到总数据量 10% 左右，整体写盘量压缩 90%。

## 关键要点

- MMO 老派持久化：全内存数据结构 + 登录/登出文件 IO + 定期全量快照
- 瓶颈不是 CPU 或网络而是磁盘 IO（因历史修补多了一些额外写盘）
- 方案 1：内存 cache 减少读穿透
- 方案 2：把定期快照改为增量 diff，常驻 C 小服务处理
- 难点在于把文本 diff 的分隔符从"行"推广为可配置结构字符
- 现成通用工具（文本行 diff、二进制 diff）都不太合用，定制成本几乎忽略
- 总数据量百兆级，IPC 代价大于 diff 本身，必须常驻服务
