# 读《游戏引擎架构》：Console 时代的内存管理回忆（云风 / blog.codingnow.com）

[[cloudwu]] 2025 年 5 月的博文——他应 Milo Yip 之邀为中译本《[[jason-gregory|Game Engine Architecture]]》写序，在阅读过程中对 Console 平台的内存管理章节产生强烈共鸣，顺手梳理了自己十多年前在网易做 MMO 客户端时的同类实践。

## 摘要

Jason Gregory 的技术背景来自 Console 游戏开发，Console 内存紧、没有虚拟内存，对分配与回收极其苛刻；许多在 PC 上可以被忽略的工程问题，在 Console 上必须郑重处理。云风回忆 2000 年代初期开发《大话西游》时，也被迫把客户端塞进 64 MB 内存，于是写了大量自定义内存管理代码。他列举了当年用过的几类朴素结构：**栈式分配器**（堆上模拟栈，记一个标记点整体释放）、**双端分配器**（一整块内存从两端向中间分配，可与栈式配合）、**帧临时内存**（生命期绑到渲染帧，帧尾整批回收，或者做双 buffer 乒乓保留到下一帧结束）。他还提到 2004 年网易公司内部办过一场内存管理器比赛——用《梦幻西游》/《大话西游》客户端采集的真实分配序列做基准，按分配速度与碎片率打分；当年前三名如今都是网易或其他公司的主程，他自己虽然没参赛但私下写了一份拿到最高分。

## 关键要点

- **Console 的内存约束是驱动定制分配器的第一因**：无虚拟内存、总量小、软实时，使得通用 malloc 过于奢侈；云风把这一点映射到 2002 年《大话西游》64 MB 的 PC MMO 客户端上，结论是一样的。
- **栈式分配器 = [[linear-allocator]] + 标记点**：只管分配，释放时回退到某个 checkpoint，整批回收；和 Gregory 书中讲的 stack allocator 完全对应。
- **双端分配器** 是 [[linear-allocator]] 的变种：同一块内存两端各一个 offset，向中间推进；可以让两类寿命不同的分配共用一块池——比如一端放跨帧资源，另一端放当帧临时。
- **帧生命期绑定**：每帧末整批释放；或做双 buffer "乒乓"，当前帧用 A、上帧 B 保留到本帧末再释放——这种保留期是 Gregory 书中详述、现代 [[d3d12-resource-binding|D3D12 UploadBuffer]] 也在用的模式。
- **用真实 trace 做分配器基准测试**：网易 2004 年的比赛把《梦幻西游》客户端的实际分配序列喂给选手的分配器，按速度 + 碎片率打分，这种"用生产负载评选"的做法非常务实，比合成 benchmark 更接近工程真相。
- 这篇博文本身是读书笔记性质，没有给出源码，而是把 Gregory 书里的章节与云风自己的历史经验做对照——可以视作他对《游戏引擎架构》中"内存管理"一章的一份中文旁注。
