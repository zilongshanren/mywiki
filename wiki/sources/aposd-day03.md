# APoSD Day 3 —— 战术 vs 战略编程

APoSD 学习推送系列第 3 天，对应第 3 章 Working Code Isn't Enough（Strategic vs. Tactical Programming）。

## 摘要

复杂性渐进累积的必然性推导出「**零容忍**」纪律。战术编程（目标是让东西工作）是短视的，制造复利陷阱。战略编程要求**投资心态**——首要目标是一个优秀设计，恰好也能工作。建议 **10-20% 时间投资**。**战术龙卷风**是外部化成本的产出英雄。Facebook（Move Fast → Move Fast with Solid Infrastructure）的迭代、Google/VMware 的战略文化作为行业证据。

## 关键要点

- 复杂性 = **复利**。每个小妥协累积成灾难。
- **[[zero-tolerance|零容忍]]**：只有每次都付小修复成本，复杂性才保持线性。
- **[[tactical-programming]]**：短视，优先「让它工作」——制造技术债，「以后重构」永远不来。
- **[[tactical-tornado|战术龙卷风]]**：速度真实但成本外部化的高产出工程师。
- **[[strategic-programming]]**：首要目标是优秀设计。需要**投资心态**。
- **10-20% 投资原则**：小到不乱排期，大到复利。
- **每个工程师、持续、小投资**——战略编程是文化，不是项目。
- **「后 crunch 再清理」是滑坡**——crunch 永远不结束。
- Facebook/Google/VMware 的对照：**好代码库是招聘护城河**。
