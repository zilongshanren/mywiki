# Effective C++ 3rd 评注节选（云风 / blog.codingnow.com）

[[cloudwu]] 发表于 2010 年 10 月的博客，他刚为博文出版的 _Effective C++ 3rd Edition_ 中文版写完几万字评注，贴出了围绕 Item 1 "View C++ as a federation of languages" 的一段。文章既是评书、也是云风对自己十多年 C++ 实践的反思总结。

## 摘要

云风开篇承认评注比翻译难做——Scott Meyers 在原书细节上讲得非常清楚，大部分页面"真不知道可以写啥"。但 Item 1 是个例外，他对作者把"C++ 不是绝对意义上的 C++"放在全书第一篇极为认同，并展开为一段对 C++ 多范式工程现实的论述。要点是：无人能掌握 C++ 所有枝节（连作者一开始也没意识到 `template` 的能量）；C++ 各个方面的差异性大于共性；它不是一开始经过深思熟虑定义出来的，而是逐渐糅合各种风格存活到今天的；新标准从 1998 年到 2010 年还未能完全定稿正是这种复杂性的体现。在工程实践里，**定义"团队怎么使用 C++"**比"标准里允许怎么使用"更重要——Google C++ Style Guide 是个好范本：有规范且大家一起遵守，比规范的具体内容更关键。

云风分享了一段亲身经历：2005-2006 年间在团队里推广过"类 C 的 C++ 子集"做开发，工作良好；但这段经历最终让他对 OO 与模板做了大量反思，并彻底转向纯 C 开发。他对 C++ 程序员的告诫是：警惕"创新的快感"——C++ 允许你把多种范式糅在一起，每种都享受高性能支持，但其引起的冲突和复杂性"可以轻易超过个人能控制的范畴"。最后一句最有重量："逐渐的，项目会偏离原始的目标，编写 C++ 代码只是为了用 C++ 编写，而非为了解决问题。"

## 关键要点

- C++ 的差异性大于共性 —— 把它当语言联邦
- 团队必须先定义"我们用 C++ 的哪个子集"
- 规范的存在比规范内容更重要 —— Google Style Guide 范本
- "类 C 的 C++ 子集"是一种合法选择，云风以此最终走向纯 C
- 不要为了用 C++ 而用 C++ —— 警惕"创新的快感"
- C++ 标准长期难以定稿正是其多范式糅合压力的注脚
