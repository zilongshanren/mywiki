# Ant Engine 移动端优化与大型场景剔除设想（云风 / blog.codingnow.com）

[[cloudwu|云风]] 发表于 2024 年 4 月 17 日的一篇长文，内容横跨两个主题：一是 [[ant-engine|Ant Engine]] 首款验证游戏 *Red Frontier* 的性能优化历程，从不达标到比刷抖音还省电；二是他给公司另一款十万 gameobject 级魔兽世界式沙盒生存游戏构想的场景剔除方案。

## 摘要

前半追溯 *Red Frontier* 的优化历史。游戏在 iPhone 8 上一度达不到 30fps——问题是 Lua 搭起整个引擎后，Lua 层的性能热点太多。解法是借助 Lua ECS 把数据放在 C 内存里，用 3 个多月把核心渲染系统用 C 重写，性能提升一个数量级以上。达到 60fps 后目标还远未完成——因为**手机玩家有电量焦虑**，玩完一局游戏后担心手机不够扫码付费，这让"长时间沉浸式游戏"在手机上本质就受限（云风甚至怀疑手机更适合放置类游戏）。达到帧率之后的优化思路与传统引擎迥异：**目标不是最快做完每件事，而是在长时间尺度上尽量少重算**。能缓存下来的耗能计算哪怕复用比重算更慢也值得做；手机 GPU 的 [[hsr-tbdr|Tile-based rendering]] 架构就是这一思路的硬件化——它不是为了"更快"，而是为了"用更低能耗检测重复计算并在帧间复用"。

具体优化案例两个：

1. **运动插值**：场景里有数百个小货车 / 无人机每帧要更新位置，gameplay 层改成**降频计算**（非常低的帧率），在 C 里做一个运动插值器把离散点补成连续轨迹，大量减少 Lua 开销。
2. **刚体动画合批**：游戏里大量建筑带动画。初版用蒙皮骨骼在 Blender 制作，难以合批（同类建筑相位不同）。第一轮尝试把动画切成 4 类（停工 / 运转 / 两段衔接），每类 3 秒，gameplay 只在 3 秒整数倍切换动画，强制相位对齐实现合批。后来云风意识到游戏动画全是机械运动——**根本不需要蒙皮**，每个零件都是刚体，骨骼直接驱动刚体位姿即可。重写美术工具后，唯一一个美术用 3 个月把所有动画转成刚体动画，相同零件天然可以合到同一 draw call。最终 iPhone 上的能耗比刷微信抖音还低。

后半讨论另一款 Unity 做的魔兽世界式沙盒生存游戏，十万 gameobject 的 CPU 压力很大。云风强调 Ant Engine 已经解决了"内存对象数 ≠ 每帧渲染对象数"的问题，剩下的关键是**怎样从内存中大量对象里廉价地挑出这一帧要渲染的那些**。他的设想：

- **离线标注**：利用场景基本静态的特性预先算可见性关系（"无窗户的房间只关心内部"、"户外不关心室内"），用"距离 + 物件大小"规则剔除大量物件，避免复杂空间分割。
- **异步粗筛**：剔除过程放独立线程，允许晚几帧甚至几秒才到达渲染线程——正确性由"玩家在场景中移动速度远小于场景规模"保证；若需瞬移则退化为同步请求。
- **渲染线程精筛**：对粗可见集再做一次视锥体剔除。

这套设计的巧妙在于**把"可复杂但可异步"的事从热路径上搬走**。同理可以用在大量点光源剔除上——不要完全交给渲染层去做。

## 关键要点

- 达到 60fps 只是起点，**移动端优化的真正目标是能耗**，而能耗优化与延迟优化是对立思路。
- 能耗优化的关键是"少做"：能缓存就缓存，哪怕复用比重算还慢也值得。
- TBDR 架构本质上是能耗优化，不是速度优化——硬件层面已经印证了这一思路。
- **运动插值**：gameplay 降频算位置 + 渲染线程插值补帧，解耦计算频率与渲染帧率。
- **刚体动画取代蒙皮动画**：当游戏里的动画本质上是机械运动时，丢掉蒙皮可以换回数量级的合批收益。
- **离线标注 + 异步粗筛 + 渲染精筛**：把复杂的剔除算法放到异步线程，允许几帧延迟，只换渲染线程热路径的稳定开销。
- 这一系列思路都贯彻了"为具体游戏定制 > 追求通用性"的取舍。
