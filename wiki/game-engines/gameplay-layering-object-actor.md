# Gameplay 分层：数据模型 / 表现 / 交互 + Object / Actor

[[cloudwu]] 在独立做单人游戏的过程中，把 gameplay 的上层结构梳理成了一套三层 + 双类的架构。这不是一个新范式，而是他从 20 多年底层开发经验里抽出来、特别适合"一个人写"的裁剪版本——**复杂度用分层吸收，持久化优先级拉到最高**。

## 三层切分：data / visual / interaction

整个 gameplay 拆成三块：

- **数据模型（gameplay）**：游戏真正的核心状态。判断标准很犀利——**它不应该有任何直接调用游戏引擎的代码**。不碰图形、不碰界面、不碰时钟、不碰 OS API（文件 IO 仅限读策划数据、写 log、持久化）。干净后就能整体或局部写单测；想换引擎、从 3D 降级到文本 roguelike 都不影响。
- **表现层（visual）**：画面、音效、粒子、镜头等。代码也会维护不少状态，但**这些状态都是"衍生的、可以从数据模型重建的"**。判断标准：存档时把这一层全部丢掉，重新加载后玩家感觉不到任何数据丢失。
- **交互层（HUD / GUI / Controller）**：处理原始输入，把设备级事件（鼠标点击、摇杆偏移）**翻译成 gameplay 语义的消息**（"发起攻击"、"向左移动"），不直接读写数据模型，也不直接控制 visual。

联网游戏还会加一个"网络输入"大块，本文不讨论。

分层的关键不是把代码按功能堆到不同目录里，而是**明确定义每层可以访问什么、不可以访问什么**。visual 可读 data（只读）；interaction 只能通过消息触达 data；data 绝不反向依赖任何一层。

## 双类：Object（被动数据）+ Actor（自治体）

数据模型内部再切一刀：

**Object** —— 按类别聚合的静态数据集合。场上物件、角色、任务清单等都属于此类。每个 Object 有 id + typename 这两个共有属性，**Object 之间尽量避免相互引用**；尽量**不提供 update 方法**，除非数据关联到必须用一个方法维护一致性。Object 是被动的。

**Actor** —— 游戏世界中的自治实体，关联一个或多个 Object、通过读写它们驱动游戏。Actor 用**消息驱动**，每类 Actor 有自己的 update 处理 tick 和消息。游戏世界对外的唯一交互接口就是"向某个 Actor 发消息"。**Actor 通常实现为状态机**，允许一个虚拟角色在不同状态下有不同行为。

之所以 gameplay 层不并行化，是因为大多数游戏的 gameplay 逻辑根本碰不到性能瓶颈。Actor 串行处理能彻底回避 Object 读写的并发复杂度——这是"**复杂度不要花在没必要的地方**"的典型体现。

## 持久化优先级最高

云风反复强调：**设计持久化方案是优先级极高的事情**。不是因为存档功能很重要（虽然也重要），而是因为**认真设计持久化会倒逼你把数据模型设计清楚**——哪些数据需要保留、哪些是派生的、哪些是运行时临时的。一旦持久化方案立起来，后续修改数据模型时会更谨慎。

但他同时警告：**不要把持久化简化为"把 Object 和 Actor 的内存结构直接序列化"**。持久化更像把运行时对象还原为"一组构造参数"，加载时按参数重建运行时结构。运行时结构往往为了性能做了复杂的交叉引用（例如 id → 订单的 hash 表方便查询），但持久化时用顺序列表更合适。这是典型的 [[aos-vs-soa|表示分离]] 思想——**运行时表示和持久表示是两回事**。

对 Actor 来说，大多数内部状态不该持久化，**通常只持久化"状态机当前状态的名字"就足够**，其余运行时状态在加载后按状态名重建。这与 [[multi-target-pathfinding|寻路模块]] 里"中间状态可随时重算"的设计原则一脉相承。

## 具体例子：工人送货

他举了个具象化的例子：一个工人从 A 点取货送到 B 点。

- **订单** 是一个 Object：起点、终点、货物种类与数量。
- **工人** 是一个 Object：当前位置、携带物、当前订单号。
- **工人控制器** 是一个 Actor：申请订单、接收订单、执行订单。

执行订单被拆成若干小步骤：定路径到 A、走到 A、拿货、定路径到 B、走到 B、放货。有些瞬时完成、有些要多 tick。**多 tick 过程里累积的中间状态都不持久化**——外部环境一变（路被堵），Actor 收到消息把状态机切回"寻路"，之前累积的中间态丢掉即可。

## 表现层怎么对接：immediate vs retained

对接方式看引擎的模式，参见 [[immediate-vs-retained-mode]]。核心原则恒定：**数据模型绝不直接调渲染 API、绝不持有 visual object 引用**；即便表现层要把物理系统反馈传回 gameplay（角色被撞飞导致位置变更），这种反馈也要先翻译成"给 Actor 的消息"，让它走消息接口。

连"存盘"都是消息：交互层发送"save"消息 → actor 处理时只做一个标记 → 每个 tick 末尾统一检查标记再执行真正的 save。这样 save 不会切断正在运行的 tick，数据一致性天然保证。
