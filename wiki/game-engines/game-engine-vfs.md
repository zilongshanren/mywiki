# 游戏引擎虚拟文件系统

几乎每个商业游戏都会把资源文件打包——一是保护（不让用户直接看到数据），二是 Windows 文件系统对海量小文件的处理性能低下。Doom/Quake 的 WAD、星际争霸的 MPQ、Allegro 的 DAT、自研 `.pak`——云风说这种"打包 + 本地文件共存（开发期裸文件，发行期打包）"的模式从十多年前延续到今天，接口变化很少，因为**一旦接口定下来，围绕它的工具链就会锁死**。

## 接口比实现重要

> 一旦一种包管理的模块成型，在一个公司内部就很容易长期用下去。

为什么？因为真正成本是周边工具链：打包 / 解包 / patch 生成 / 发布脚本。云风给了个非常具体的数据点：

- **网易的游戏升级补丁**：网络下载占整个升级时间 **95% 以上**，打补丁几乎瞬时。
- **暴雪的升级补丁**：网络下载往往不到 50%，大部分时间用户在等待 **patching** 而非 **downloading**。

好的包格式能极大提升 patch 速度，是个被低估的 [[interface-vs-implementation]] 决策。一次设计失误会被维护者的惰性放大几年，所以一开始的**概念**比实现重要。

## 一次反悔：过度设计的代价

云风 2001 年给《大话西游》设计的包格式用了将近十年没改。2006 年给新 3D 引擎重做时，他刻意避开旧思路：

- 资源文件里**显式记录依赖关系**，支持预读。
- 从系统里**去掉字符串文件名**，包内用 ID 关联。

听起来都很合理，但几年用下来，他反省道：

> 保持一般的惯例更有利于开发。看似不错的设计，由于人员沟通的成本，会极大的降低原本应该带来的好处。

新程序员进来都得先听他解释一遍整个资源系统的工作原理；精心设计确实带来了预读、多线程加载的性能优势，但抵不过**理解偏差导致的误用**造成的净负。这是一个 [[cognitive-load]] 的具体教训——也是他不喜欢 C++ 那种 all-in-one 设计哲学的动因之一：

> C++ 哲学下设计出来的东西都有 all-in-one 的倾向；C 的哲学设计出来的东西往往可以更好的相互融洽地工作。

## 第二次重写：Linux VFS 的简化版

2010 年那次重写，他直接拿 Linux VFS 当参照，做了功能削减版。核心观察：

**大多数时候游戏引擎只需要"读"——这能极大简化设计。**

### 架构

- **VFS 层独立于具体文件系统**：维护一颗虚拟文件树，节点上存文件名、目录项、cache。**不需要先有任何具体 FS 就能管理这棵树**。
- **多种具体 FS 实现**：本地文件系统、内存 FS、自定义包、标准 zip（便于开发期用）。
- **mount 操作**：每个具体 FS 可以被挂到 VFS 的某个挂载点上，按需展开这个点下的一级目录项（lazy）。
- **cache**：对同一文件的第二次访问走 cache。
- **嵌套包**：zip 里再套 zip 应当能用多级路径直接访问，不必递归解包到磁盘。

### 和 Linux VFS 的一处分歧：覆盖 vs 回落

Linux VFS 把新 mount 完全**覆盖**旧子树——挂上 `foo.zip` 到 `/foo`，原来的 `/foo` 不可见了。但游戏开发期希望：**zip 里找不到，自动回落到本地文件系统**。

云风的办法不是魔改 mount 语义，而是加一层"特殊文件系统"：

- 根下挂 `/zip`（包 FS）、`/os`（本地）、`/mem`（内存）、`/auto`（fallback 派发 FS）。
- 打开 `/auto/foo/bar.txt` 时，`auto` 依次尝试 `/zip/foo/bar.txt`、`/os/foo/bar.txt`……
- **成功后在自己的子树上创建一个软链接**指向真正的命中。下次访问 `/auto/...` 直接走链接，不再重复探测。

本质上是在 VFS 自身上用**软链接 + 延迟绑定**实现 fallback——不污染 mount 的语义，也天然带 cache。

## 设计价值观

这篇笔记里有几条他一直反复强调的取舍，值得单独抄一份：

1. **独立出来的"树管理"和"具体 FS"**：一个是 [[abstraction]]，另一个是策略，各自可以替换。
2. **优先权威概念（Linux VFS）而非自创概念**：新程序员一眼就能理解，沟通成本低。
3. **只读语义大幅简化设计**：承认"我们真正需要的是什么"。
4. **软链接兜底 fallback**：比"注册 loader 轮询"的旧方案更通用，因为 fallback 的结果被 cache 进了树。
