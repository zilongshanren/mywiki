# 用 C 实现的 ECS 粒子系统

[[cloudwu]] 在 2024 年重拾 2020 年 [粒子系统设计] 的话题，把它落到了一个纯 C 的实现 `psystem_manager.h`。核心问题是：粒子这种"数据量大、每个粒子属性不同、行为在运行期组合"的对象，用传统 OOP 静态结构体 + 虚函数写会非常难受——最终会长成满是 `if/else/switch` 的分支丛林。换成 [[ecs]] 结构之后，把同一属性的大量粒子聚合管理，天然获得了 [[aos-vs-soa|SoA]]、[[cache-friendliness|缓存友好]]、并行友好、属性自由装配这四项好处。

## 为什么粒子系统天然适合 ECS

云风给出的观察朴素但切中要害：处理粒子时，单个 tick 里关心的往往只是某一个属性。递减生命期时只碰 life；应用重力时只碰速度和加速度；做空间更新时只用上一帧位置和瞬时速度；渲染时这三者又都不关心。**在任何一个时刻，代码的工作负载只覆盖对象的一小片断面**。按属性列连续存放，对应的 cache line 只装真正用到的字节，即使某个属性只有一个字节也不会因 struct 对齐浪费；同时同属性的数据尺寸统一，批处理的内层循环简洁。

更关键的是组合性：不同类型粒子装配不同的属性组合——有的有物理、有的只有贴图、有的是 mesh 而非 sprite。即便同样拥有"物理形状"属性，有的参与刚体碰撞改变轨迹、有的只用来触发事件。OOP 的做法是用多态和大量开关；ECS 的做法是把"哪些粒子参与这个 system"变成查询条件，行为自然按组件分发。

## C 的朴素实现与 C++ 的自我怀疑

云风先给了一个 C 版本，把属性分开管理的核心数据结构摊开，所有操作是平铺的 `for` 循环。然后他用 C++ 重做了同样的功能，一整个晚上做完后反而陷入怀疑：强调类型安全换来了什么？C++ 版本用模板与类型系统保证"只有拥有 life 的粒子才能走 life-decay system"，编译期消除了一类错误，但代码的浅显易懂性明显下降——读者要先理解一套 template 机制才能看懂这个粒子系统在做什么。

这就是 [[type-safety-vs-simplicity]] 这条张力的具体展开：类型安全的收益（早期发现 bug）与它带来的认知成本（更难读、更难 onboarding、更难重构）并非永远正比。对粒子系统这种"逻辑朴素、数据量大、性能敏感、改动频繁"的模块，云风倾向后者——C 版本丑陋但所有细节都摆在明面上。
