# 移动游戏的能耗优化

传统游戏引擎的性能优化目标是"最小化单帧延迟"——每件事做得越快，帧率越高。但在手机上，这个目标并不完整。[[cloudwu|云风]] 在 2024 年 4 月复盘 [[ant-engine|Ant Engine]] 的性能工作时指出：达到 60fps 不等于优化完成，因为**手机玩家有电量焦虑**。玩家担心玩完一局游戏后手机电不够扫码付费、支付公交，这会在心理层面限制"长时间沉浸式"游戏类型在移动端的生存空间。云风甚至一度怀疑手机是否真的适合这类游戏，或许放置类这种"玩一下放一下"才是本质更匹配的形态。

## 低延迟与低能耗的本质分歧

一旦承认能耗目标，优化方法论就翻转了：

- **传统延迟优化**追求每个步骤尽量快——尽快做完、尽快返回，时间是敌人。
- **能耗优化**追求"少做"——在较长时间尺度上尽量减少重复计算，能缓存的都缓存。哪怕**复用缓存比重算更慢也值得**，因为 CPU/GPU 不干活就能下电。

这条原则在硬件层面其实早已被固化——手机 GPU 的 [[hsr-tbdr|Tile-based rendering / TBDR]] 架构本质上不是"为了渲染更快"，而是用更低功耗的方式**检测潜在的重复计算并在 tile / 帧之间缓存结果**。它不是一个速度优化，而是一个能耗优化被伪装成的速度优化。

## 运动插值：降频算物理

Ant Engine 在 *Red Frontier* 里放了大量跑在公路上的小货车、在仓库与机器之间穿梭的无人机——这些对象每帧都要更新位置并同步到渲染底层。常规做法是每帧在 Lua 里算一遍，数百个这样的对象加起来 CPU 就吃不消。

云风的解法是**降频**：gameplay 层用一个非常低的帧率计算这些对象的离散位置，然后在 C 里实现一个运动插值器，把离散点在渲染线程补成连续轨迹。**逻辑计算的频率和渲染帧率解耦**——一个为 gameplay 服务的采样节奏，一个为视觉连续性服务的插值节奏。

## 合批的代价：牺牲表达自由换回几千份绘制

游戏里大量建筑带有动画。一开始在 Blender 里做蒙皮骨骼，导出后由于相同建筑"动画相位不同"，引擎很难把它们合并到一个 draw call 里批量绘制。这是 [[gpu-skinning-matrix-palette|蒙皮合批]] 的经典难题。

Ant 团队做了两层尝试：

1. **强制相位对齐**：把每个建筑的动画切成四类（停工 / 运转 / 两段衔接），每类都做成相同时长 3 秒，gameplay 只在 3 秒整数倍切换动画。这样所有同类建筑的动画相位就完全一致，可以蒙皮合批。
2. **放弃蒙皮**：后来云风意识到游戏里的动画全是机械运动，根本不需要蒙皮——每个零件都是刚体，骨骼直接驱动刚体位姿即可。把美术工具重写了一遍，唯一一个美术用 3 个月把所有蒙皮动画转成刚体动画，**相同零件天然就能合到同一 draw call**。

这是一个典型的"放弃通用性换性能"的取舍：蒙皮是 3D 引擎的通用武器，但具体游戏未必需要它。如果你能看清游戏的动画本质上是几何变换而非形变，删掉蒙皮可以换回数量级的合批收益。

## 结果

经过这些优化，游戏在 iPhone 上的单位时间耗电据称比刷微信 / 抖音还低——这让云风"对性能不再焦虑"，转而把精力放回 gameplay 本身。从"能玩"到"玩久了也不怕没电"是两个完全不同的工程阶段，后者是传统 PC / 主机游戏引擎方法论触及不到的区域。
