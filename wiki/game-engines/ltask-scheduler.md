# ltask 任务调度器

ltask 是 [[ant-engine|Ant Engine]] 的并发基础设施，负责把 m 个任务（服务）调度到 n 个 CPU 核心上执行。表面上它要解决的问题和 [[cloudwu|云风]] 的另一个代表作 skynet 相同，但优化目标完全相反：**ltask 面向游戏客户端的低延迟，skynet 面向游戏服务器的高吞吐**——这对矛盾决定了两者在调度器设计上几乎走向对立的路。2024 年 3 月云风重构了 ltask 的调度器，这篇重构笔记把两种场景的取舍、以及一个被删除的大特性"独占线程服务"讲得相当透彻。

## 低延迟与高吞吐的对立

服务器端（skynet）有**成百上千**的同质任务，优化目标是让 CPU 一刻不闲：最简单的做法是每个核心一个任务队列，谁闲谁从别人那里"偷"任务，或者一个共享大队列加上一个好的竞争规避算法。调度器本身越简单越好，感知不到最好。

客户端（ltask）只有**一两个重负荷任务加一堆轻任务**。优化目标是让"主线任务"的延迟最低——每一步一旦依赖满足就应立刻开始，因为主线任务的完成时间往往等于整帧完成时间。这就不得不接受更复杂的调度器算法与更多的调度器运行开销，用复杂度换延迟。

这条鸿沟是云风做两套系统的根本理由。能否"既要又要"？他的答案是不能——两种算法的假设前提就是对立的。

## 为什么删掉"独占线程服务"

早期 ltask 为了回避一些不好处理的边角，把服务分成两类：**共享工作线程**的服务由调度器管，**独占系统线程**的服务交给操作系统去调度。后者用来塞三类麻烦事：

1. **会阻塞的系统 API**——`sleep`、`select`/`epoll_wait`、IO 等，会长时间占着系统线程。
2. **要求同线程调用的 C 库**——某些 C API 内部使用 TLS，或者要求必须在主线程调用，光靠"服务内串行"不够，还要保证物理线程不变。
3. **永不返回的系统循环**——如 iOS 上窗口创建后主线程会阻塞在系统调用里直到退出。

云风一开始认为"独占线程把复杂性吸走"，后来发现两套 API 的边界越来越模糊，想统一又让中间层更复杂。重构时他一一重新审视这三个问题：

- **第一个问题**（阻塞系统调用）他曾尝试仿照 Python 多线程的思路——Lua VM 类比 Python 的 GIL，把"在 VM 内"和"在 C 代码内"划分为两态，用 `yield` / `resume` 两个 C API 显式标注边界。在 C 代码区域内可以并行（由 C 自己负责线程安全），但这要求改写所有已有 C 库，使用者也容易用错。最终他放弃了这套，转而承认"**阻塞工作线程没那么不可接受**"——只要稍微增加工作线程数（超出 CPU 核心数）、再让调度器对长挂起的工作线程做特殊处理即可。
- **第二个问题**（服务与物理线程的绑定）才是 ltask 真正没做好的一块。他为调度器加了"将服务绑定到特定工作线程"的能力——不是独占，而是"这个服务永远跑在那条线程上"，从而满足 TLS / 主线程的硬约束。
- **第三个问题**（iOS 主线程永不返回）他选择不在 ltask 里解决——因为这是唯一特例，而 ltask 定位是库不是框架，使用者完全可以在 ltask 之外单独写几行代码兜住。

三个问题都有了更便宜的解法之后，独占线程服务这个大特性就可以整个删掉——C 代码减了 600 多行，Lua 代码也大量简化。

## 绑定不等于低延迟

重构过程中最反直觉的一条观察：**把"关键任务"绑定在某条物理线程上未必能得到最低延迟**。云风用一个小的思想实验来解释——如果团队里有一个任务特别关键，管理者倾向于把所有步骤都交给同一个人做；但这人若中途被依赖卡住，要么闲等浪费产能，要么去做别的事但回不来了。

大多数商业引擎都把渲染线程、物理线程等"主要任务"固定到固定系统线程，把问题丢给 OS 调度器。云风的观点是：这样做是默认"OS 更聪明"，但其实 OS 无法理解任务之间的依赖——它只看到被阻塞的线程。**想真正降低延迟，就得有一个可以当替补的工作者**，而这正是自研调度器能做、而系统调度器做不到的那层。

## 和 Python GIL 的一段对话

重构笔记里一段有趣的旁注：Python 的 GIL 看起来是多线程的敌人，但云风认为它其实把"VM 解释器在跑 Python 代码"和"VM 已经进入 C 库"这两件事划得很干净——GIL 锁住的只是前者，后者（进入 C 库之后）允许真正的并行，只要 C 代码自己保证线程安全。Lua VM 在一定条件下（独立 coroutine、不触发 GC、不构造新对象）也能这样用，但约束太苛刻、容易出难定位的 bug，他最终没有选择这条路。
