# 游戏引擎向 Web 工程学习的四堂课

[[angelo-pesce]] 在 2024 年的一篇文章中系统梳理了游戏引擎开发者可以（也应该）从 web 工程借鉴的思维模式与实践，驳斥了"游戏开发者才是真正的精英程序员"这一偏见。核心结论是：领域间工程实践的差距完全来自需求压力与市场激励的不同，而非智识水平的高下。

## 第一课：接受"糟糕代码"是产品工程的常态

纯粹的代码美学只在代码本身是产品的情况下成立（教学代码、演示项目）。一旦代码服务于产品，它就必然承担技术债与各种妥协。好的工程师不是写出没有糟糕代码的人，而是**让糟糕的部分不暴露在最终体验和长期可维护性上**。Razer 的驱动软件是反面案例（恶意软件级别的"垃圾"全部暴露给用户）；VS Code 和 Python 是正面案例（运行时开销巨大，但"浪费"换来的生态价值超过了成本）。

## 第二课：大多数计算机科学规律与规模无关

磁带时代为最小化寻道次数设计的算法，映射到今天的 CPU 缓存结构上仍然适用——因为"计算是局部的，数据增长就变得昂贵"是普遍规律。Hadoop 的 map/reduce 与 GPU 的数据并行是同一个模式在不同尺度的实例。REST 的本质是不可变数据结构加引用透明，提供天然的缓存语义；SOAP 可以理解为 Actor 模型的一种实现。认识到这些同构关系，就能跨越领域边界直接迁移洞见。

## 第三课：Web 后端领域的模块化实践遥遥领先

Web 服务因物理上运行在不同机器而被**强制**实现模块间隔离：子系统必须通过接口通信，崩溃不会级联，部署可以滚动更新，测试必须通过接口边界进行。游戏引擎中这些事情极少被当作一等设计目标，导致"音频系统崩了，所有人停工"或"要改引擎就得重编整个工程"的局面。Pesce 认为游戏引擎在 API 设计、契约测试、热重载等方面都可以从 web 服务实践中借鉴大量具体技法。

## 第四课：编程语言长期在错误的粒度层面思考

主流语言优先考虑**代码复用**（函数、类、库、包管理生态），而非**运行时隔离**。结果是代码可以随意共享，但复杂度也随之蔓延。Pesce 认为运行时隔离才是控制系统复杂度的有效手段——正如操作系统通过进程隔离让"OS 以下的代码"对应用透明。Erlang 的进程模型是极少数以运行时隔离为语言一等公民的设计。参见[[complexity]]与[[engine-layering]]中关于边界划定的讨论。
