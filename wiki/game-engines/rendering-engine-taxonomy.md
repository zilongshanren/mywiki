# 渲染引擎分类学

[[angelo-pesce]] 在 REAC（Rendering Engine Architecture Conference）的背景下提出：渲染工程领域缺乏一套**描述上下文的共同语言**，导致架构经验难以迁移——一个方案在某个引擎里完美运作，放到另一个引擎却完全不适用，却没有人解释清楚"这两个引擎有什么根本不同"。

类比数据库领域：没有人会说"这是做数据库的正确方式"，而是先问：关系型还是 KV？分布式吗？强一致吗？渲染引擎同样需要这样的分类维度。

## 三组九维度

**1. 产品特征**

- **引擎用户范围**：单一团队内部引擎 → 多团队共用 → 单类型中间件 → 多类型中间件 → UGC 平台（如 Roblox）；
- **平台支持广度**：单平台（PC / PS / Web） → 多平台 → 多模态（PC + 移动 + 主机 + Web + VR + 车载）；
- **可扩展性需求**：是否需要跨能力差异巨大的设备缩放？向下（LOD 降级）、向上（程序化细节生成）还是双向？

**2. 生产：人与流程**

- **内容抽象层级**：引擎是"绘制 API 封装"（无内容管线，代码驱动）？还是数据驱动？数据驱动的话，是通用网格属性 + Shader Graph，还是为特定内容类型写死渲染循环（narrow schema）？
- **迭代模式**：优先支持实时编辑（无需烘焙，UGC 常见）？还是接受较长的烘焙-预览周期？
- **用户画像**：美术驱动还是工程驱动？面向专家还是易用优先？

**3. 技术需求**

- **延迟要求**：数据可以双/三缓冲以助并行，还是必须尽早执行（低延迟 XR / 交互场景）？
- **动态性**：哪些数据被约束为静态（可烘焙），哪些允许每帧变化？
- **流式传输**：无流式（全量在内存）/ 本地流式（磁盘→内存）/ 分布式流式（服务器→客户端）？

## 第十维度：规模（用户量与团队规模）

Pesce 认为这是最重要但也最被忽视的维度。**没有用户的技术在工程复杂度上几乎是平凡的**。工程问题随产品用户数和团队规模呈指数增长：

- 团队大小影响代码如何被组织，模块边界如何划定；
- 某些在小团队看来"好"的算法，在大团队维护下可能因复杂度或依赖关系成为瓶颈；
- AAA 引擎未来面临的是"商品化"——更高效地覆盖更多用户，而不是发明新的游戏类型。

## 实用价值

有了这套语言，就能在上下文中回答具体的架构问题：

- 最佳线程模型？→ 取决于延迟需求；
- 最佳 draw call 抽象？→ 取决于平台广度与内容类型；
- 场景数据结构？→ 取决于内容类型与用户预期；
- 如何接收游戏/仿真端的更新？→ 取决于动态性和实体变化频率。

Pesce 明确指出，这套分类不是要被奉为标准，而是邀请每个人在分享架构经验时**主动声明影响该选择的关键上下文因素**，而不是只展示"这是我们怎么做的"。
