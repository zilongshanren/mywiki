# 按游戏类型做薄封装框架

[[cloudwu|云风]] 2024 年 9 月给 [[ant-engine|Ant 引擎]] 开出的一剂处方：在引擎之上再做一个精简版的游戏框架，按当前游戏的需求从最基本功能开始、逐步完善；把"引擎已经做好的部分"与"设计不满意、想动刀的部分"用这一层框架隔开。

## 问题

云风在独自使用 Ant 引擎开发游戏时碰到两件事：一是引擎某些模块不是他亲手写的，没有完整的 API 文档，只能不断回去读源码；二是并非每个模块的设计都满意，让他"经常有修改引擎的冲动"。直接改引擎会破坏老代码、得罪其他 user。

## 方法

额外做一层轻量框架（discussion #199），这层框架的任务是：

- **好用的模块**：做浅封装，让游戏代码不直接碰引擎 API；
- **有问题的模块**：在框架里写不侵入的改进（包一层、替换一层），让底层引擎保持稳定；
- **针对游戏类型二次封装**：本来不同类型的游戏使用引擎的方式就差异巨大，框架可以只为当前这个游戏（基地建设 + 生存）定制，不追求通用。

这样，**游戏代码只依赖框架，不依赖引擎本身**。后面无论底层是被大刀阔斧重构、被裁剪、甚至被替换，都可以让游戏相对免疫。

## 和其他立场的呼应

- 对应 [[interface-vs-implementation|接口胜于实现]]：框架就是一层新的接口，让底层实现有重写空间；
- 对应 [[ecs-data-oriented-revert]]：ECS 回归面向数据，gameplay 辅助上移到这一层薄框架；
- 类似 skynet 的 `service` 模式：底层给足原语，业务按场景再组合。
