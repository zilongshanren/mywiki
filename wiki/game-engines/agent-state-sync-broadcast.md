# Agent 状态同步与广播优化

在 actor 模型的游戏服务器（如 [[cloudwu]] 的 skynet 及其自研项目）中，每个玩家由一个独立 Agent 进程代表。Agent 需要把自身状态变化（位置、动作、技能释放）告诉虚拟场景中附近的其他玩家。当同一地图上聚集 50+ 玩家时，状态同步包的数量按 $O(n^2)$ 级增长，会迅速成为服务器内部通讯的主要负载。

## 朴素方案：无过滤广播

最省事的做法基于一个假设：**服务器内部广播比逐个发送更廉价**，因为同机器内的 actor 系统（如同机内 Erlang 进程、skynet 同节点服务）通常把消息传递退化成指针传递或函数参数，省掉序列化开销；广播时发一份内存，N 个接收者共用，不需要复制 N 次。在此假设下，同地图任意 Agent 的状态变化直接向全地图广播，由每个接收 Agent 用自身逻辑（距离、视野、队伍关系）做过滤，再决定是否转发给各自的客户端。这避开了动态维护 AOI 分组的复杂度。

## 假设失效的时刻

云风在 2025 年 2 月的 40v40 压测中发现多人战场 90% 的内部通讯包是状态同步包，原有"广播廉价"假设下的设计开始吃紧。即便 Erlang 进程间通讯在同节点被退化为函数传参，数据 marshal 和内存复制依然有可观边际成本；接收端过滤意味着大量 Agent 做无用功。

## 优化方向

- **区分静态订阅与动态分组**：位置、视野几乎不变的 Agent 可以预建订阅关系，避免每帧重算
- **降低广播单位**：按房间/区块分，而不是整张地图一锅端
- **减少内存复制**：用引用计数 / immutable 消息，让所有接收者共享同一份内存
- **协议 diff**：只同步变化量，参考 [[snapshot-diff-persistence]] 的思路
- **过滤下推**：把可见性过滤放在发送端而不是接收端，节约无效派发

这类优化落在"早期发现的性能问题常常是设计错误的外显"这条云风反复强调的原则上——越早动刀越省力。
