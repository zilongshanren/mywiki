# 游戏资源包格式与补丁更新

把数千上万份美术、音频、关卡数据合成几个大的"资源包"（asset pack / archive），再让游戏引擎从这些包里按需读取，是商业 PC 客户端长期的标配——Quake 的 `.pak`、暴雪的 MPQ、Unreal 的 `.upk`、网易《大话西游》的自定义包都是同一类东西。[[cloudwu]] 在 2010 年总结了他 9 年前替网易设计、并在多个项目里反复演化的资源包格式，连同对"下一代引擎应该怎么改"的设想，是一份难得的工程笔记。

## 最初的设计目标

- 解析快、定位单文件快
- 更新方便、补丁体积小、节省玩家下载带宽
- 可承受频繁更新（MMO 的日常补丁场景）

## 索引与文件名脱敏

文件结构上，最初是把所有要打包的文件首尾相连，文件末尾追加一张索引表。索引里**不存文件名字符串**，只存文件名的 hash，这样既能按 hash 直接定位、又顺手做了"防解包"——文件名清单单独保存在不对外发布的 `index` 文件里。这套思路与暴雪的 MPQ 完全一致，网上的 MPQ 解包工具往往要附带一份针对特定游戏的"已知文件名列表"才能还原原始路径。

## 允许包内"空洞"——为更新速度让路

第一个重要分歧是：**网易包允许文件之间留下被删除文件的空洞**。常规打包软件删除一个内部文件时会前移后续数据来填空，这在玩家更新时会触发大量文件 IO；WoW 或 SC2 打补丁的总耗时里，下载只占一小部分，**绝大多数时间花在把 patch 应用到本地 MPQ 上**。云风的方案是删除即释放、不移动数据，新增小文件优先复用空洞，复用不上就把空间浪费在那。这等价于在资源包内做了一份原始的[[linear-allocator|内存分配器]]——时间久了会有碎片，但对玩家可接受。

## 旁路更新：另一份高优先级包

第二种更新通路是把待更新的文件**单独打成另一份资源包**，与原包同名不同后缀放在玩家硬盘上，引擎读取资源时优先在更新包里检索。这种"前置覆盖"思路与 id Software 的 Quake / Doom 系列完全一致——`pak1.pak` 会覆盖 `pak0.pak` 里的同名文件——优点是补丁安装本身几乎零成本：把新包丢过去就行。

## 补丁不是文件集合，而是整包二进制 diff

最有意思的是补丁本身的形态。网易的补丁不是"被改动的小文件的压缩包"，而是**整个资源包的二进制 diff**。因为允许空洞、且包内布局相对稳定，"局部修改的资源对整个资源包二进制布局的影响"被压到很小，diff 出来的体积就很小。这套设计被后来的同事质疑过：直接发小文件、让玩家机器逐文件 patching 难道不够？云风给出的历史原因是——10 年前硬盘 IO 极慢，《大话西游》又要做无缝大地图加载，地图文件本身被特别设计成支持局部更新的形态；对这种文件、以及未压缩贴图，二进制 diff 的命中率非常高。今天的工程项目越来越多用文本数据（JSON / XML），一个小改动就会冲垮整个二进制 diff，于是 diff 的优势变弱，但这并不否定原始设计的合理性——它是被当年的硬件特征逼出来的。

## 下一代设计构想

云风设想新引擎里改进几件事：

- **内置压缩**。原格式不管压缩，由上层模块管。新格式希望像文件系统那样把大文件**分块**，每个块独立选择压缩或不压缩；用类似 FAT 的表来管理分块。这样既能压缩、又能保留对单文件的随机访问能力，也方便把数据包**嵌套**进数据包。
- **包内链接**。开发期允许同一资源以独立副本反复出现在不同子目录里（比如模型旁边各自带一份贴图），打包时检测内容相同的文件、合并成"链接"。引擎也能识别这种链接，让相同资源只加载一次。
- **补丁工具的工作流改进**。补丁文件直接装的是每个小文件的 diff，而不再是整包二进制 diff。打补丁时由专门的 `patch` 工具从旧包里抽出待 patch 的小文件、与 diff 合并、再删除旧包里那些条目并向前压缩空洞，最后把新旧两段拼起来。压缩空洞会消耗一点 IO，但因为"经常被改的文件会被逐渐挤到包尾"，搬运量会自动变小。这一套设计让补丁包本身更"干净"，也更适合每日构建发布流程。

## 工程权衡

这篇笔记本身就是一份"为什么早期的奇怪设计是有道理的、但现在该怎么变"的好例子：

- **当年的瓶颈是磁盘 IO**——补丁慢主要慢在 patching，而不是下载，所以选择二进制 diff + 空洞复用。
- **数据形态在变**——文本格式让二进制 diff 失效，触发"按小文件 diff"的方案重生。
- **开发期友好与发布期友好同等重要**——内置链接、嵌套包、每日构建友好的打补丁流程都是为了让程序员/美术不被资源管理拖慢迭代速度。
