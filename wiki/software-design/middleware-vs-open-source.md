# 中间件 vs 开源：独立团队的依赖取舍

[[branimir-karadzic]] 在 2011 年那篇《Open source or it didn't happen!》里记录了 Carbon Games 做《AirMech》时的一个选择：**把最后一个闭源库从代码库里剔除，改成要么自研、要么用开源**。这不是反商业的意识形态发言，而是一份实打实的工程取舍清单。

## 中间件的真实代价

团队并非原则上反对商业中间件，但几乎每一次选型都证明它是"绊脚石"：

- **平台锁定**——中间件厂商可能不支持你要上的平台；
- **法律阻力**——复杂 License 协议签署耗时；
- **广告负担**——很多中间件强制在启动时显示其 Logo 若干秒；
- **供应商风险**——厂商如果不支持某平台，就是团队的瓶颈。

作为独立团队，能自由挑平台并在上面移植代码，这点本身就值钱——这也是他们后来把《AirMech》移植到 [[native-client-porting]] 一类非主流平台时的先决条件。

## 选择开源库的守则

作者明确指出"开源"不等于"好"，他们的筛选标准非常"Orthodox"：

- **小而专**——只做一件事、做好一件事；避免试图"什么都做"的大库。
- **易集成、易维护**——额外依赖越少越好。
- **C 比 C++ 优先**——即使项目用 C++，C 库通常比 C++ 库简单（C++ 库常因为作者想炫耀元编程技巧而复杂）。
- **不依赖 exceptions / RTTI**——这两者在他们所有 build 里都是关闭的，与 [[orthodox-cpp]] 一脉相承。

文中举了个 JSON 库的对比：客户端需要的是既轻又只处理"可信来源"（自家打包或后端）的 JSON，那么 **JSON_Spirit** 这种厚重 Boost 风的库就输给了 **js0n** —— 单文件 C、无依赖、不做多余校验。后端那边要对客户端不可信数据做校验，才用得上更厚重的库。"Simple always wins!" 是他们的选型口号。

## 放回当时的语境

2011 年的另一个背景是：显卡行业已经收敛到少数几家厂商与少数几种 API，不再像 1990 年代那样需要面对各种奇葩显卡、甚至还得给没有显卡的玩家写软光栅。这让独立团队"自己做引擎"重新变得现实——显卡成熟 + 开源生态成熟 = 做游戏从未如此容易。

作者还提到一个副产品：他们打算未来把代码库里**独立的组件**以 BSD 2-clause 放出来，而不是整体开源。这和他后来 **bgfx** 的做法一致——bgfx 本身就是一个"小而专、易集成"的渲染抽象，符合他自己总结的守则。

## 与本 wiki 的其他节点
