# 软件发布估时难题

软件交付的时间估算之所以普遍失准，根因在于软件的**根本性可复用本质**：每一个值得做的功能，都是你的团队有史以来**第一次**做这种事。

## "第一次造房子"的类比

Brent Simmons 把应用开发比喻成「历史上第一次建造房子，用一堆生锈的钉子和赤手空拳，在永不停歇的龙卷风中施工」。这个比喻之所以准确，正是因为软件的可复用性把所有的"重复劳动"都消除掉了：

- X-Plane 的飞机内容制作（3D 建模、UV 展开、动画、贴图）有稳定的工作量估算，因为每架飞机的**任务类型**相同
- 但软件功能没有这个性质——一旦把渲染引擎移植到 Vulkan，就永远不会再做第二遍，因为 Vulkan 支持已经在那里了
- 每个软件功能相对于上一个都是**全新品种**，没有已知参照系

## 缩减范围是唯一有效手段

Brent 的文章结尾说"唯一让软件发布的原因是人们不停地工作直到准备好"。[[ben-supnik|Supnik]] 认为这只说对了一半。实际上还有另一条路：

> 缩减范围，让它只包含**已经完成**的那些部分。

这是真正能压缩交付时间的唯一杠杆。如果"什么算准备好"的定义可以动态调整（市场条件变化、实现过程中对真实需求的理解加深），那么有时候**软件会在你意识到之前先准备好**——那就是所谓的"Klingon 软件"：它逃出去了，留下一路血迹。

这与 [[good-software-no-double-check]] 和 [[always-shippable-game]] 的精神是一致的：识别已完成的最小集合，尽早交付，而不是等到所有预想功能都做完。

## 估时的正确心态

- "ready"不是固定的终点线，是一个随时间浮动的动态标准
- 功能颗粒度越细、越独立，越容易拿出"已完成子集"来交付
- 越是大型、职责混杂的模块，越容易形成"全做完才能发"的锁死
