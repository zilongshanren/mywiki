# 文件格式与内存数据模型的分离

把内存数据结构直接序列化为文件格式，是一种表面省事、实则将两个设计目标对立的东西捆绑在一起的做法。[[ben-supnik]] 在 WorldEditor 的演化中亲历了这一代价，并将其归纳为：**序列化容器合理，但把容器结构作为文件格式规范是糟糕的选择**。

## 两种目标的根本分歧

内存数据模型和文件格式服务于截然不同的约束：

- **内存模型**：针对运行性能优化——局部性、快速遍历、减少间接跳转、方便算法操作；可以随代码重构自由改变。
- **文件格式**：针对持久化优化——长期可读、向前兼容（旧程序能读新文件）、向后兼容（新程序能读旧文件）、易于调试/手工编辑；一旦写入磁盘就必须保持稳定。

把两者合一，就是声称"运行时高效的布局"同时也是"持久化稳定的布局"——这几乎不可能成立。

## 直接序列化的代价

WorldEditor 的多边形模型用"thing 树 + 隐式边（每对顶点间的 edge 隐含）"表达。选中边的需求迫使引入显式 edge 对象，但旧文件没有 edge，读取旧文件时需要"理解旧数据结构来重建新结构"。代价是二选一：

1. **保留旧代码**：维护一套仅为解析旧格式存在的旧数据结构，这套代码会随着时间越来越难维护。
2. **让新数据模型兼容旧布局**：向内存模型里加入"edge 可选"逻辑，这把向后兼容的负担注入了本该聚焦性能和正确性的内存结构。

X-Plane 从 v9 到 v10 的迁移是另一个教训：v9 的飞机文件是内存 C 结构体的 `memcpy`，v10 必须保留整套 v9 的 C 结构体、`fread` 进来、再逐字段搬运。改用 key-value 格式后，后续版本迁移就轻松得多——新代码遇到不认识的 key 跳过，旧 key 缺失时用默认值，升级是增量的。

## 翻译层是特性，不是负担

主动为文件格式写一层**翻译代码**（内存 ↔ 文件）看起来多余，实际上是一条保险：

- 当内存模型因性能需求重构时，翻译层只需更新一个方向；
- 当文件格式需要向后兼容时，翻译层是唯一需要修改的地方，内存模型保持干净；
- 翻译代码本身可以随时间积累版本分支，而不会污染主数据结构。

如果不在版本 1 写翻译层，最终还是要在版本 2 写——只是那时候你要翻译的东西是一个从未为可读性和稳定性设计的格式。

## 例外：生命期限于单次运行的情形

对于 undo 栈、会话缓存、进程内消息这类**不需要跨代码版本存活**的数据，直接序列化完全可以接受——反序列化代码和序列化代码由同一份二进制执行，绝不会遇到版本漂移问题。这正是 WorldEditor 的 undo 系统能用直接序列化、而磁盘文件不行的原因。
