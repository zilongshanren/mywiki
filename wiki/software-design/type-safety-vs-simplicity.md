# 类型安全 vs 代码浅显——一次自我怀疑

[[cloudwu]] 在做完 C++ 版本的 [[ecs-particle-system-c|ECS 粒子系统]] 后写下的反思：**"强调类型安全无非是为了减少与之关联的代码的缺陷，提高质量；但代码不那么浅显易懂却降低了质量。"**

这不是对类型系统的否定，而是对一个常被隐去的权衡做直白的命名：类型安全的收益是提前暴露一类错误（在编译期或链接期，而不是运行期），代价是为表达约束而引入的抽象机制——模板、 concept、复杂继承体系、运行期 RTTI 等等——这些机制会加厚代码，需要读者先建立额外的思维模型才能读懂系统本身在做什么。

## 两种"质量"的冲突

**质量的一种度量是 bug 数**：类型安全的收益主要在这条坐标轴上，它阻止"把速度当位置传"、"把 sprite 句柄喂给 mesh 系统"这类 whole class 的错误。

**质量的另一种度量是可读性/可维护性**：一份代码只有被人轻松读懂，它才能被正确修改、被正确复用。当类型机制本身成为"代码里最难懂的那块"时，它就从资产变成了负债——新人读不懂、迁移时不敢改、调试时需要反复查模板展开。

这两条坐标轴在大多数项目里不是同向的，而是存在 trade-off。把系统往任意一端推到极致，另一端都会损失。

## 云风的立场

他的经验判断是：**对逻辑朴素、改动频繁、性能敏感的底层模块**，C 的粗糙但透明比 C++ 的严密但绕要更合适。粒子系统就是典型样本——算法本身非常简单（属性 × N 的批处理），错误的代价低（粒子画错一帧没人看得出），而代码的修改频率高（每次新美术需求都要加 flag、加属性、加变体）。在这种场景，让代码"一眼看穿"比"编译器帮你兜住"更重要。

反过来，他也不是一刀切地否定类型安全——金融系统、协议解析、跨语言 binding 这种错误代价高或边界复杂的地方，严格类型仍然是正确选择。区别在于认清当前模块到底属于哪一类。

## 与 APoSD 的呼应

[[john-ousterhout|Ousterhout]] 的 [[complexity|软件复杂性]] 框架里把"读一段代码需要多少脑容量"（[[cognitive-load|cognitive load]]）列为复杂性的核心指标之一。类型机制膨胀到喧宾夺主时，它就是在贡献 cognitive load，哪怕它同时减少了 bug。[[deep-modules|深模块]] 的理想是**复杂实现 + 简单接口**；[[shallow-modules|浅模块]] 的典型症状是**简单功能 + 花哨接口**——过度的类型包装有时正是把一个本该深的模块压薄成浅的。
