# 始终可发布的游戏（Always-Shippable Game）

游戏项目在生产阶段的任意时刻都应当处于**可发布状态**：能运行、不崩溃、不超内存、帧率达标。迭代的本质不是从「未完成」走向「完成」，而是从「可发布但粗糙」走向「可发布且精细」。

## 为什么这是原则而非目标

[[people/angelo-pesce]] 把游戏开发类比于绘画：你不会让一位画家负责手指、另一位负责眼睛、再一位负责鼻子，然后期望所有部分在截止日期前完美拼合。游戏也一样——没有一个可以随时停下来的「整体」，在 crunch 期拼合碎片只会得到一个损坏的产品。

这与 [[component-degradable-build]] 的思路吻合：每个功能集成时就要集成到一个活的整体里，而不是在某个时间点批量合并。

## 完成的五项标准

Pesce 给出的「任务完成」清单：

1. **Checked-In** — 代码已提交到版本控制。
2. **Stable** — 通过自动化测试，不引入新崩溃。
3. **In-budget** — 内存与性能预算满足目标平台要求。
4. **Usable** — 有工具和参数接口，美术/设计师可操作。
5. **Verified** — 美术总监、设计师或主程序已验证效果。

前四项缺一，就是在对团队、对项目撒谎。第五项确保功能不只是技术正确，而是在整体语境中成立。

## 与 waterfall 的对立

Game jam 式「后期整合」是 waterfall 思维在创意行业的错误移植。创意工作的不确定性要求每一步改动都能在整体中验证。[[zero-tolerance]] 对类似思路做了补充：不合格的状态不该被容忍哪怕一天。

## 为什么 crunch 是症状

如果一个团队到了 crunch 才开始让游戏「能跑」，那么所有隐藏的技术债在截止日期前集中爆发是必然的。Always-shippable 模式让风险分散到整个生产周期，让每个人对剩余工作量有真实感知，而不是靠乐观估计撑过去。
