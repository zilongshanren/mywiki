# 好软件不反复自检

Boris The Brave 在与 agent 辅助编程共事一段时间后，总结出一类「agent 专属的代码气味 (code smell)」。最典型的一种叫做**过度防御式编程**：agent 喜欢在每个函数入口堆砌大量形如 `if 'config' in settings and 'height' in settings['config'] and isinstance(...)` 的检查。

## 为什么 agent 倾向这样写

Boris 归因于强化学习奖励结构——代码跑通就有奖励，**冗长不扣分**、可读性也不扣分。于是 agent 快速学到「多加检查更容易过关」。这属于工程味道上的失败，但在训练目标上是理性的。

## 为什么「看起来稳健」其实更脆

这类检查并不提高真实鲁棒性，只是把错误信息变得更漂亮。危害在于**它们是对假设的重复声明**，而不是对假设的**一次性确立**：

- 当代码演化，A 处的检查说「height 是 int」、B 处的假设说「height 可选」，两处会逐渐漂移；
- 真正的错误会在栈中部某个随机函数里炸出来——不是检查失败那处；
- 和 [[data-structure-invariants]] 的思路相反：不变量应当在**一处建立并文档化/类型化**，其他地方信任它。

Boris 把这种模式类比为代码版本的 **TOCTOU (time-of-check to time-of-use)**：任何事实被重复依赖超过一次，就给漂移留了口子。

## 与之相关的坏味道

Boris 列出几条同源气味：

- ad-hoc 类型校验（本应靠静态类型）；
- 把会失败的函数包一层 try/catch 或 retry（让失败变静默）；
- 检查「设计上就是不变量」的状态；
- 反复解析字符串、写残留的 `case`、只为「记一下然后重新抛」而 catch；
- **multiplicative retry**：上下游都各自带 3 次重试，深层调用会乘成 27 次——故障诊断被严重延迟。

## 替代姿势

Boris 自己的工作方式是把**静态类型**用得更严，让读者（以及 agent）能信任程序处于某个已知状态，多余检查就显得冗余。更一般地：

- 把假设升级为文档化的/由类型系统强制的**不变量**；
- 一旦确立，后续代码**不再重复检查**；
- 只在真正会越过信任边界（外部输入、跨进程/跨网络、反序列化入口）时校验一次。

这和 [[type-safety-vs-simplicity]] 是一体两面：把复杂度推给类型系统与接口契约，函数体里才能简单起来。对 agent 时代的工程实践而言，识别这种新型气味、并在 prompt 或 lint 规则里压制它，可能比「让 agent 写更多代码」更关键——Boris 自己把这个称作「新的一组鼻子受体」。
