# C++ 多范式与团队纪律

C++ 把过程式 C、面向对象、模板元编程、RAII、STL 算法/迭代器这几个互相之间并不天然兼容的范式糅在了同一门语言里。Scott Meyers 在 _Effective C++ 3rd Edition_ 的开篇 Item 1 里把这件事点明了：**View C++ as a federation of languages**——把它当成一个语言联邦，而不是一门统一的语言。[[cloudwu]] 在 2010 年为 _Effective C++ 3rd_ 中文版写评注时，对这一点做了大段补充，本页归纳他的论点。

## "无人能掌握 C++ 的所有枝节"

这并非夸张，也不是藐视读者。C++ 一直在长，长出了**连它的发明人一开始都没意识到能量的特性**——`template` 在云风学的第一个 C++ 编译器（Turbo C++ 1.0）里只是一个保留但未实现的关键字，几年后却成了 STL 的基石。Effective C++ 第二版没有 Item 1 这一篇；到了第三版，作者把"C++ 不是绝对意义上的 C++"放在了第一条，并且全书行文从"必须怎样做"变成"温和地承认无奈"。这本身就是 C++ 演化压力的注脚。

## 各部分的差异性大于共性

云风的核心论断："C++ 各个不同的方面的差异性要远大于它们的共性。" C++ 试图同时满足各种项目、各种人在各种时期的不同需求，**不是在一开始经过深思熟虑定义出来的**。在工程实践中，这意味着：你不能把 C++ 当一门统一的语言来用——必须先在团队内**定义你们要用 C++ 的哪个子集**，并且所有人都认同这个定义，才有可能长时间把项目做下去。

## 规范本身比规范的具体内容更重要

> 有规范、且大家一起遵守之，比到底规范了些什么重要得多。

云风以 Google C++ Style Guide 为例：它的具体条款（不要异常、不要 RTTI、对继承的限制、命名约定）在外人看来未必"对"，但 Google 内部有非常一致的写法，新人能很快读懂老代码。这个一致性本身才是产出价值的根源。这条经验对任何 [[modular-design|模块化设计]] 与 [[cognitive-load|认知负担管理]] 都成立——风格一致 → 阅读成本低 → 重构与代码评审更便宜。

## "C 的 C++ 子集"作为一种合法选择

在 2005-2006 年间，云风曾在团队内推广过"类 C 的 C++ 子集"做开发：用 C++ 的改进（更严格的类型检查、`const`、`bool`、引用、`new/delete`）弥补 C 的痛点，但**避开继承、避开模板元、避开异常**。这套写法和他更早期写的"标准 OO 风格 C++"完全不同，但在工程上工作良好。这段经历最终把他带去了完全的 C 开发——成为后来 skynet / ejoy2d 选 C 而非 C++ 的潜在原因。本条在 [[classitis|classitis]] 与 [[shallow-modules|浅模块]] 的语境里都是同一组症状的另一种处方。

## 警惕"创新的快感"

C++ 允许你把不同范式揉在一起、每种都享受高性能支持——这种"取各家之所长"的感觉很容易带来快感，**但其引起的冲突和复杂性，可以轻易超过个人能控制的范畴**。云风的提醒是直白的：

- 仅仅是语言学习、没有长年的工程经验沉淀，是很难有切身体会的；
- C++ 程序员往往聪明，这反而是危险所在——他们倾向于"为了用 C++ 而用 C++"，而不是为了解决问题。

这与 [[strategic-programming|战略式编程]] vs [[tactical-programming|战术式编程]] 的张力同源：能写出复杂解法不代表应该写出复杂解法。

## 项目长期化的隐藏前提

即便你是一个人写整个项目，你也要和**别人写的代码**打交道——至少是标准库，可能还有第三方库、可能还要给别人提供扩展点。这意味着即便没有团队，也无法"随心所欲地用 C++ 中看起来最酷的特性"，否则项目会逐渐偏离最初目标，**编写 C++ 代码只是为了用 C++ 编写，而非为了解决问题**。这是云风对 Item 1 的最终注解，也是这一段评注最有重量的一句话。
