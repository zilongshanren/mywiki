# C 结构序列化：自描述元信息与环图合并

C 和 C++ 缺乏运行期类型元信息，所以没有一个像 Java/.NET 那样被广泛接受的"标准序列化"方案。MFC 那一套已经二十年了，Boost.serialization 用高级 template 换来"非侵入"的表面漂亮，但调试真实类型时的代价不小。protobuf 又不符合云风这种"我要合并重复值、处理任意图结构"的需求。

他 2010 年给引擎重写资源管理时，顺手摸索出了一套纯 C 的思路：**自己发明一套小型的结构描述语言**，用一个小工具生成元数据头文件，运行期拿着这些元数据去驱动一个 500 行的序列化库。本页记录这个方案的要点。

## 数据只有两种

有了元信息之后，一个结构字段只分两类：

- **值类型（value）**：定长 POD，按字节拷贝即可；只需要知道字段的尺寸。
- **引用类型（reference）**：内存里是指针，序列化结果中是"相对数据块的偏移量"。云风用 **base 1**（偏移量从 1 起算），这样 0 就可以保留给空指针。

引用再细分为：

- **外引用**：指向不需要被序列化的资源（如文件句柄、窗口句柄）。库把它翻译成一个 atom（通常是唯一字符串，比如文件名、窗口标题），反序列化时再还原。
- **内引用**：引用的数据类型也在序列化范围内；被引用的数据会作为一个节点加入输出块。

如果所有内引用都处理对了，被序列化的数据块**与内存地址无关**，可以直接写到磁盘或网络上去。

另外一个不大但常见的需求：**变长数组的长度由同一结构中另一个整型字段决定**。这类 trick 用 meta 描述一下即可。

## 要解决的核心问题：合并与环

云风对这套库提了两个硬性需求：

1. **值相同的节点要合并**。相同字符串只存一份；一颗树里值相同的叶子、完全相同的子树也应当合并。
2. **正确处理有向有环图**（循环链表、复杂图）。

但为了多项式时间复杂度，不追求合并"值相同 + 拓扑结构相同"的有环子图——理论上能合，工程上不值。

## 算法演化：从 O(N!) 到单次遍历

**朴素版**（先做对）：不合并，遍历整个图，算每个节点 hash，排序找到完全相同的节点 pair，合并并更新引用，反复迭代直到规模不再缩小。最坏情况 O(N!)，只是用来跑通。

**改进版**（和同事讨论后）：

- 维护两个集合：`原始指针集合` 与 `有效节点 atom 集合`。
- 遍历原图，每个节点先进原始集合（相同指针自动去重），生成带 hash / 长度 / 遍历状态 的临时对象。
- 当一个节点的**所有出边**都处理完了，它可以被 finalize 成一个 atom，加入有效节点集合。此时做一次查询合并：已经有相同内容的 atom 就指向老的，没有就新建。
- 遇到环：说明当前节点指向一个还没处理完的祖先。这种情形下节点直接被转成 atom，不再尝试合并。云风在文末自己做了补丁：这里牺牲了"A 和 D 同构就能合并"的情况，但换来了一次遍历的复杂度和实现简洁，他觉得可以接受。

最后把所有有效节点拼成连续块、修正内部引用偏移即可。

## 工程实现的两点经验

- **局部 arena 堆**：序列化过程中产生了大量零碎临时结构（hash 表、待处理 set、atom 对象），生命期跟这次序列化绑在一起。定义一个专用 arena，从 arena 里分配，结束时整个 arena 一次性清理——否则这些零碎对象的生命期会让你爆炸。和 [[linear-allocator]] 的思路一致。
- **context + longjmp 异常**：大量状态塞进一个 `context` 结构里传递；用户提供的 buffer 空间不够这类深层错误用 `setjmp/longjmp` 从任意深度直接跳出，而不需要每层都做返回值检查。程序反而更简洁。

## 与外部方案的对照

- 和 Boost.serialization 比：后者追求"非侵入"和"现代 C++"美感，这个方案选择**让 C 的结构自描述**——用一个离线工具生成 meta。云风的价值观：苦力堆出来的代码不值得写。
- 和 protobuf 比：protobuf 不处理任意图结构、不做等值合并——不能复用。
- 和 C++ 二进制 dump 比：这个方案处理了循环、合并、32/64 位无关的引用偏移表达，更像一个"可持久化的图存储"。
