# 销毁重建胜过隐藏重置

Ronimo 的 [[joost-van-dongen|Joost van Dongen]] 曾长期用「隐藏 + 重置」来处理角色死亡重生：死时把角色所有可视元素（血条、阴影、本体、特效）隐藏，重生时把所有状态（连击计数、技能冷却、中毒剩余时间）逐一清零。这套方案每加一条新状态就得**同时改隐藏函数和重置函数**，漏掉任何一处都是 bug——而「没重置」这种 bug 比「没隐藏」更隐蔽，因为很多效果在重生倒计时走完前自然超时了，只有少数情况暴露。

同事 Maarten 提的解法很极简：**死时直接 delete 整个对象，重生时重新 new 一个**。没有隐藏、没有重置、没有两张需要同步维护的清单。Joost 把它推广到 Swords & Soldiers 的菜单系统：原来所有菜单在启动时一次性创建后全部 hide、只留当前那张 show，为什么不直接干脆 delete 掉当前不用的菜单？

## 为什么值得

这条原则本质是**消除「两个必须同步但编译器不会帮你查」的清单**。隐藏 + 重置方案里，「创建」、「隐藏」、「重置」三个函数的字段列表必须保持一致；销毁重建方案里只有「构造函数」一处——所有字段的初始状态都通过它定义，不可能漏。这是 Ronimo 编码纪律的缩影：**宁可失一点点性能，也要让类型系统 / 对象生命周期本身禁止整类 bug**。

## 性能反驳与回应

评论区和 Joost 自己都提到动态内存分配有开销：

- 资深 C++ 程序员会说「重置更快」。Joost 同意在多数情况这是对的，但他认为**设计上禁止 bug 比性能更重要**，并且当前主机硬件并不需要为了这几百字节分配斤斤计较。
- 真有性能问题可以用 **placement new**：预先 malloc 一块内存，用 placement new 在它上面反复构造析构，等价于一个极简对象池。
- Ronimo 内部还有自研的「小分配器」，256 字节以下的分配开销极低。
- C# / XNA 评论者补充：在 compact .NET（Xbox 360 XNA / Windows Phone 7）上 delete+new 会制造 GC 压力并引发 mini lag spike，那里**必须用对象池**，而 C# 没有 placement new。
- 另一派观点：即使保留 reset，也可以强制「只有一条初始化路径」——new = alloc + init，reset = hide + init——保证清单只维护一份。两条路都能根治 bug 清单不同步的核心问题。

## 什么时候用

Joost 在评论里收下一条警示：**粒子系统应该用 reset**，因为性能诉求压倒设计简洁；但「角色死亡重生」、「菜单切换」这种低频对象，销毁重建明显更安全。

这条原则和 [[raii|RAII]] 在**精神上**相近——都强调「对象生命周期天然覆盖所有状态」——但并不完全等同：RAII 处理资源获取与释放，这里处理的是「完整状态的隐式重置」。Joost 本人在评论里拒绝了「这就是 RAII」的说法，他认为 RAII 核心是「未初始化的类」，而他的角色在任何时刻都是合法的，只是**状态维度太多以至于很难人肉维护重置清单**。
