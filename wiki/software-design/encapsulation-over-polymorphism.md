# OOP 的 90/10/0 原则：封装、多态、继承

[[ben-supnik|Supnik]] 在 2010 年的 *What OOP Isn't* 里给初学者一条粗暴但可操作的相对重要性估计：**封装 90%、多态 10%、继承 0%**。这个比例未必严格成立——他自己也在评论区承认在「继承是多态的实现机制」的 C++/Java 语境里给继承打 0 分太过分——但**方向本身是正确的**：大型软件里真正给你带来价值的是「避免模块之间相互污染」，而不是类层次的美学。

## 为什么是封装

封装给每块代码画一圈围墙——外面看不到里面的细节，里面不用考虑外面的变化。这个属性在单人原型里几乎没感觉，但**项目一旦跨越一个阈值（多开发者、多月维护、多层改动）**，它就是唯一能让复杂度不爆炸的东西。这正是本科教学里很难讲明白的点：学生从来没写过大到「封装开始救命」的代码，看到的只有「多写一层模板代码的代价」。

封装本身不需要继承也不需要运行时多态。C 的不透明指针、Lua 的闭包、Rust 的 module system，都是没有 OO 语法糖的封装——参见 [[c-opaque-struct-modules]]、[[information-hiding]]。OO 的独特价值是把封装的**工具**打包成开箱即用的语法，让你少写样板、少按几次 Ctrl-V。

## 多态为什么只排第二

Supnik 的产品谱里给出了经验数据：WorldEditor（LR 的开源场景编辑器）里多态层次几乎无处不在——UI 组件、文档项、工具——而 X-Plane 本身却**几乎没有多态类层次**。结论是「多态性」是**问题域属性而非架构意愿**：有些领域天然要求同构接口（GUI、文件格式解析器、数据库驱动），有些则根本不需要。对不需要的领域硬套多态，会得到一堆只有一个实现的抽象类，这是 [[false-abstraction|假抽象]]。

另一条：一旦你有了多态接口，你实际上就拿到了封装——接口是封装的载体。但反过来不成立：很多封装是一次性的（单模块内部的实现隐藏），没有多态意义。所以封装的价值覆盖面远大于多态。

## 继承的真正问题

Supnik 更早的博文 *Inheritance of Implementation is Evil* 把话说得更狠。他在评论里把该立场细化成三条：

1. **接口继承** 没问题——这是 Java `interface` 的用法，近似于「多态接口的声明机制」。
2. **实现继承** 往往比组合更难管理——因为派生类与基类的耦合穿过多层调用、贯穿整个生命周期。
3. **实现继承并不必然提升复用**——大多数场景组合一样能做到复用。

他给的决策启发非常工程化：**取决于重构预期**。如果你要一次性铺 50 个 UI 类，基类 template-method 控制骨架、派生类填空是正确的；如果你要慢慢铺十个月、每次加一个独立组件，组合更轻，类层次反而绑手绑脚。

评论区里 LogicalError 的补充被 Supnik 认同并放大：**不要为还没写的代码做预设计**。你只有在成为某个问题的专家之后才写得出那个问题的好抽象——而「还没写」往往就意味着「还不是专家」。这条和 [[strategic-programming]] 的「先写能跑的，再提炼抽象」同源，也是 Carmack 反复讲的「先具体、再泛化」。

## OOP = 封装 + 少量多态 + 语法糖

Supnik 对 (OOP − hype) 的最终定义是：**语言层面为「封装与偶尔的多态接口」提供的语法糖**。他承认这对他有用——否则他得用 C 写更多重复的样板，RSI 会更严重。但他拒绝把 OOP 当成「救世方法论」：OOP 不会让你写得更快、bug 更少、或者把坏程序员变好。坏程序员在任何范式下都有办法写出坏代码——这是 [[experience-as-noise-filter]] 的反面写照。

## 与社群讨论的对位

评论区里有三条值得记的立场：

- **David**：「某些问题天然需要实现继承」，用「抽象数据库类」做例子——一套定义好的接口，实现之间只差底层细节。Supnik 不反对，只是强调这恰是「一次铺完 N 个派生类」的场景，正中实现继承的甜区。
- **LogicalError**：从「相信 OOP」到「相信最小 OOP」再到「倾向数据导向 + 写当下够用的代码」。这条轨迹在 2010 年之后十年成为游戏引擎社区主流——见 [[tactical-programming]]、[[now-principle-productivity]]。
- **Paul W. Homer**：「以前学的是 ADT（抽象数据类型），OOP 只是把数据和代码绑在了一起」；他现在「顶层 OOP、底层合并」——上层类结构能看出清晰的抽象，下层对象收拢到父对象里避免 Smalltalk 式的爆炸。这条路径本质上是 [[deep-modules]]。
