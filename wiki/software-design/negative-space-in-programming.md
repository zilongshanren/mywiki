# 编程中的「负空间」

视觉艺术里，负空间指主体之外被留空、反过来定义主体轮廓的那部分区域。[[fabian-giesen|ryg]] 把这个概念借来描述**程序设计中「没有被写进去」的部分**——被拒绝的替代方案、被砍掉的特性、因为很难在文档里解释清楚而被修改过的 API、因为不变量设计得好而根本用不到的测试，以及因为某类错误被设计上杜绝所以不需要的校验。他的主张很朴素：**一个程序真正的形状是由你选择不做什么决定的，而不是由你做了什么决定的。**

## 做 vs 不做

教材和博客铺天盖地讲「如何设计、写、文档、构建、测试代码」，几乎没人谈「我考虑过但拒绝了什么」「我为什么删掉了这个特性」。而资深工程师的经验通常正好是：优雅的程序不是勾选了 feature list 上所有条目的那个，而是**解决了目标问题然后几乎什么都不多做**的那个。quality = 它恰好做对了要做的事 + 它几乎不做别的事。

## 两个可操作的建议

ryg 给出两条具体、不浮夸的建议：

1. **把失败写下来**。当你「随手加一个小特性」结果几天后发现推不动、只能回滚时——花几分钟把尝试过什么、为什么没走通写清楚。和代码相关的写进注释，和架构相关的写进 Wiki 或内部邮件。这是一道把「这里有堵墙」变成集体知识的护栏。否则每个新人都会再撞一次，直到撞出血为止。这和 [[continuous-design]] / [[strategic-programming]] 讲「主动让系统演化得更健康」的精神是一致的。
2. **改写代码 ≠ 替换 X 行写 Y 行**。重写遇到的最大麻烦永远是**周围那些没被说出口的假设**：某些 API 没被调用是因为它们差一点点不对路；某些未定义行为的副作用被别的模块依赖；某些问题根本没出现，是因为当初的数据结构就把它排除在外了。你不是在重新实现算法，你是在继承一整套**设计决策的负空间**，这恰恰是看代码最看不见的那一层。

## 和其他话题的连线

- 和 [[data-structure-invariants]] 同源：好的不变量让一大类 bug **根本没法被写出来**——这本身就是典型的负空间。
- 和 [[shallow-modules]] / [[false-abstraction]] 互补：浅模块之所以坏，是因为它们把被刻意隐藏的复杂度重新暴露了出来，负空间被打穿。
- 对低层渲染代码尤其明显：ryg 自己写的是 Iggy 2D UI，所有的优化最后都归约成「别做任何多余的事」——把渲染命令流翻译成 GPU 命令缓冲区，能有多少 `memcpy` 就多少 `memcpy`。「如果你做对了，什么花哨的东西都不会发生」——这是优化哲学的一种阴面。
- 和 [[zero-tolerance|零容忍]] 的调试文化是同一种美德的两面：前者要求你在问题被察觉的瞬间立刻修，后者要求你在代码被写下之前就先设计好「哪些错误根本不可能发生」。

## 重写代码之前问三个问题

把 ryg 的经验固化下来：

1. 现有代码**没有**调用哪些明显的 API？它是在绕开什么？
2. 它**没有**处理哪些 case？是因为这些 case 上层已经排除，还是因为它赌这些 case 不会出现？
3. 它**没有**的那条依赖、那条特性、那次重构——背后是什么设计决策？

这些问题的答案都是负空间，都是搜索代码搜不出来、但是会在你重写完两周后爆炸的东西。
