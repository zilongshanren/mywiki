# ID 索引 + 销毁标记：替代引用计数的对象生命期模式

[[cloudwu]] 在重写 skynet 2.0 时，把自己过去零散用过的一个生命期管理手法固化成了一个模式——它解决的是 **RAII / 引用计数的"销毁时机不可控"之痛**，尤其是在并发环境下。

## 常规 refcount 的问题

C++ 智能指针和所有非 GC 语言框架都用引用计数：创建时 1，每次引用 +1，释放 -1，归零就销毁。

这套机制有两条深坑：

1. **销毁时机被最后一个持有者决定**，设计系统的人无法明确说"我现在就要销毁"。对象可能在你完全想不到的线程、完全想不到的时机被释放，甚至引发 dtor 链式连锁。
2. **到处 +1/-1 的累积开销不小**。实际上大多数引用传递是"模块内部函数调用"这种明显不需要计数的场合。这也是为什么多数 GC 语言选择了 mark-sweep 而不是引用计数——不是 refcount 算法本身贵，是"随处都做"的模式本身有问题。

于是常见的"优化"是在函数内部局部使用裸指针，只在模块边界处维护 smart pointer。但 C/C++ 里"模块边界"根本没法硬性约束，只要有一处疏漏就是 bug。

## 第一层：用 id 替代指针做长期持有

第一步是规约**长期持有 = id**。所有需要长期保留对象引用的地方，存的都是一个 id（整数），通过全局 hash 表换成指针。这和 [[handle-based-resource-manager]] 的精神一致，但用法稍不同：handle-based 强调"所有操作都通过句柄 + manager"，云风这里强调"**长期**持有才用 id，临时使用仍可拿裸指针"。

核心效果：**传递 id 没有任何开销**，也没有加减引用的需要；唯一的成本是"id → 指针"这一步的查表，而这一步强制使用者处理"索引失败"（对象已销毁）这一情况——把错误路径推到它应该被处理的地方。

## 第二层：销毁标记

在全局 hash 表里，每个对象除了一个引用计数，再挂一个**销毁标记**。标记一次性、不可翻转。

- 想销毁对象：直接 set 销毁标记；然后检查引用计数；只有 refcount 为 0 时才真正进入销毁流程。
- 想使用对象：用 id 查 hash 表 → 拿到指针同时 refcount+1 → 用完 refcount-1。
- **一旦销毁标记被 set，所有从 id → 指针的查表都会失败**，不再有人能增加 refcount。于是 refcount 单调递减，对象必然在可预期的时间内被销毁。

关键转变：语义从"所有人都不用了才销毁"变成了"**我决定销毁，但等当下正在用的流程结束**"。销毁时机由设计者主动决定，并发里正在执行的短期操作不会被打断。

## 单线程创建销毁的额外收益

云风加了一条约束：**所有对象的创建和销毁都只在同一线程完成**。这天生吻合 actor 模型——actor 对象本来就该只由"actor 注册表"这一个主控线程增删。

有了这条约束，底层的 id→pointer hash 表可以用最简单的读写锁实现：查表是最常见的、加读锁即可；增删是罕见的、加写锁即可；而写锁从不并发（因为只有一个 writer），对 CPU/cache 都友好。更进一步还有一个技巧：**增删前把 hash 表整份复制一份，在副本上慢慢改，最后一步用写锁 swap 指针**——因为 writer 只有一个，这种 copy-on-write 式的切换毫无竞争成本，reader 在切换前后各自拿到一致快照。

## 和引用计数的本质差别

表面上依然有一个 refcount，但它服务的目标完全不同：

- 传统 refcount：**判断对象是否还活着**。
- 云风模式下的 refcount：**只用来保护"销毁标记被 set 后、当前正在执行的短期使用不被打断"**。长期持有完全交给 id。

这也契合他对并发的基本看法：**长期状态归 id，短期状态归本地操作**。两套机制分离，各自责任单一。
