# C 位运算符优先级为什么是今天这个样子：B/BCPL 的历史包袱

在 C/C++ 里写这样的代码一定会被编译器偷偷坑到：

```c
if (value & mask == flag)    // 不是你想的那个语义
```

因为 `==` 优先级高于 `&`，实际上被解析成 `value & (mask == flag)`——`mask == flag` 先算成 0/1，再和 `value` 做位与。想要按"先 mask 再比较"的顺序，必须显式写 `(value & mask) == flag`。

直觉上 `&` 是位运算，应该**优先级高于比较**才对——毕竟表达式"提取位然后判相等"在 C 里几乎是最常见的用法。**但 `&` 被放在比较之下**。Dennis Ritchie 在他写的 C 历史一文里亲自解释过为什么。

## B / BCPL：单个 `&` 同时承担位与和逻辑与

C 的前身 B（以及 B 的前身 BCPL）里没有今天这个 `&` / `&&` 的区分——**只有一个 `&`**。它在不同上下文里做两件事：

- **普通表达式里**：按位与；`flag = ptr & 1;` 提取低位。
- **`if` / `while` 条件里**：短路逻辑与；`if (ptr & ptr->value)` 能安全地先判空再解引用，因为第二个操作数不会在第一个为假时求值。

为了让 `if (ptr & ptr->value)` 写法自然，B/BCPL 必须把 `&` 的优先级**放在比较之下**——因为真实代码里的合法形式是 `if (a == 0 & b == 0)` 这种「两个布尔结果做逻辑合取」，而不是 `if ((a == 0) & b) == 0`。换句话说，**B 里的 `&` 是按逻辑 AND 的优先级来定位的**。

## Ritchie 的两选一

C 从 B 拆出来时，Ritchie 做了一件「罕见的偏向理智」的选择：**把 `&` 拆成两个不同的 token**——`&` 永远是位与、永远两边都求值；`&&` 永远是逻辑与、永远短路。`|` / `||` 同理。

但此时他面临一个现实约束：**B 和早期 C 共享同一批用户代码**，这些代码里大量的 `x & mask` 已经按照 B 的旧优先级写好了。如果在拆 token 的同时**把 `&` 的优先级也抬高到比较之上**——数学意义上更自然，和 `+`、`-`、`*` 同属"算术/位运算"档次——**那所有这些老代码的语义都会静默改变**，而且这种改变还非常难检测（表达式都能通过类型检查，只是值错了）。

所以 Ritchie 选了"保住旧代码不变"：**`&` / `|` 的优先级原地不动**，继续和逻辑操作挨着。代价就是今天每个 C 程序员都要记的坑：位操作表达式里要**手动加括号**。

## 类似的坑

`<<` 和 `+`：`1 << 2 + 3 == 1 << 5 == 32`，因为 `+` 优先级高于 `<<`。典型踩坑是 `1 << bits - 1` 被解析成 `1 << (bits - 1)`——这个意外地是你**想要的**语义，但靠的是"巧合"不是设计。反过来 `1 << position | other_flags`（构造 bit field）就自然工作了，因为 `<<` 高于 `|`。

## 记法：几组还算可用的粗糙分层

即便被历史搞得有点乱，C 的优先级里还是能找到几条合理的大分层：

1. **一元 before 二元**：`*p++`、`-a[i]` 都按预期工作；
2. **算术 before 比较**：`a + 1 == b` 按"先算后比"工作；
3. **比较 before 控制流式的 `&&` / `||`**：`a == 1 && b == 2` 按预期工作；
4. **赋值最低**：`x = a == b` 是 `x = (a == b)`。

**按位运算**只在"构造 bit field"（用 `<<` 和 `|` 组合常量）这一类场景下才跟分层匹配；**在"提取位后和常量比较"这类场景下永远要手动加括号**——这条规则如果只能记一句，就是它。
