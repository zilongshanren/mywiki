# C++11 精选特性（游戏引擎视角）

C++11 在 2013 年前后通过 Visual Studio 2012/2013 进入游戏引擎开发主流。与其将 C++11 视为一次全面升级，[[angelo-pesce]] 的建议是把它当作一份食谱：只挑对当前项目有净收益的特性，忽略那些增加语言复杂度却没有对等简化的部分。

这种态度与 [[orthodox-cpp]]（C+）一脉相承：核心判断是 C++ 的根本问题来自语言规则数量和质量，而不是缺少某个特定功能。C++11 补充了功能清单，但并未削减规则——事实上它还增加了规则（构造函数重载决议的新路径、rvalue references 的重叠语义等）。

## 值得立即用的特性

**`auto` 类型推断**是列表里净收益最高的特性。它不只是缩写——类型推断意味着隐式转换必须显式写出，如果你改变了一个函数的返回类型，下游的 `auto` 局部变量不需要手动同步修改。对 STL 迭代器和 lambda 尤其明显。

**Lambda 表达式**是对函数指针的实质性改进：支持闭包捕获，且捕获语法（`[=]`、`[&]`、显式列表）是显式的，强迫程序员在写 lambda 时就思考生命周期和所有权，这比 C++ 其他大多数特性更诚实。无捕获的 lambda 可以隐式转换为函数指针，方便与旧 API 互操作。其底层是栈上的无类型对象，用 `auto` 持有可以避免转换到 `std::function<>` 的开销。

**Type traits + `static_assert`** 的组合实现了编译期类型约束：例如"这个类型必须是 POD 才能 memset"可以从注释变成断言。Boost 里已经有了 type traits，但标准化降低了依赖和兼容顾虑。

**Range-based for** 减少样板，与其他现代语言对齐。`override`/`final` 为虚函数重写提供编译期验证，消灭了「以为重写了实际签名不符」的静默 bug。

## 需要审慎的特性

**Rvalue references** 生成了大量讨论，但对游戏引擎代码的实际价值有限。游戏引擎的最佳实践本已是：避免大对象、避免意外拷贝、不在构造函数里做重工作。在这个前提下，move semantics 能解决的问题已经基本不存在了。其规则复杂度（尤其是与 `auto` 的交互，universal references 等）与收益不成比例。在 STL 层面移动语义确实有意义，但如果你本来就不大量使用 STL，这部分收益也随之消失。

**Variadic templates** 解决的是"通用参数包转发"这类库级问题（`std::tuple`、`std::make_shared` 等），在业务代码里几乎找不到合理使用场景。语法本身（三种不同位置的 `...`）的晦涩程度是一个明确信号。

## C++11 的根本局限

C++11 的设计决策暴露了其政治性：**它没有废弃任何东西**（除了少数边角如 `auto_ptr`），只是堆砌新特性，同时寄希望于程序员自觉记住「以后应该用新方式」。在一个大型团队里，这意味着同一个概念现在有三四种写法，而编译器只能对少数情况给出有意义的错误信息。Template concepts——唯一能让模板错误信息变得可读的特性——被推迟到 C++20 才入标准，这本身就说明了委员会的优先级。

对实时渲染/游戏引擎这类高性能场景，标准库的新增（并发、智能指针、容器）仍然达不到需求：没有 `fixed_vector`（栈分配定长容器）、没有 job system（只有线程）、没有 SIMD 支持。工作室自建的版本在这些场景仍然更合适。
