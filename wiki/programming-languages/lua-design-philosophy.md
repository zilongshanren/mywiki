# Lua 的设计哲学（Roberto / Luiz 访谈）

Lua 由 Roberto Ierusalimschy、Luiz Henrique de Figueiredo 与 Waldemar Celes 于 1993 年在巴西里约的 PUC-Rio 创建，是迄今唯一一门由发展中国家创立、被全球广泛采用、并被 ACM HOPL 重点推介的编程语言。这门语言在《魔兽世界》、《孤岛危机》、Adobe Lightroom、Wireshark 等截然不同的宿主里都能毫无违和地寄居，背后并不是什么巧合，而是一整套被两位作者反复谈及的设计准则。[[cloudwu]] 在 2010 年校译《Masterminds of Programming》第七章时，把这套准则的中文表达打磨到位，本页据此整理。

## "脚本语言"是给宿主当胶水的

Roberto 反复强调：当下大多数人把"脚本语言"误用为"动态语言"的同义词，连 Erlang、Scheme 都被这么叫。但在 Lua 团队的原始用词里，**脚本语言指那种用来粘合、控制其它语言所写组件的语言**。Lua 的全部设计都围绕这个定位展开——它不打算自己成为一门独立写大型应用的语言，而是要钻进别人写好的 C/C++ 框架里，作为可热改、可沙箱化、可暂停可恢复的"软上层"。这与 [[lua-cpp-binding]] 一类手写绑定文里反复出现的"脚本管快速改动、原生管快速运行"的分工是同一句话。

## 经济学：每个特性都太贵

Lua 团队评估新特性时的第一问永远是 "它的成本有多大"。Roberto 说："几乎所有的特性，相对于它们能带给语言的东西来说，都成本太高。" 一个简单的 `continue` 语句都没能通过他们的标准。值得加进语言的特性，需要满足两条经验法则：一是它能让设计者自己感到"惊喜"——也就是说，它的用处超出了最初动机；二是它的受益面足够宽。`for` 循环和弱表都是这样被加进去的，而前者的最终形态是 Roberto 在想到"用闭包做生成器函数"以后才解锁的——`for` 之所以可以通用而紧凑，正是因为闭包替它保留了循环之间的内部状态。

## 机制而非法策（Mechanism, not policy）

Lua 不内置类、不内置面向对象，而是给出 metatable / metamethod 这套机制，让用户在上面"自己长出"OO。Roberto 直言："这保证语言简洁，但用户必须提供自己的法策。"代价是 Lua 写出来的代码在不同的应用里风格分裂——WoW 的 Lua、Lightroom 的 Lua、Wireshark 的 Lua 各有内部文化，库很难跨项目复用。但 Lua 把这视为可接受的代价：他们要的是嵌入到坚固宿主里的灵活内核，不是要造一门"世界上最流行的语言"。这种 DIY 美学对 [[c-interface-oop]] 和 [[c-opaque-struct-modules]] 这类"在没有 OO 的语言里手搓 OO"的实践有强烈的同源性。

## table 作为唯一的聚合结构

为什么所有数据都是 table？Roberto 的灵感来自形式化方法 VDM——VDM 把数据聚合分为 set / sequence / map 三类，但 set 和 sequence 都能由 map 表达，于是干脆只留 map。Luiz 的理由更直白：他喜欢 AWK 的关联数组。这条统一让整个语言的元能力（metamethod、模块、原型链 OO、命名空间）都能挂到同一种结构上，配合 first-class 函数与 [[closure|闭包]]，就能用极小的核心拼出极大的表达力。

## 协程（asymmetric coroutine）作为并发观

两位作者明确说 "我们不信任基于抢占式内存共享的多线程"，并引用了 HOPL 论文里的话："如果连 `a=a+1` 都没有确定结果，无人能写出正确的程序"。Lua 给出的方案是去掉抢占（用协程），或者去掉共享（每个 OS 线程持有独立 `lua_State`）。Lua 选择的是**非对称协程**：通过 `coroutine.create` 显式创建，`resume` 启动，`yield` 显式让出。它和 Python 生成器最大的区别是 Lua 协程**可以在任意嵌套调用里 yield**，因此每个协程必须有独立堆栈——这"有栈协程"比"扁平生成器"强大到可以构造一次性延续点（one-shot continuation）。这套模型是后来 skynet 那种 actor/coroutine 服务器框架的语言基础。

## 垃圾回收而非引用计数

Lua 从第一天起就用 GC。Roberto 的判断是：解释型语言通常已经有自描述数据（带 tag 的值），写一个 mark-and-sweep 极其简单，对解释器其余部分几乎零侵入。引用计数对无类型语言反而是重负担——没有静态类型，每次赋值都得动态检查新值旧值并改计数；他们试过，性能没提升。这一段对所有想用引用计数取代 [[garbage-collector]] 的语言实现者都是一记冷水。

## 可移植性高于一切的 ANSI C 实现

Lua 的实现一直死守 ANSI C89。这条决定的后果是 Lua 跑遍了机器人、打印机固件、网络路由器、嵌入式 8/16 位平台——这些都不是作者们最初瞄准的目标。被问到要不要换用更现代的语言或 C99 时，Roberto 的回答是："ANSI C 是我目前知道的可移植性最好的语言。" Luiz 补充："我们仍未感觉到有必要转移到 C99。" 团队甚至考虑过调整 C 结构体里字段顺序、为了节省几个字节。这种近乎偏执的资源经济学，是 Lua 能寄居在如此广谱宿主中的根因。

## 基于寄存器的 VM 与手写 parser

Lua 5.0 起改用了基于寄存器的 VM——选择寄存器架构是为了"避免所有的 getlocal / setlocal 指令"，倾向于用更少操作码、每个操作码做更多事，从而减轻 dispatch loop 的压力。同时 Lua 的扫描器和语法分析器都是手写的递归下降，从 lex/yacc 切到手写并不是为了追性能，而是因为 yacc 生成代码可移植性差、不可重入、错误信息差，并且自顶向下分析器对"边解析边生成代码"和"继承属性"更友好。Roberto 也坦承，**他不会向语法尚未稳定的语言推荐手写 parser**——LR(1) 比 LL(1) 强大太多。

## 给所有语言设计者的话

- 实现的简单性优先；速度与正确性会随之而来（Luiz）
- 永远把硬件资源当成有限的，因为它们本来就是有限的；一切程序都会膨胀直到耗尽资源（Roberto）
- 注释只是写给"以后回来重写这段"的便签——清晰的代码比加了注释的代码更可读
- Lua 的核心心智模型是：**面向无人——也包括你自己——意想不到的部署环境而设计**。"它能不能跑在微波炉上？"是他们内部的真笑话。
