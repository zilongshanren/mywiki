# 变步长下的时间步长平滑（Time Step Smoothing）

[[niklas-frykholm|Niklas Frykholm]] 在 2010 年 Bitsquid Blog 上的一篇短文，专治一个容易被忽视的事实：**用"上一帧的耗时"当作"本帧要推进多少时间"，看上去直觉，其实不对**。

## 为什么变步长不能直接用 `dt = elapsed_time()`

标准的变步长循环是：

```
float dt = elapsed_time();
update_game(dt);
```

每帧量一下上一帧多长，就用这个时间推进游戏时钟。常速运动的物体在"帧起点时间 × 位置"这张图上画出来是一条直线，看上去没问题。

但这张图掩盖了一件事：**图里的 x 轴是"我们开始模拟这一帧的时刻"，不是"这一帧被画到屏幕上的时刻"**。每一帧从开始模拟到真正送显，有一段 latency，这段 latency 的抖动才是 `elapsed_time()` 变化的来源。把每个点按 latency 偏移到"玩家真正看见它的时刻"上重画，直线就变成了锯齿——**玩家眼里的运动是抖的**。

理想办法是预测"下一帧要花多久"并用这个预测值推进。但完美预测不可能，所以时间步长滤波的目标之一是：**给出一个比"原始上一帧耗时"更好的下帧预测**。

## Bitsquid 默认策略

简单但经过工程打磨的四步：

1. 记录最近 **11 帧** 的 `dt`；
2. **丢掉两个最高、两个最低** 的离群值；
3. 对剩下的 **7 个** 取均值；
4. **把上一帧 dt 向这个均值 lerp** 过去，再加一层平滑。

丢离群值是为了应对 PC 上的"毛刺帧"（OS 抢占、驱动抖动）——如果简单取均值，一次毛刺会污染接下来好几帧。

## 第二个目标：不让步长大幅震荡

帧率里常见的锯齿模式（一帧短一帧长地交替），诱惑你去拟合这种偶/奇帧差异。Niklas 明确反对：

- 锯齿往往是**引擎内部或驱动**的 bug，该修的是 bug 而不是去适应它；
- 游戏逻辑对**剧烈震荡的步长**反应不好。很多跟随摄像机、弹簧阻尼、插值类代码一旦步长忽大忽小，自己就开始抖。

所以除了"预测得更准"之外，滤波的第二条目标是：**让步长**本身**在帧间保持相对稳定**。

## 时间欠账（time debt）

平滑后的步长与真实墙上时钟会漂移。对联网对战等要求严格同步的场景，需要累积一个 **time debt**：

```
debt += actual_time_elapsed - time_step_taken;
time_step_to_take += f * debt;     // f 比如 0.1，小口还债
```

多付的时间在未来若干帧里慢慢补回去，既保持平滑又不至于长期脱锚。

## Bitsquid 的政策是"没有默认政策"

引擎不规定必须用定步长还是变步长。Bitsquid 把 `set_time_step_policy()` 暴露给上层，变步长/定步长/平滑/不平滑都可选——因为"步长要不要平滑、平滑到什么程度"是**游戏感**的范畴，不是渲染的范畴，应由游戏本身决定。

## 一个反例：God of War 3

评论区 GoW3 的工程师贡献了一个相反的数据点：他们**故意**用未滤波的 CPU 帧耗时做动画步长推进，在三缓冲 + VSync 的 zig-zag 场景里反而比均值滤波主观感觉更顺。原因大致是："误差的随机分布"在他们那套 PPU/SPU/RSX 松散同步的 pipeline 上，比"一个平滑预测值"更能掩盖 GPU 呈现时刻的锯齿。Niklas 的回应很诚实：**"平滑"与"跳变"最终是靠人玩过来感觉的，没有可量化的最优**。

## 一个作者的自白

Niklas 在评论里补了一句，特别值得记下来：

> 这篇文章基本是事后合理化。我先注意到游戏加了点 step smoothing 后手感更好，然后才坐下来想为什么会这样。

——工程经验往往先于理论解释。
