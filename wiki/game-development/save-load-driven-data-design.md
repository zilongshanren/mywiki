# 以持久化驱动数据模型设计

[[cloudwu]] 在自研游戏架构的梳理中反复强调一个优先级：**认真设计存档/读档，比你想的要早得多**。它不仅是一个功能，而是一种**倒逼数据模型清晰化的设计工具**。

## 为什么要早

"存档"这件事看起来只是"把当前状态写入磁盘，再读回来还原"。但一旦你要**认真**写它，你会立刻面对一连串必须明确回答的问题：

- 场景里所有对象都要存吗？哪些是派生的、不需要存的？
- 对象之间的引用关系怎么序列化？是存指针、存 id，还是存路径？
- Actor 的运行时状态要存多少？全存吗？存到哪一步？
- 加载时依赖顺序是什么——先建 Object 还是先建 Actor？

回答这些问题的过程，其实就是在**强迫你把数据模型本身设计清楚**。什么是"数据"（必须保留）、什么是"运行时派生状态"（可以丢弃）、什么是"纯表现"（根本不该进数据模型）——持久化方案会逼你在三者之间画出硬边界。

反过来，后续任何修改数据模型的动作，如果同时考虑"不破坏存档"，都会变得更谨慎——不会随手加一个字段、不会随手塞一层隐式依赖。

## 两个重要的分离

### 1. 运行时表示 vs 持久表示

云风明确反对"把 Object 和 Actor 的内存结构直接序列化"。运行时结构往往为了性能做复杂设计——hash 表索引、指针网络、缓存字段。持久存储应该是**"还原对象所需的最小构造参数列表"**，加载时按参数重新构造运行时结构。

例子：订单系统运行时是 "id → 订单" 的 hash 表（方便查询），持久化时只存一个顺序数组（方便加载与版本兼容）。两种表示各有各的合理性，硬要统一反而两头都难看。

### 2. Actor 的状态名 vs 中间状态

Actor 作为状态机，真正需要持久化的往往**只有当前状态的名字**。在该状态下累积的具体运行时数据（当前路径、当前移动目标的插值位置、临时动画参数）都不该存——加载时以状态名为起点重算即可。

这和 [[multi-target-pathfinding|寻路]] 模块里"路径算一次、执行中不再重算"的约束是同构的：都是**"把易得的东西当派生量、只持久化真正的种子"**。

## 存档本身也应该是一条消息

云风强调：`save` / `load` 不应该是一个直接的函数调用，而应该是一条发给 Actor 的消息。消息处理时**只做一个标记**，每个 tick 末尾再检查标记、统一执行真正的 I/O。这样：

- tick 内部的计算不会被 save 打断，数据一致性天然保证。
- load 发生在所有 Actor 都"静止"的时刻。
- save 和 load 配对出现时（例如 quick save / quick load），可以在同一 tick 末先 save 再 load。

这和 [[render-graph|render graph]] 思路接近：**分离"声明"和"执行"**，所有命令先收集、帧末统一结算，把并发与时序问题压到最小。
