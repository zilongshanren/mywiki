# 受约束的 LLM 文本生成（游戏 NPC 对话）

在游戏场景中，直接将大语言模型（LLM）用于运行时对话面临一个根本问题：模型输出难以控制，可能脱离角色或产生有害内容。**受约束的束搜索（constrained beam search）**是一种以「限制输出形式」换取「可控性」的折中方案——它保留了 LLM 的语义理解能力，但把最终输出锁定在一个预审核的短语集合或语法结构内。

## 核心思路

LLM 的文本生成本质是对 token 树的搜索：从 prompt 出发，每步选择下一个 token，直到生成终止符。束搜索（beam search）同时维护多条候选路径，而不是贪心地选最高概率的一条。

受约束的束搜索在此基础上加一个过滤器：每步只保留**符合某个前缀约束**的 token。HuggingFace Transformers 通过 `prefix_allowed_tokens_fn` 回调实现这一点——在每次 token 候选评分之前，调用方提供的函数可以返回一个白名单，屏蔽所有不在预批准路径上的 token。

这样，如果预批准的输出集合是一组短语（如 NPC 的固定台词库），模型就只能从这些短语中选择，但选择逻辑仍由模型的语言理解驱动，而非随机或规则硬编码。

## 扩展变体

- **固定短语集**：最简单的形式。适合 FAQ 机器人、简单 NPC 对话。模型退化为分类器，但句子本身可以很丰富。
- **语法约束**：将 Tracery 或类似的程序化语法作为树过滤器。LLM 充当语法扩展的「智能选择器」，在每个扩展点选择最符合上下文的规则，而不是随机展开。比单纯的 Tracery 更具语义连贯性。
- **结构化输出约束**（JSON schema）：强制输出符合固定 JSON 结构，解决 LLM 在结构化生成任务中频繁偏离 schema 的问题。对需要解析模型输出的工具调用场景非常实用。

## 局限

约束生成不能提升 LLM 的事实准确性——如果约束集合里有错误的选项，模型仍可能选到它（GPT-2 在「How many quarts in a gallon?」中优先选到了错误答案 `13`）。此外，如果短语集规模不大，做束搜索意义不大，直接对每个候选独立评分（分类）更高效。该技术的价值在于**安全边界**，而非生成质量本身。
