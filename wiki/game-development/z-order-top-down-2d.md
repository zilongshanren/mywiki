# 俯视角 2D 游戏的 Z 序

俯视角 2D 游戏（像 *塞尔达：众神的三角力量*、*星露谷*、各种 Action RPG）需要解决一个看似矛盾的问题：明明所有精灵都画在同一个 2D 平面上，却要让玩家相信"角色站在树后面"或"敌人正绕到柱子前面"。实现这种伪深度的工具叫 **z-order（绘制顺序）**：后绘制的精灵盖住先绘制的。Elias Daler 在 2013 年总结了两种主流做法以及它们的取舍。

## 静态层方案：分层 + 手工拆图

最朴素的做法是给每个精灵预设一个固定的 `z` 整数层级，绘制循环里按 `z = 0, 1, 2, ...` 顺序遍历。这正是 *塞尔达：众神的三角力量* 处理静态地物的方式：树、房子之类需要遮挡角色的部分被**事先拆成两片**——下半部分放低层（角色画在它之上），上半部分放高层（画在角色之上）。这种拆图法实现简单，对静态场景非常稳健。

代价是**美术与代码都要为每张图额外做工**：每加一棵新树就要切两次图、调一次层级；而且对**移动物体**毫无帮助——两个互相绕圈的敌人到底谁应该盖谁，固定层级答不上来。

## 动态 Y 排序方案：按 bounding box 底边排序

更通用的办法是利用一个朴素但极其有效的观察：**俯视角下，"底边 Y 坐标更大"的物体在视觉上更靠近相机**。所以把当前屏幕上所有可见精灵按 `boundingBox.top + boundingBox.height`（即 box 的最低边 Y）从小到大排序，再依此顺序绘制，就能自动得到正确的遮挡关系。Link 站在树前时，他脚下的 Y 比树根更大；他绕到树后时，树根的 Y 比他脚下更大——切换是连续而免维护的。

这个算法的优雅之处在于它**消除了所有手工层级标记**：美术只要给精灵定义碰撞 box，排序自动发生。它和 [[ecs|ECS]] 风格的渲染系统结合得很自然——把所有持有 `Sprite + Bounds` 组件的实体收进一个 vector，按底边排序后顺次发 [[draw-call]] 即可。

## 复杂物体：z 轴 + 多 box 拆分

一旦遇到带"拱门"或"房子门洞"这类**自身上下结构会让玩家穿过**的物体，单一 box 的 Y 排序就不够了。解决办法是把这种物体拆成若干小部分，每个部分有自己的 box，再额外引入一根**真实的 z 轴**记录"离地高度"——`z = 0` 是地面（参与 Y 排序，会被角色穿过），`z = 1` 是抬高的部分（永远画在所有 `z = 0` 的之上，玩家看起来就是"穿过门洞"）。最终的排序规则变成"先按 z 分桶，每个桶内按 Y 排序"。

要注意作者强调的语义：这里的 z 不是真正的 3D 深度坐标，而是"绘制层 + 碰撞层"的复合标签——同一个 `z` 层内的物体之间才进行 Y 排序，跨 z 层不互相干扰。这同时给碰撞系统带来好处：地面单位永远不必去检测高架物体的碰撞。

## 性能考量：静态 vs 动态分桶

读者评论里提了一个常见担忧：200×200 tilemap 每帧排序所有可见精灵会不会太慢？作者的回答抓住了关键——**静态物体只排一次**，把结果缓存为一个有序列表；每帧只对**移动物体**单独排序，再 merge 进静态列表。这是典型的"把不变的开销移出主循环"思路，和 [[culling]]、[[batching]] 等优化的精神是一致的。

俯视角 2D 的 Y 排序至今仍是标准做法——从 RPG Maker 到 Unity 的 2D 工程模板（Sorting Group / Transparency Sort Axis），背后的原理都是这一个 12 行的算法。
