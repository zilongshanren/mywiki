# A* 寻路与动态环境下的取舍

A* 是游戏 AI 里最常用的启发式寻路算法，本质是 Dijkstra 的一种优化：引入一个"剩余距离估计"的启发函数，让搜索优先扩展"更像是解"的方向。

## 算法谱系

[[people/gameknife|gameknife]] 在 2019 年的"重新启发"总结里回顾了三种经典算法：

- **Dijkstra**：遍历整个可行走节点空间，一定能找到最短路径，但效率低到基本不可用。
- **Greedy Best-First Search（贪心）**：每步都选最接近终点的邻居，不走回头路。复杂度极低，但容易"短视"，常常不是最优解。
- **A\***：在 Dijkstra 的 `g(n)` 上叠加启发项 `h(n)`：

  ```
  f(n) = g(n) + h(n)
  ```

  其中 `g(n)` 是已经走过的实际代价，`h(n)` 是到终点的预估（常用欧式距离）。A\* 的两个极端正好退化成前两者：`f=g` 时是 Dijkstra，`f=h` 时是贪心。

## g(n) 是游戏性的入口

A* 的工程乐趣不在 `h`，而在 `g`：把游戏性需求编码成代价就行。作者举了自己"地形道路生成"里的 g 函数设计：

- **坡度代价**：越陡越贵 → 路径自然形成盘山公路。
- **水域代价**：越靠近水越贵 → 路径倾向于远离水面。
- **曲率代价**：持续计算最近三个路径点的曲率 → 路径倾向平直。
- **阻挡代价**：水、峭壁给 `+∞` → 此路不通。

效率与 `g` 的分布直接相关：**当 `g` 代价在空间上非常均匀时，A\* 会像水波一样展开，搜索次数暴涨**；非均匀的 `g` 能让搜索快速收敛到一两条可行走廊。

## 动态环境：NavMesh 的困境

A\* 只是搜索策略，真正麻烦的是"在什么图上搜"。NavMesh（体素化生成的导航面）是静态大场景的标准答案：一次性烘焙、查询极快、原生支持 3D 寻路。

但一旦场景是 **高频动态** 的——可行走的移动平台、断桥、临时地洞、坍塌地形——NavMesh 的"生成开销 > 它能为寻路节省的时间"。作者给出的思路是：

- **2D Node 空间的局部重采样**：环境初始化或改变时，只对受影响区域重采样，落到 2D grid 上。
- **多层 2D 联通**：传统 grid 的连通性是 4/8 邻域，为了在 3D 空间里表达跨层移动，把空间分成多层 2D，通过特定"入口"做跨层连通。
- **自定义 g(n) 叠加游戏性代价** + ARA\* / D\* / B\* 等 A\* 变种做增量搜索。

## 搜索网格的空间裁剪

道路生成场景里，作者把搜索限定在 **以起点终点中点为圆心、以起终点距离为半径** 的圆形子空间内。这是个很实用的小技巧：牺牲"理论最优"换来一个有界搜索空间。
