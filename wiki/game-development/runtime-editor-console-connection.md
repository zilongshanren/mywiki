# 运行时编辑器-主机连接（Runtime Editor-Console Connection）

**让美术在 PC 编辑器里实时调参，主机上跑着的游戏同步响应**——这是 _The Witcher 2_ Xbox 360 版在主机移植过程中写出来的一套网络协议工具。[[bartosz-wronski|Bart Wronski]] 的总结是「**迭代速度比加特性更重要**」：一个几天写完的 tooling 带来的生产力收益，远超过同期大部分引擎特性。这篇文章不谈渲染，而是一篇**主机时代工具链设计的复盘**——什么功能值得做、哪些会坑、哪些当时没做但应该做。

## 为什么需要这个工具

_The Witcher 2_ 是 CD Projekt RED 第一次完全自己内部做主机版。X360 比游戏的原始目标 PC 落后一代，很多内容需要为了性能重写、裁剪、重调。两类问题特别逼人：

### 1. 光照系统的取舍

游戏**没有 GI / 没有烘焙**——所有光照动态。为了"伪 GI"，美术在一些场景里摆了**多达 40 盏**不同类型的局部光（additive / modulative / diffuse-only / specular-only / character-only / gobo / 带动画的烛火 shadow-casting 灯……），尤其"modulative"灯是反向减光用来伪造大范围 AO / 软阴影，比真 shadowmap 便宜很多。这在 PC 上跑得动，在 X360 上直接崩。

问题是：**不能靠离线工具判断哪盏灯该砍**。你需要同时看到光照叠加和场景绘制的总成本，还要按「这个镜头里可以花多少 ms」的可变预算决定——有些过场 12 ms 光照也是可以的，只要网格绘制 < 10 ms。这种决策必须在主机上跑的真实场景里做，必须在美术的手里做。

### 2. 色彩精度断崖

为了性能，X360 版把 lighting buffer 从 16-bit 砍到 RGBA1010102（带一个 exp bias 近似同样的动态范围），同时改了 color grading 算法、加了 filmic tonemap、重调了 gamma 曲线去适配电视。结果是 banding 四起、色彩和 PC 校准屏幕上完全不一样。美术需要**坐在电视前**一边看主机画面一边调环境预设，而不是在 PC 上瞎猜最终色相。

这两种需求都指向同一个答案：**开一条从编辑器到主机的实时通信通道**。

## 协议与实现

编辑器和引擎之间本来就有一条网络调试通道——_The Witcher 2_ 内置一套自己写的类 C 脚本系统，带 RTTI、状态机、调试器、采样 profiler，脚本 IDE 可以远程连到跑着的编辑器或游戏里打断点、热重载脚本，添加动态 property 后编辑器的 property grid 都会自动刷新。既然这条通道在，**多开一个端口监听另一类命令**就顺理成章。

第一天就把前几条命令跑起来了。整个系统是**命令式**的：编辑器端发事件（改属性、移动物体、切预设），主机端 replay 这些事件。

### 常用命令集

- **Camera 劫持**：编辑器把完整相机属性（位置、旋转、near/far/FOV）序列化过去。副作用意外地好——它帮你调试流式加载：如果主机画面上少了东西而编辑器里有，就能查是 streaming layer 没激活、还是 culling 标志错了、还是 cooker export 漏了。
- **Streaming layer 加载 / 卸载**：命令列表发到主机的 streaming 系统。原本想用来做内存和 CPU culling profiling，但实际上没特别有用——因为 streaming layer 同时被玩法系统用来做叙事分支（非线性剧情），hide/unhide 的时机被玩法逻辑控制。Wronski 的反思是：**这是实体系统设计上的失误——没有把"对象逻辑"和"视觉表现"分开**，导致工具做了也不好用。
- **灯光的添加 / 移动 / 属性修改**：新灯组件一旦创建、任意属性一旦改动，就发一条 replication 命令过去。缺点：**主机重启就全丢**——要么在编辑器里保存 + 重 export，要么手动重放所有改动。
- **简单 mesh 移动**：没有玩法逻辑的静态 mesh 被打包成一个紧凑的列表（不像 entity 那样吃 template 内存开销），可以直接移动；由于用了 [beam-tree 形式的动态遮挡层级](http://www.flipcode.com/harmless/issue01.htm)，不用重算加速结构。
- **环境预设**：最复杂的一条。环境系统是多优先级、按区域覆盖的时间曲线容器（太阳、天光、雾、color grading、light group 色相……）。连上以后**主机上的环境系统被整个关掉**，所有参数直接从编辑器插值推过去。
- **HLSL 后处理 shader 重载**：Wronski 认为这条是所有引擎的必备项。

## 没做但当时就该做的事

Wronski 的复盘同样有价值，它明确列出了"若当时有时间就做"的几条：

- **预编译资源的替换**（mesh / texture）——静态 cache 文件没做动态性，所以不能热换贴图和网格。植被密度性能问题几乎是 Wronski 在每个项目里都撞到的头号大问题，能热换贴图可以直接定位。
- **美术创作的材质 / particle shader 替换**——shader cache 同样静态。
- **navmesh 和 gameplay collision**——静态物体能动，导航和碰撞不能动。对关卡 / 任务设计师来说这是重要痛点：改一下 blocker 的位置就要重启整个任务链。
- **粒子系统**——属性序列化 + 网络复制 + 反序列化，这条路本来写起来不难，但始终没优先级够。
- **动态物体（角色）**——涉及太多全局 manager 和状态捕获/重建，在主机内存受限下非常难，需要大规模 refactor。
- **主机上热重载脚本**——最终极的目标。主机版故意剥掉了完整 RTTI 以省性能，加回去就又是一次取舍。Wronski 把这条标记成"未来终极挑战"。

## 设计教训

几条可以跨项目复用的观察：

- **在已有网络通道上加新命令类型，比写第二条通道简单得多**。复用一个 TCP 端口 + 命令路由是最低成本的起点。
- **"小团队 KISS" 警告**：脚本热重载这种"高级特性"会在每次重构时被悄悄搞坏——因为没有专人维护。链路一旦不稳定，用户就会绕开它去用 save-and-restart，你得到的 bug 报告就会更少，然后越修越少，最终死亡循环。Wronski 的说法："如果没有一个大团队去专门维护，请 **KISS**。"
- **对象系统要把"逻辑"和"可视化"分开**——否则所有 tooling 都会被玩法副作用污染。Streaming 命令的失效是活教训。
- **主机重启丢状态**几乎是所有 replication 系统的默认缺陷；想真正稳就得加一个"重连后同步差异"的协议，但那是另一个量级的工程。
- **工具做在正确的地方**：美术和设计师的迭代速度 = 最终游戏质量。"几天写成的网络协议"换来几个月的美术效率，这是最划算的投资之一。
