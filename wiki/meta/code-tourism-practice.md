# Code Tourism：把读代码当成看艺术

2011 年 1 月 [[angelo-pesce|Pesce]] 在 C0DE517E 上提出一个口号化的说法——**code tourism**：把阅读他人代码当成像画家「朝圣大师原作、逛画廊、游历城市」一样的学习方式。这篇短文在他 2010 年的 [[code-as-art-manifesto|代码平权宣言]] 之后出现，是那份宣言的**教育学侧补充**——如果承认代码是艺术，那么学习代码也应该有对应的美学熏陶通道，而不只是读书、写代码、再读书、再写代码的闭环。

## 核心观察

Pesce 从画家的学徒流程开始：搜集参考（读论文）→ 画小稿（探索式编程）→ 打草图、分块、细化（自顶向下编码）。这部分对应的是**做**。但画家除此之外还做另一件事——**系统性地研习历史、研习同行**：逛美术馆、走建筑、被前人作品震到。

程序员呢？我们入门时会翻别人的源码、加入小项目、改一改东西；但一旦「变得有经验」，就容易把这个动作丢掉。两个原因：一是**自命不凡**——觉得自己已经足够了；二是**成本太高**——读懂一个陌生项目代价昂贵，且事先不知道里面有什么值得看。

## Pesce 的提议

- **Code galleries**：开源项目应当在 wiki 上有专门的「入口页」，列出值得一读的主路径、典型函数、精彩片段——像旅游局的 sightseeing 指南。他举了一个 Stack Overflow 问答（「Linux 内核哪些部分可以读来找乐子？」）作示范。
- **有些项目天生「旅游友好」**——boost 这种，规整但难「住」；有些项目像他的老家 Naples，宝藏多但对游客不友好——这两种代码都需要导览。
- **公司内部同样适用**：每次他加入一个新项目，第一件事就是梳理渲染主流程并写一份 wiki 页面，标出「应该从哪里开始读、哪几个函数是主街、主要地标在哪」。他提议把这个实践制度化——不止入门导览，还可以维护一个「精彩片段陈列馆」：由 lead / TD 在代码评审时摘录值得欣赏的代码段、附上短评。

## 和其他想法的串联

- **代码即艺术**：直接承接 [[code-as-art-manifesto|code rights]]——既然代码是艺术，就需要「美术馆 / 美术史」层面的基础设施，而不只是「工厂」层面的工具链。
- **Tools 诉求**：和 [[c0de517e-pix-is-great-but|PIX is great but]] 一脉相承——真正有用的是项目**内建的导览**，不是外部工具。
- **反对闭源文化**：评论区读者补充「闭源世界是糟糕的学习场所」——Pesce 没有直接展开，但整篇文章隐含了这点：**如果代码都藏着，code tourism 就没法成立**。
- **有别于 kata**：Pesce 明确提到此文的诱因是 Atwood 的「the ultimate code kata」，但他反对把学习完全压缩到「自己写练习题」——读别人的代码同等重要。

## 历史位置

这个想法在 2011 年还只是一个半正经的口号。到 2020 年代，它部分兑现：

- GitHub 成为默认的公共代码展览空间；
- 许多开源项目确实有了 `CONTRIBUTING.md`、`ARCHITECTURE.md`、代码 tour 文章；
- 「读源码」类博客文章（比如 [[adrian-courreges|Courrèges]] 的 graphics study、[[jasper-st-pierre|Jasper St. Pierre]] 的 Mesa 源码漫游）形成了一个稳定的体裁；
- 但「公司内部代码陈列馆 / 精彩片段库」在大多数团队仍然不存在——仍然依赖口口相传和 code review 当下的交流。
