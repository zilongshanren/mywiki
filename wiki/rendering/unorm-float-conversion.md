# UNORM8 → float 的精确转换

GPU 的 UNORM8 纹理把 `[0,1]` 区间的实数压成一个 8-bit 整数 `x`，反向解码的「数学定义」就是 `x / 255`。问题是：在 IEEE 754 单精度下，**多数实现并不真的做这个除法**，而是用 `x * (1/255)` 近似——`1/255` 不是机器数，所以个别 `x` 上会差 1 ULP。D3D11 功能规范明确写过「要求 1/2 ULP 的精确转换被认为代价过高」，而事实上现代硬件普遍能做到精确，并不需要真除法器。

## 为什么 `x * (1/255)` 不够精确

`1/255` 在 float32 里只能舍入存储，乘上某些 `x` 后，舍入方向和「真除法再舍入」不同。对 UNORM8 来说总共也就 256 个值，可以穷举验证：少数样本的最低位差 1。对图形而言这通常无所谓，但**作为正确性问题**值得有干净解法。

## 解法一：用 double 做中转

把 `x` 升到 float64，乘上精确的 `1./255.`，再降回 float32——可以证明结果与 `x / 255.f`（float32 除法）一致。穷举 256 个值即可验证。直观但很多场景不愿引入 double。

## 解法二：把 `1/255` 展开为几何级数

`1/255 = 2⁻⁸ + 2⁻¹⁶ + 2⁻²⁴ + …`，每一项都是 2 的幂、可以无损地用乘法表达。证明只需要 5 项就足以让 round-to-nearest 命中正确值（再加一项作为 sticky bit 防止半数舍入歧义），ryg 给出的成品只用两次乘加：

```c
const float k0 = (1.f + 256.f + 65536.f) / 16777216.f;
const float k1 = k0 / 16777216.f;
float r = (float)x * k0 + (float)x * k1;
```

第一次乘法把 `x` 复制成 3 段连排的 24-bit 显著数；第二次乘法再产生 24 bit 的低位续接；最后一次加法是唯一的舍入点。FMA 可用时只需 2 次浮点指令。

## 解法三（更短）：Alexandre Mutel 的 (3·x) ÷ (3·255)

`1 / (255*3)` 在 float32 里恰好是「足够精确」的常数，而 `3·x`（`x ∈ [0,255]`）也能无损地在 float32 表示。于是：

```c
return ((float)x * 3.f) * (1.f / (3.f * 255.f));
```

不需要 FMA、没有除法、两次乘法搞定。是目前公认的最短精确方案。

## 启示

这是一个典型的 **微内核数值优化**：硬件没有真除法，但在 [[ieee-754|IEEE 754]] 的舍入规则下可以用乘法 + 加法把 `1/255` 这种「看似要除法」的常数严格还原。同类技巧在 SNORM8、SNORM16 上也能找到对应的常数（`1/(31·127)`、`1/(73·32767)`），但 UNORM16 至今没有同样干净的两乘法构造。
