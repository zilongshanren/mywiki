# 光线追踪与光栅化的比较（Raytracing vs Rasterization）

[[angelo-pesce]] 2011 年这篇文章是一次系统性的「去神话化」，目标是拆解两个常见错误断言：「光线追踪可以被更有效地并行化」和「光线追踪有更低的算法复杂度」。文章的结论：**二者是对同一个双重循环的不同遍历顺序，各自的权衡是对称的，没有普遍胜者**。

## 双循环的对称性

两个算法的骨架可以用互相颠倒的两重循环来写：

**光线追踪**（外层遍历像素，内层遍历图元）：
```
for each pixel px: for each primitive pr: intersect ray(px) with pr
```

**光栅化**（外层遍历图元，内层遍历覆盖像素）：
```
for each primitive pr: for each pixel px covered by pr: mark px
```

循环顺序的翻转带来**内存访问模式的对偶性**：光线追踪需要把场景图元全部留在内存（内层循环），但每个像素可以以流式方式处理；光栅化只需要 z-buffer（逐像素的深度缓冲），场景图元可以流式送入，但 z-buffer 要驻留内存。

## 复杂度并不不对称

「BVH 让光线追踪达到 O(log N)」的常见论断**只对了一半**：

1. 空间加速结构在光线追踪里是标配，但等价的层次化遮挡剔除（HOMs、hierarchical z-buffer）也可以给光栅化带来相近的对数级别复杂度。
2. 构建加速结构本身是 O(N) 或更高，动态场景下每帧重建会吞噬所有理论收益。
3. 在现实游戏场景中，光栅化配合 frustum culling、LOD、early-z 已可线性扩展，并未遭遇深度复杂度瓶颈。

## 并行化的神话

初学者写光线追踪容易并行化，是因为内层循环（图元遍历）是无状态的；光栅化的 z-buffer 有共享状态，需要同步。但这只是"裸算法"层面。

一旦加入**空间加速结构和着色**，光线追踪的并行性就崩塌了：

- 相邻像素的光线可能在 BVH 里走到完全不同的深度层，无法 SIMD。
- 不同图元的着色需要不同材质，内存访问高度不一致。

应对策略（ray packets、ray reordering、QBVH 扩宽加速结构宽度等）多年来一直是研究热点，但都有适用范围。GPU 光栅化反而以几何上的强一致性在相同硬件预算下持续领先。

## 各自真正的权衡

| 维度 | 光线追踪 | 光栅化 |
|------|----------|--------|
| 一致性（coherence）| 弱，加速结构+着色后严重发散 | 强，图元遍历天然局部 |
| 全局可见性查询 | 直接，任意方向光线 | 间接，需近似（shadow map, SSAO…） |
| 遮挡剔除 | 内建在 BVH 遍历里 | 需额外层次化 z-buffer 或 SW occlusion |
| 动态场景 | 加速结构更新是研究难题 | 无此约束 |
| 着色生产力 | path tracer 百行实现全局光照 | 需大量近似算法 |

Pesce 把这对关系类比为**静态类型 vs 动态类型语言**：二者都是图灵完备的，从各自的端点向对方靠近；性能这条轴历史上更多决定技术主流，所以即便 Haskell 在理论上更优雅，C++ 还是更普及。

## 对未来的判断（2011 年视角）

- 实时光线追踪短期内不会进入游戏主流，**不是因为算法弱，而是因为硬件生态尚未准备好**。
- 离线渲染（Pixar Renderman = REYES 光栅化器）在 2011 年依然是混合的，并不是全面倒向光线追踪。
- 最终答案很可能是**混合管线**：不同子问题选择最合适的可见性算法。
