# 可变长度 Bresenham 直线

标准的 [[bresenham-lines]] 解决的是“从点 `(x0,y0)` 到点 `(x1,y1)` 绘制一条整数直线”这一问题。但在 roguelike、射线投射、视野计算等场景中，我们常常需要另一个形式的问题：**从 `(x0,y0)` 出发，沿某个方向走指定距离**——即可变长度直线。原始实现由于做了“起终点交换”这一优化，无法直接胜任这种需求。

## 问题所在

标准 Bresenham 依赖一个聪明的优化：算法只显式处理四个八分圆（恰好是自底向上那一半），入口处的 swap 把其他方向的线翻转成这四种之一后再画。其代价是——绘制顺序可能是从 `(x0,y0)` 开始，也可能是从 `(x1,y1)` 开始，取决于两端谁在下方。当我们只关心最终像素集合时这无所谓；但如果要沿着“起点→方向→走 `range` 步”来迭代，翻转会导致直线朝相反方向延伸，越过起点走向错误的一侧。

## 展开为八个八分圆

修复方式相当简洁：去掉入口处的 swap，改为显式枚举全部八个八分圆，然后让水平和垂直两个分支在主轴方向上迭代用户给定的 `range`，而不是走到 `(x1,y1)` 为止。作者 [[steven-sell]] 发现，展开后的代码反而比原始“只判四个八分圆 + swap”的版本**更短**——因为只需对 `dx`、`dy` 取绝对值来决定主轴方向，而不必再去检测两端位置、处理各种交换情况。设置 `range = 0` 时，新实现退化为标准行为，仍然画到 `(x1,y1)` 结束。

## 现代 CPU 上的“反优化”现象

原版 Bresenham 诞生自“每条乘法都贵”的年代，大量精力用于消除乘除、把循环压到最小。作者在 Chrome v72 上跑 jsperf 对比两个实现，结果却出人意料：

| 实现 | Ops/sec |
| --- | --- |
| 标准 Bresenham | 47,432,265 |
| 可变长度 Bresenham | 48,722,462 |

可变长度版本反而略快。这是一个关于 [[latency-vs-throughput]] 和现代 CPU 微架构的小型提醒：被有意“反优化”的直白代码，由于分支更均匀、结构更规则，有时比精心拼接的老式手工优化更容易被乱序执行和分支预测器吃下。至少在此例中，抛弃半数八分圆合并优化换来的是“几乎没有代价”的通用性。
