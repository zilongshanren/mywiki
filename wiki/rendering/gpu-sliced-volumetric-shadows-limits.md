# GPU 切片体积阴影：在「偏不透明的粒子云」上的失败模式

NVIDIA 在 *Smoke Particles* 白皮书（含 CUDA SDK sample）里推广的 **sliced shadow** 算法是一种把视角方向和光源方向同时考虑的粒子自阴影方案：**沿某个方向把所有粒子按深度切成薄片，每切一片就把它先绘到主缓冲、再把结果累加进一张"已阴影"纹理，后面的切片采样这张纹理拿到前置粒子的遮挡**。切片数越多，阴影积分越平滑、结果越接近真实多重散射。

Ben Supnik 在 X-Plane 团队试图把它用到 **飞行模拟里的真实云** 时踩到一组互相挤压的约束，最终证明这个算法**在 flight-sim 云场景下根本用不起来**。这篇把他拆给出来的几条失败路径汇总下来。

## 一、算法的两条性能瓶颈

- **fill-rate 受限**：所有大量重叠的粒子系统都有这个问题——粒子越多、越半透明，overdraw 越重；
- **切片数受限**：每加一片都要把当前渲染目标 **rasterize-to-texture 再 sample-from-texture**，每片都强行在 GPU 管线里插一条显式的 barrier。NVIDIA 白皮书推荐 **32–128** 片才看得出软阴影质感，这个下限本身已经对驱动 + render target 切换成本提出了要求。

## 二、"偏不透明 + 数量少"的粒子设置让算法失去内建的柔和性

flight-sim 云的工程习惯恰好是 sliced shadow 的**反面**：为了省 fill-rate，少量但偏不透明的粒子 + 贴花来撑体积感。

这里出现第一个 mismatch：sliced shadow **依赖"单个粒子不够黑"来让 self-shadowing 柔和**。它本身并没有主动控制自遮挡强度的机制——它默认"两个相邻粒子都是半透明，叠在一起也不黑"。当你换成偏不透明的粒子，**紧邻的两片就会相互投重黑影**，阴影立刻变硬变脏。想通过减少切片数来掩盖这个问题又会引出下一条失败模式。

## 三、bucket culling 和 slicing 的冲突

真实飞行环境里粒子数上量后必须做空间 bucket：**一方面快速剔除视锥外/镜头远处的粒子，一方面 bucket 本身的遍历顺序能帮你少排序（只要桶间有序就只需桶内排序）**。

但 bucket 和 slice **共用的是"切平面"这个资源**：

- 全局 slice 数被"每个 bucket 分几片"摊薄，典型情况下 **每桶 8 片都很勉强**；
- 桶和桶之间的切面不对齐——**两个 bucket 的切面边界处会出现 seam**；
- 推荐的 32–128 片在分桶后基本不可达。

## 四、相机旋转时的 popping

sliced shadow 的切面是沿"视角 + 光源"合成的方向切的。切片数越少，**每一片的厚度越大**，里面的一组粒子 **要么一起被算进阴影、要么一起被漏掉**。相机稍一旋转，原本同属一片的两个粒子就会跨到相邻的两片里——**互相投影关系瞬间变化，画面上表现为阴影 popping**。

最坏的一种 popping 来自 **太阳从相机前方翻到相机后方** 这一刻：这时切片方向要整体翻转 90°（因为 front-to-back 与 back-to-front 排序方向互换），**所有粒子的阴影关系全部重排**。切片多时这种过渡还能被平滑掉；切片少时，这是一次肉眼可见的"阴影 pop"。

## 五、结论：什么时候不能用

Supnik 总结的三条同时成立就会失败：

1. 粒子偏不透明；
2. 切片预算低（无论是因为分桶还是 render target 切换成本）；
3. 有外部约束（culling、bucketing）在进一步抢切片额度。

flight-sim 云刚好三条全部占。这个案例也说明一件很一般的事：**白皮书里的算法**都是在**作者选定的输入分布**下最优的——真正的工程判断是 **读算法时同时读它的"隐含前提假设"**：这里 sliced shadow 的隐含前提是"大量高度半透明粒子 + 无分桶"，脱离这个前提就会把每条弱点都暴露。
